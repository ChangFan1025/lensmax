## 1. Workspace 与 crate 划分

```toml
# Cargo.toml
[workspace]
members = ["crates/domain", "crates/app", "crates/jobs", "xtask"]
resolver = "2"

[workspace.dependencies]
axum = "0.8"
sqlx = { version = "0.8", features = ["runtime-tokio-rustls","postgres","macros","migrate","time","uuid","json"] }
tokio = { version = "1", features = ["full"] }
serde = { version = "1", features = ["derive"] }
serde_json = "1"
time = { version = "0.3", features = ["serde","formatting","macros"] }
thiserror = "2"
garde = { version = "0.20", features = ["derive"] }
tracing = "0.1"
```

```
crates/
  domain/     # 零 I/O、零 async、零 sqlx 查询。只有类型、常量表、纯函数、错误枚举
  app/        # 库：config, db, services, storage, auth, api, log
  jobs/       # bin：一个 binary，子命令选 job
  xtask/      # 开发命令：dev-db / gen-api / check-sqlx
migrations/   # SQLx 迁移（顶层，不进 crate）
.sqlx/        # 离线查询缓存，提交进仓库
```

**`jobs` 复用 `app` 的库，不重复实现。** 因此 `app` 的模块边界要干净：

```rust
// crates/app/src/lib.rs
pub mod config;
pub mod db;
pub mod services;
pub mod storage;
pub mod auth;
pub mod log;
pub mod api;      // ← 只在这里依赖 axum
```

`jobs` 引 `app` 但不碰 `app::api`，所以它的二进制里没有 HTTP 栈。`xtask` 不依赖 `app`。

**`domain` 不依赖 sqlx 的查询宏，但依赖 sqlx 的类型。** 具体做法：领域枚举派生 `sqlx::Type`，让 SQLx 直接读写，避免在 app 层维护一份字符串映射表：

```rust
// crates/domain/src/state_machine.rs
#[derive(Debug, Clone, Copy, PartialEq, Eq, serde::Serialize, sqlx::Type)]
#[sqlx(type_name = "text", rename_all = "SCREAMING_SNAKE_CASE")]
#[serde(rename_all = "SCREAMING_SNAKE_CASE")]
pub enum EquipStatus { InStock, CheckedOut, Maintenance, Disabled, Sold }
```

这样数据库里的 `'IN_STOCK'` 和 API 上的 `"IN_STOCK"` 与 Rust 的 `EquipStatus::InStock` 是同一个真理，只有一处定义。这条值 `domain` 引入一个类型层依赖。

## 2. 类型放置：三套类型，各有唯一职责

这是 Rust 落地里最容易做乱的地方。规则如下，不要混用：

| 类型 | 位置 | 职责 | 允许出现 |
|---|---|---|---|
| **Row** | `app::db::rows` | 精确对应一条 SQL 结果 | 所有列、可空列、无业务含义 |
| **Model** | `domain::models` | 业务对象 | 领域字段，不含 DB 细节 |
| **View** | `app::api::views` | 对外 JSON，**按角色裁剪** | 只有该角色可见的字段 |

```rust
// app/db/rows.rs —— 一行一条 SQL，字段名与列名一致
#[derive(sqlx::FromRow)]
pub struct EquipmentRow {
    pub id: i64,
    pub code: String,
    pub name: String,
    pub category_id: i64,
    pub brand: Option<String>,
    pub model: Option<String>,
    pub serial_number: Option<String>,     // 申请人看不到
    pub location: Option<String>,
    pub purchase_date: Option<time::Date>,
    pub price_cents: Option<i64>,          // 申请人看不到
    pub internal_note: Option<String>,     // 申请人看不到
    pub photo_id: Option<i64>,
    pub status: EquipStatus,
    pub archived_at: Option<time::OffsetDateTime>,
    pub created_at: time::OffsetDateTime,
    pub updated_at: time::OffsetDateTime,
}

// app/api/views.rs —— 两个结构体，权限差异由类型承载（主稿 D4）
#[derive(serde::Serialize)]
#[serde(rename_all = "camelCase")]
pub struct EquipmentRequester {
    pub id: String, pub code: String, pub name: String,
    pub category: String, pub brand: Option<String>, pub model: Option<String>,
    pub status: EquipStatus, pub location: Option<String>,
    pub photo: Option<PhotoRef>,
    pub actions: Vec<Action>,
}

#[derive(serde::Serialize)]
#[serde(rename_all = "camelCase")]
pub struct EquipmentAdmin {
    #[serde(flatten)] pub base: EquipmentRequester,
    pub purchase_price_cents: Option<i64>,
    pub purchase_date: Option<time::Date>,
    pub serial_number: Option<String>,
    pub internal_note: Option<String>,
    pub created_at: time::OffsetDateTime,
    pub updated_at: time::OffsetDateTime,
}
```

**`EquipmentAdmin` 用 `#[serde(flatten)]` 而不是复制字段。** 否则两个结构体会漂移——加一个申请人可见的字段时只改了 `Requester`，`Admin` 就不带了。

`flatten` 的代价是**不能用 `deny_unknown_fields`**、序列化会多一层拷贝。这里两者都无所谓（只序列化，不反序列化）。

**注意 `flatten` 与"不得下发"的配合**：`EquipmentRequester` 里不能有任何"申请人不可见但为了复用而塞进来的"字段。一旦有人往 `base` 里加一个 `serial_number: Option<String>`（哪怕值恒为 `None`），它会**跟着 `flatten` 出现在管理员的响应里**——而管理员的响应本来就有这个字段（在 `EquipmentAdmin` 自己那一层），于是 JSON 里出现**重复的键**，反序列化时以最后一个为准。这是一个只在序列化层暴露、不会被编译器发现的坑。**规则：`EquipmentRequester` 只放申请人可见字段，一个都不多。**

### 2.1 唯一的角色分支点

```rust
// app/api/views.rs —— 全项目只有这一个函数按角色分叉
pub enum EquipmentView {
    Requester(EquipmentRequester),
    Admin(EquipmentAdmin),
}

impl EquipmentView {
    pub fn for_actor(actor: &Actor, row: EquipmentRow, cat: &CategoryRow,
                     photo: Option<PhotoRef>, actions: Vec<Action>) -> Self {
        let base = EquipmentRequester { /* … 只搬可见字段 … */ };
        match actor.role {
            Role::Requester => Self::Requester(base),
            _ => Self::Admin(EquipmentAdmin { base, /* … */ }),
        }
    }
}

impl serde::Serialize for EquipmentView {
    fn serialize<S: serde::Serializer>(&self, s: S) -> Result<S::Ok, S::Error> {
        match self { Self::Requester(v) => v.serialize(s), Self::Admin(v) => v.serialize(s) }
    }
}
```

**为什么不用泛型 + type-state。** 更严格的做法是 `EquipmentView<A: Viewer>`，让 `EquipmentView<Requester>` 在类型系统里根本不存在价格字段，那样"给申请人返回价格"连编译都过不去。但它会让每个 handler 变成泛型、每个 `From` 变成带约束的 impl，可读性代价明显。

**决定：用上面的枚举 + 一个函数，再用测试守住它**（第 9 节 V1）。理由：本项目的角色只有三种、可见性规则只在一张表里（主稿第 3 节），一个函数足够小到能读一遍就确认。**type-state 留到"可见性规则变复杂"时再上。**

### 2.2 硬规则

> **handler 不允许自己构造 `EquipmentAdmin`。** 构造只发生在 `EquipmentView::for_actor` 里。

原因：一旦有一个 handler 图快，直接 `EquipmentAdmin { serial_number: row.serial_number, … }` 返回给所有人，权限边界就破了，而且没有任何机制会提醒。这条靠 code review + 测试 V1 守。

## 3. 事务模式

主稿 5.1 的形状在 Rust 里的具体落法。

### 3.1 签名约定

```rust
// 服务层：收 &mut PgConnection，收领域命令，返回领域结果
pub async fn checkout(
    conn: &mut PgConnection,       // ← 不是 &PgPool
    actor: &Actor,
    cmd: CheckoutCmd,
) -> Result<CheckoutView, AppError>;

// handler：唯一管事务边界的地方
async fn checkout_handler(
    State(st): State<AppState>,
    actor: Actor,
    Json(cmd): Json<CheckoutCmd>,
) -> Result<Json<CheckoutView>, AppError> {
    let mut tx = st.pool.begin().await?;
    let out = services::checkout(&mut tx, &actor, cmd).await?;
    tx.commit().await?;
    Ok(Json(out))
}
```

**收益是类型级的**：服务函数拿到的是 `&mut PgConnection`，它**无法**开出新事务、也无法拿到 pool。所以"状态变更与写历史必须同事务"（主稿 C1）不靠纪律，靠签名。

`&mut *tx` 是必须的写法（`Transaction` 通过 `DerefMut` 得到 `PgConnection`），别为了少打几个字符去解构 `tx`。

### 3.2 服务内部的顺序固定

```rust
pub async fn checkout(conn: &mut PgConnection, actor: &Actor, cmd: CheckoutCmd) -> Result<CheckoutView, AppError> {
    // 1. 锁行。批量按 id 升序（主稿 5.2），这里用 ORDER BY + FOR UPDATE 一次拿完
    let rows = db::equipment::lock_many(conn, &cmd.equipment_ids).await?;

    // 2. 状态机。收集全部违规再返回，不做部分成功（主稿 C4）
    let violations: Vec<_> = rows.iter()
        .filter_map(|r| domain::state_machine::check(r.status, EquipStatus::CheckedOut).err())
        .collect();
    if !violations.is_empty() {
        return Err(DomainError::BatchRejected { items: violations }.into());
    }

    // 3. 占用：先查（为人话），再插（正确性由排他约束兜底）
    let during = domain::occupancy::checkout_range(cmd.checkout_date, cmd.expected_date);
    for r in &rows {
        if let Some(c) = db::occupancy::find_conflict(conn, r.id, during, None).await? {
            log::reject_reserved(actor, &cmd, &c);
            return Err(DomainError::Reserved { /* … */ }.into());
        }
        db::occupancy::insert(conn, r.id, during, OccupancyKind::Checkout, None, None).await?;
    }

    // 4. 写 checkout / checkout_item
    // 5. 改状态
    // 6. 写 history（主稿 5.5 定的 UPDATE 语义同理）
    Ok(view)          // ← 不在这里记业务日志，见下
}
```

**业务日志记在 `tx.commit()` 成功之后，不在这里。** 这是重试策略逼出来的修正：

> 如果日志写在提交前，**3 次重试会产出 3 条 `biz.checkout`，其中两条对应已回滚的事务**。日志里于是出现"出库了三次"而数据库只有一次——排查时这是最坏的一类误导。

所以形状是：

```rust
let mut tx = pool.begin().await?;
let out = services::checkout(&mut tx, &actor, cmd).await?;   // 服务层只管数据
tx.commit().await?;
log::checkout(&actor, &out, &cmd);                            // ← 提交后才记
Ok(Json(out))
```

**这需要在 handler 层拿到记日志所需要的全部信息**，所以服务函数的返回值（`CheckoutView`）必须带上日志要的字段（`checkout_id`、`item_count`、`project_id`）。这是"返回新对象而不是 `{"ok": true}`"这条既有约定的又一个理由。

**代价**：如果提交成功但进程在记日志前崩溃，会丢一条业务日志。**接受**——日志不是事实来源（运行时篇 R1.1），而数据库里的事实已经落库了。这与"重试产生幽灵日志"是两个不同量级的问题：前者丢信息，后者制造错误信息。

**绝对不要**为了让日志和事务严格一致去用 `NOTIFY` 或两阶段——那是为不存在的问题引入的一致性机制。

### 3.3 批量取锁的写法

```rust
pub async fn lock_many(conn: &mut PgConnection, ids: &[i64]) -> Result<Vec<EquipmentRow>, AppError> {
    Ok(sqlx::query_as!(
        EquipmentRow,
        r#"SELECT … FROM equipment WHERE id = ANY($1) ORDER BY id FOR UPDATE"#,
        ids
    ).fetch_all(conn).await?)
}
```

`ORDER BY id` 必须在 `FOR UPDATE` 之前——这是防死锁的全部机制。**两个批量事务若按不同顺序取锁会互锁**，而这个 bug 只有在并发批量操作时出现，本地测不出来。

## 4. 状态机：唯一的合法性来源

```rust
// crates/domain/src/state_machine.rs
pub const ALLOWED: &[(EquipStatus, EquipStatus)] = &[
    (EquipStatus::InStock,     EquipStatus::CheckedOut),
    (EquipStatus::InStock,     EquipStatus::Maintenance),
    (EquipStatus::InStock,     EquipStatus::Disabled),
    (EquipStatus::InStock,     EquipStatus::Sold),
    (EquipStatus::CheckedOut,  EquipStatus::InStock),
    (EquipStatus::Maintenance, EquipStatus::InStock),
    (EquipStatus::Maintenance, EquipStatus::Disabled),
    (EquipStatus::Disabled,    EquipStatus::InStock),
    (EquipStatus::Disabled,    EquipStatus::Sold),
    // Sold 是终点，没有出边
];

pub fn check(from: EquipStatus, to: EquipStatus) -> Result<(), DomainError> {
    if from == to {
        return Ok(());   // 幂等：重复触发不算违规
    }
    if ALLOWED.contains(&(from, to)) { Ok(()) }
    else { Err(DomainError::IllegalTransition { from, to }) }
}
```

三点：

1. **用一张常量表，不写 `match` 的嵌套 if。** 这张表就是交接稿第 4 节那张表，一眼能对着校对。
2. **`from == to` 返回 Ok。** 两个管理员同时点"确认出库"，第二个事务拿到行锁时状态已经是 `CHECKED_OUT`，如果这里报错，用户会看到"不能从出库改为出库"这种荒谬提示。**幂等在这里是必要的**——但要注意：这让"重复出库"不会报错，而**重复出库必须由占用层的排他约束拦住**（第二次插入同一区间会冲突）。两层的分工要清楚。
3. **`EquipStatus` 的数据库 `CHECK` 约束（主稿 3.3）是第三层**，防止有人绕过代码改库。

## 5. 错误：三层翻译，一个出口

```rust
// domain
#[derive(Debug, thiserror::Error)]
pub enum DomainError {
    #[error("不能从“{from}”改为“{to}”")]
    IllegalTransition { from: EquipStatus, to: EquipStatus },
    #[error("已被「{project}」在 {start} 至 {end} 占用")]
    Reserved { project: String, start: Date, end: Date },
    // …
}

// app
#[derive(Debug, thiserror::Error)]
pub enum AppError {
    #[error(transparent)] Domain(#[from] DomainError),
    #[error("{0}")] Validation(ValidationError),
    #[error(transparent)] Sqlx(SqlxError),          // ← 带原始 SQLSTATE，见 5.1
    #[error(transparent)] Io(#[from] std::io::Error),
    #[error("上传失败：{stage}")]
    Upload { stage: UploadStage, source: anyhow::Error },
}

/// 校验错误不能 `#[error(transparent)]`——那会把 garde 的**英文** Display
/// （`length is not in range`）直接交给用户，而主稿 7.3 规定 message 直接进
/// 表单内红条、5.2 规定 Display 是给用户看的中文。
pub struct ValidationError {
    pub field: Option<String>,   // snake_case 路径 → camelCase，如 "purchaseDate"
    pub code: &'static str,      // "TOO_LONG" / "REQUIRED" / "INVALID_FORMAT"
    pub message: String,         // 中文，直接给用户
    pub all: Vec<(String, &'static str)>,  // 其余问题，供一次性列出
}

/// 包一层是为了留住原始 SQLSTATE：重试分类（实现契约 §4）必须区分
/// 「08006 可重试」与「57014 不可重试」，而一旦翻成 DomainError 就分不出了。
pub struct SqlxError {
    pub source: sqlx::Error,
    pub sqlstate: Option<String>,
    pub constraint: Option<String>,
}
```

**`Validation` 的 `field` 是主稿 7.3 错误信封里那个字段的生产者。** 原先没有生产者——信封定义了 `field` 但没人填。配套一条**元测试**：断言任何校验错误的 `message` 不含 `length` / `required` / `range` / `invalid` 这类英文词。

### 5.1 SQLSTATE 翻译集中在一处

**完整分类表在[实现契约](20260930_IMPL_CONTRACT_v1.md) §4.2 与主稿 8.1。** 本稿只写形状，因为完整的 `match` 有五大类、十几条约束名，抄在这里一定会与那边漂移：

```rust
/// 翻译点。返回 None 表示"没翻译"，调用方落 500 并记 error 日志
/// （未匹配意味着"有一条约束我没翻译"，那是要补代码的信号）。
///
/// 它**不收 AppError**，而是返回 Option<DomainError>，因为在服务层调用时
/// 才拿得到业务上下文（用户填的是哪个字段、编号是什么）。
pub fn translate_constraint(db: &dyn sqlx::DatabaseError) -> Option<DomainError> {
    match db.code().as_deref()? {
        "23P01" => Some(DomainError::Conflict),                  // 排他：档期冲突
        "23505" => translate_unique(db.constraint()?),            // 唯一：逐条 discriminate
        "23514" => translate_check(db.constraint()?),             // CHECK：→ 400，不是 500
        "23503" => Some(DomainError::ReferenceInUse { entity: "该记录" }),
        _ => None,
    }
}
```

三个实现要点：

- **约束名必须在迁移里显式命名。** 依赖 Postgres 默认命名（`equipment_workspace_id_code_key`）会在某次改列名时静默失配，而失配的表现是"这个错误不翻译了"，很难注意到。主稿第 8 节原先自己要求了显式命名，同节的示例代码用的却是默认名——**那处自相矛盾已修**。
- **`23514` 走 400 而不是 500。** 分类前缀填小写 `cam` 是用户会真的犯的错。给它 500 会让用户看到"服务器错误"而不是"前缀只能是大写字母和数字"，还会污染错误率指标。
- **`23P01` 翻译成错误还不够，要记 `biz.conflict` 的 WARN**（日志设计 6.1）。它是唯一"正常路径下不该出现"的告警。做法是在 `IntoResponse` 或中间件里按 `DomainError::Conflict` 记，**不是在翻译点记**——翻译点可能在无 span 的地方被调用。

### 5.1.1 重试：handler 层的包装器

**完整策略在[实现契约](20260930_IMPL_CONTRACT_v1.md) §4。** 这里只记它与本稿第 3 节签名约定的关系：

```rust
// handler 层唯一的重试入口。服务层收到的是 &mut PgConnection，
// 它看不到这个包装器，也无法自己决定重试。
pub async fn with_retry<T, F, Fut>(pool: &PgPool, f: F) -> Result<T, AppError>
where
    F: for<'c> FnMut(&'c mut PgConnection) -> Fut,
    Fut: Future<Output = Result<T, AppError>>,
{ /* 重新 begin() → f(&mut tx) → commit()；commit 失败不重试 */ }
```

**两条不能错的**：① `23P01`/`23505` **绝不重试**（重试必然再失败，而且把 409 变成 503——前端据此把"换日期"变成"稍后重试"，用户的下一步动作被改错）；② **`commit()` 失败不重试**（"响应丢包"与"连接断了"在客户端同形，重放会写出第二份数据）。靠封闭 enum + `_ => Fatal`（fail-closed）钉住。

`for<'c>` 这个 HRTB 写法是本设计里唯一一处生命周期会咬人的地方，**待验证**（本稿第 12 节）。

### 5.2 `IntoResponse`

```rust
impl IntoResponse for AppError {
    fn into_response(self) -> Response {
        let request_id = /* 从当前 span 或 task-local 取 */;
        let (status, code) = match &self {
            // 400 —— 用户输入类
            AppError::Validation(_)                                  => (BAD_REQUEST, "VALIDATION"),
            AppError::Domain(DomainError::InvalidField{..})           => (BAD_REQUEST, "INVALID_FIELD"),
            AppError::Upload{..}                                     => (BAD_REQUEST, "UPLOAD_FAILED"),
            AppError::Domain(DomainError::BatchRejected{..})          => (BAD_REQUEST, "BATCH_REJECTED"),

            // 401 / 403 —— 身份与权限
            AppError::Unauthenticated                                 => (UNAUTHORIZED, "UNAUTHENTICATED"),
            AppError::Forbidden(_)                                    => (FORBIDDEN, "FORBIDDEN"),
            AppError::Domain(DomainError::OwnerImmutable)             => (FORBIDDEN, "OWNER_IMMUTABLE"),
            AppError::Domain(DomainError::OwnerNotDisableable)        => (FORBIDDEN, "OWNER_NOT_DISABLEABLE"),
            AppError::Domain(DomainError::BrowsingDisabled)           => (FORBIDDEN, "BROWSING_DISABLED"),

            // 404 —— 不存在或已归档
            AppError::NotFound(_)                                     => (NOT_FOUND, "NOT_FOUND"),

            // 409 —— 冲突，改一改就能成功
            AppError::Domain(DomainError::Reserved{..})               => (CONFLICT, "RESERVED"),
            AppError::Domain(DomainError::Conflict)                   => (CONFLICT, "RESERVED"),
            AppError::Domain(DomainError::DuplicateCode{..})
                | AppError::Domain(DomainError::DuplicateCodeUnknown)
                | AppError::Domain(DomainError::DuplicateUserName)    => (CONFLICT, "DUPLICATE"),
            AppError::Domain(DomainError::ReferenceInUse{..})          => (CONFLICT, "REFERENCE_IN_USE"),

            // 422 —— 业务规则拒绝
            AppError::Domain(DomainError::IllegalTransition{..})       => (UNPROCESSABLE_ENTITY, "ILLEGAL_TRANSITION"),
            AppError::Domain(DomainError::CheckedOutNotArchivable)     => (UNPROCESSABLE_ENTITY, "CHECKED_OUT_NOT_ARCHIVABLE"),
            AppError::Domain(DomainError::OpenMaintenanceExists)       => (UNPROCESSABLE_ENTITY, "OPEN_MAINTENANCE_EXISTS"),
            AppError::Domain(DomainError::RequestingDisabled)          => (UNPROCESSABLE_ENTITY, "REQUESTING_DISABLED"),

            // 503 —— 稍后重试可能成功。**不是 500**：前端据此显示
            //        "系统繁忙"而不是"出错了"，用户的下一步动作不同。
            AppError::Domain(DomainError::TemporaryUnavailable)        => (SERVICE_UNAVAILABLE, "TEMPORARILY_UNAVAILABLE"),

            // 500 —— 真的出错了
            AppError::Sqlx(_) | AppError::Io(_)                        => (INTERNAL_SERVER_ERROR, "INTERNAL"),
        };
        // message 直接用 thiserror 的 Display（主稿 7.3：直接进表单内红条）
        // 内部错误不把 Sqlx 的 Display 给用户，只给 requestId
    }
}
```

> **这个 `match` 是穷尽的，所以它同时是一份"新错误必须落码"的检查表**：往 `DomainError` 加变体而不在这里给分支，**根本编译不过**。主稿第 8 节原先的枚举就是被这个机制抓出来的——`Conflict` 在别处已被使用却不在枚举里，另外四个变体没有分支。
>
> 加变体时要一起决定三件事：状态码、`code` 字符串、以及**是否可重试**（实现契约 §4.2）。

**`503` 与 `500` 的分界是有意的，也有测试守它**（实现契约 §3.7、§4.6）。

**硬规则：`Display` 输出直接是给用户看的中文，不允许在 API 层再拼一次文案。** 主稿第 8 节定了"违规给人话"，实现上就是让 `thiserror` 的 `#[error("…")]` 承担它。这样文案只有一处，而且领域层测试可以直接断言这句话。

**例外是 `Sqlx` / `Io`**：它们的 `Display` 会泄漏表名和路径，一律换成通用文案 + `requestId`，详情进日志。

## 6. Extractor 与鉴权

### 6.1 `Actor` 的获取

```rust
// app/auth/extract.rs
#[derive(Clone, Debug)]
pub struct Actor { pub id: i64, pub role: Role, pub workspace_id: Uuid, pub session_id: String }

impl FromRequestParts<AppState> for Actor {
    type Rejection = AppError;
    async fn from_request_parts(parts: &mut Parts, st: &AppState) -> Result<Self, AppError> {
        let sid = parts.cookies.get("sid").ok_or(AppError::Unauthenticated)?;
        let a = db::session::load_actor(&st.pool, sid.value()).await?   // 一次查询带出 user + role
            .ok_or(AppError::Unauthenticated)?;
        parts.extensions.insert(a.clone());   // 供日志中间件读 actor_id/role
        Ok(a)
    }
}
```

**每请求一次会话查询。** 主稿第 9 节已经定了这个取舍：十人规模下这次查询可以忽略，换来的能力是"停用账号即踢下线"。

`parts.extensions.insert(a.clone())` 这一句是日志中间件能拿到 `actor_id` / `role` 的前提（日志设计 7.4）。**如果 extractor 不写 extensions，日志里就永远没有 actor**——这个失败是静默的（JSON 里那个字段是空字符串），所以第 9 节有一条测试专门查它。

### 6.2 角色守卫

```rust
// app/auth/guard.rs
pub struct Admin(pub Actor);      // 只允许 OWNER / ADMIN
pub struct Owner(pub Actor);      // 只允许 OWNER

impl FromRequestParts<AppState> for Admin {
    type Rejection = AppError;
    async fn from_request_parts(p: &mut Parts, st: &AppState) -> Result<Self, AppError> {
        let a = Actor::from_request_parts(p, st).await?;
        if a.role.is_admin_or_above() { Ok(Admin(a)) } else { Err(AppError::Forbidden("需要管理员权限")) }
    }
}
```

**用类型做守卫，不用 `if` 做守卫。** handler 签名里写 `Admin` 就天然要求了角色；漏写会变成编译错误（少了 extractor），而不是一个能被忘记的运行时检查。

**OWNER 不可被改**这条不在这里（它是业务规则，不是路由规则），放在 `services::account::change_role` 里显式判断并返回 `DomainError::OwnerImmutable`（主稿第 9 节）。

### 6.3 中间件顺序：不要靠记忆，要写测试

```rust
Router::new()
    .merge(api_routes())
    .layer(from_fn(auth_middleware))       // 会话 → extensions
    .layer(TraceLayer::new_for_http()…)    // 日志 span
    .layer(RequestBodyLimitLayer::new(8 * 1024 * 1024))
```

`Router::layer` 是"包住已经加进来的所有路由"，**同一段代码里后加的 `.layer` 在请求方向上先执行**。上面的顺序让 `TraceLayer` 先建 span，`auth_middleware` 往里插 actor。

**但这条规则我建议不要相信文档和记忆，直接写一个测试固住它**：

```rust
#[tokio::test]
async fn middleware_order_is_trace_then_auth() {
    // 打一个受保护的接口，断言：
    //   ① 日志里有 http span（说明 TraceLayer 在 auth 之前建了 span）
    //   ② 响应头里有 X-Request-Id
    //   ③ 该请求的业务日志带 actor_id（说明 auth 在 span 内执行并写了 extensions）
}
```

理由：**tower 的层级语义反直觉到"每个人都会理解错一次"**，而理解错的后果是"日志里永远没有 actor_id"或"每次请求都 401"——两种都是静默的，不会报错。一条几十行的测试能永久省掉这类排查。

**`MatchedPath` 只能挂在路由之后的层上。** 它是路由匹配阶段插入的 extension，所以：

- `.layer` 加载 Router 上（上面那个位置）→ `make_span_with` 里拿到的 `MatchedPath` 是 `None`，`route` 只能退化成实际路径 `/api/v1/equipment/1284`，**按端点聚合失效**。
- `.route_layer` → 匹配之后执行，能拿到模板，但**不作用于 fallback 和未匹配的请求**。

推荐 `route_layer` + 兜底：拿不到模板时就用实际路径。未匹配的请求（404）本来就该暴露实际路径——那正是"有人在扫路径"的信号。

> **这一节的两条（顺序、`MatchedPath` 的可见性）我无法在写文档时验证**（手边没有可编译的 axum 工程）。实现第一步就应该跑上面那个测试，并把结果写回本节。

## 7. `sqlx` 工作流

### 7.1 三种查询，三种写法

| 场景 | 写法 | 校验 |
|---|---|---|
| 固定 SQL（插入占用、取详情、改状态、写 history） | `sqlx::query_as!` / `query!` | **编译期**，需要活库 |
| 器材库的四个筛选器、排序、搜索 | `QueryBuilder` + `.bind()` | 运行时 |
| 报表、占用对账、巡检 SQL | `query_as` + 手写 `FromRow` | 运行时 |

**`QueryBuilder` 的那条硬规则**：拼进 SQL 的每一段都必须是编译期常量字符串，用户输入只走 `.bind()`。拼接类代码是最经典的注入点，而 `QueryBuilder` 的 API 让两者看起来一样。

### 7.2 离线缓存与 CI

```bash
cargo sqlx prepare --workspace        # 生成/更新 .sqlx/，提交进仓库
SQLX_OFFLINE=true cargo build         # 无库环境（CI）编译
```

`.sqlx/` 进仓库，CI 里加一条：

```bash
cargo sqlx prepare --check --workspace   # 改了 SQL 忘了 prepare 就红
```

**没有这条检查，"改了 SQL 忘了 prepare"会表现为"别人机器编译不过"**，而不是一个明确的错误——排查成本很高。

### 7.3 迁移

- 纯 SQL 文件，`migrations/0001_init.sql` 起步，forward-only。
- **每一条约束都显式命名**（第 5.1 节）。
- 迁移在**部署流程里单独执行**，不在应用启动时自动跑（启动时跑迁移在多实例下会互相竞争，而且失败现场难以复现）。`/readyz` 查迁移版本（运行时篇 R1.9）保证"忘了跑"会立刻暴露。

## 9. 测试骨架

### 9.1 分层与真库

```rust
#[sqlx::test(migrations = "../../migrations")]
async fn excluded_overlap_is_rejected(pool: PgPool) { /* 每个测试一个隔离库 */ }
```

`migrations` 的路径**相对于 crate 根**（即 `crates/app/`，不是 `src/`），所以要指到工作区顶层的 `migrations/` 就是 `"../../migrations"`。

> 这个相对基准（crate 根 vs `CARGO_MANIFEST_DIR`）和 workspace 下的解析行为，**要在第一条测试跑通时确认一次**，然后写进本节。写错的表现是"迁移没跑、表不存在"，而不是一个明确的路径错误——很容易被误判成 fixture 写错。

**不 mock 数据库**（运行时篇 R3.1）。`sqlx::test` 给每个测试一个隔离库并自动跑迁移，比 Testcontainers 快，且不需要 Docker（只要本地有 Postgres）。它需要 `DATABASE_URL` 或 `--database-url` 指向一个**可创建库的**连接。

**并发测试不能包事务回滚**，必须用两个真连接（运行时篇 R3.1）。写法：

```rust
#[sqlx::test(migrations = "../../migrations")]
async fn concurrent_overlapping_reservation_only_one_wins(pool: PgPool) {
    let a = pool.clone();
    let b = pool.clone();
    let (ra, rb) = tokio::join!(
        insert_reservation(&a, EQ, during),
        insert_reservation(&b, EQ, during),
    );
    assert!(ra.is_ok() ^ rb.is_ok(), "恰好一个成功");
    // 成功方是 Ok，失败方必须是 DomainError::Conflict，不是 Sqlx 原始错误
}
```

### 9.2 测试辅助

| 辅助 | 用途 |
|---|---|
| `fixtures::{empty, one_in_stock, one_checked_out_no_due, one_reserved, one_in_maintenance}` | 运行时篇 R3.3 的五个起点 |
| `LogCapture` | 日志设计 8.1 |

**V1：可见性契约快照**（运行时篇 #3 的强化版）

```rust
#[sqlx::test(migrations = "../../migrations")]
async fn requester_never_sees_forbidden_keys(pool: PgPool) {
    // 用 requester 打每一个 GET 接口，收集 JSON 的所有 key 路径
    // 断言不含：purchasePriceCents / serialNumber / internalNote / createdAt / updatedAt
    // 同时断言：这些 key 也**不以 null 形式出现**（主稿 7.7 的硬规则）
```

后半句是关键：**"字段存在但为 null" 也算泄漏**——它泄漏了字段的存在。这条断言比"值不为空"更强，也是唯一能守住主稿 7.7 那条"不用 `skip_serializing_if` 做权限"的测试。

**V2：服务层不接受 pool**

这条不是运行时测试，是**编译期的意图**。可以用 `trybuild` 写一个"故意传 `&PgPool` 给 `services::checkout`"的用例，断言编译失败：

`trybuild` 对签名变更的守门能力很强，而且它是**唯一能防止"有人为了图方便把签名改成 `&PgPool`"的机制**。

## 10. CI

```yaml
# 关键步骤（顺序有意义）
- run: cargo fmt --check
- run: cargo clippy --all-targets -- -D warnings
- run: cargo sqlx prepare --check --workspace      # 忘了 prepare 就红
- run: cargo build --workspace --locked
- run: cargo test --workspace                      # 需要 Postgres service
- run: cargo run -p xtask -- gen-api && git diff --exit-code   # 契约漂移
- run: git grep -n 'now_utc().date()' && exit 1    # 运行时篇 R2.3：业务日期必须走 business_today()
```

三条值得解释：

**`gen-api` 那条**（运行时篇 R6.3）：生成的 `openapi.json` 和 `schema.d.ts` 提交进仓库，CI 检查重新生成后没有差异。**没有它，主稿 D8（服务端下发 `actions`）会慢慢失效**——前端拿到的枚举值和后端实际的会对不上，而这是静默的。

**`now_utc().date()` 那条**：运行时篇 R2.3 的坑（东八区每天 08:00 前逾期判断少算一天）。这个约定没有类型能表达，只能靠 grep 守。**这类检查不优雅，但它守的是一个会静默给出错误结果的 bug。**

**`clippy -D warnings`**：本稿里好几条约定（比如"不要在 handler 里构造 Admin 视图"）无法用类型表达，而 clippy 至少能挡住一部分（比如 `clippy::too_many_arguments` 会把参数列表膨胀的 handler 标出来）。
