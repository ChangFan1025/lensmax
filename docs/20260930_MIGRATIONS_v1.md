## 1. 三条不可协商的前提

先摆清楚，后面所有规则都从这三条推出来：

### 1.1 迁移由独立的角色执行，不是应用角色

```sql
-- 应用角色：有超时，防止慢查询拖死连接
ALTER ROLE lensmax_app SET statement_timeout = '15s';
ALTER ROLE lensmax_app SET lock_timeout = '5s';
ALTER ROLE lensmax_app SET idle_in_transaction_session_timeout = '2s';

-- 迁移角色：**不设 lock_timeout**
CREATE ROLE lensmax_migrate LOGIN;
GRANT ALL ON DATABASE lensmax TO lensmax_migrate;   -- 实际按最小权限收紧
```

**为什么必须分开**：`ALTER TABLE` 需要 `ACCESS EXCLUSIVE` 锁。如果迁移用应用角色跑，`lock_timeout = 5s` 会让它在等待锁时**失败在迁移中途**——而迁移是一串语句，中断会留下半完成的 schema。见 §3.3。

### 1.2 迁移不在应用启动时跑

应用启动只做两件事：**读当前迁移版本**、**在 `/readyz` 里报告它**（运行时篇 R1.9）。

**为什么**：多实例部署时两个进程会同时尝试迁移并互相竞争；而且迁移失败时应用会陷入"启动一半"的状态，现场难以复现。

正确顺序是：

```
1. 跑迁移（独立步骤，独立角色，CI/CD 里显式一步）
2. 验证 /readyz 返回的 migrationVersion 是期望值
3. 部署新版本应用
```

**步骤 2 不是可选的**——"部署了但忘了跑迁移"的表现是第一个写操作在运行中途失败，而不是启动失败。

### 1.3 迁移是 forward-only 的 SQL 文件

- 纯 `.sql`，`migrations/0001_init.sql` 起
- **不用** `down` 脚本（见 §5 为什么）
- 每条约束**显式命名**（主稿 8.3）——这条和迁移强耦合，因为 `translate_constraint` 靠约束名 discriminate

## 2. 兼容性窗口：为什么破坏性变更要分两次发

这是本稿最核心的一条。

**部署不是原子的。** 从"跑完迁移"到"新版本应用全部生效"之间有一个窗口。在这个窗口里：

```
数据库：新 schema
应用：  旧代码（可能还有多个副本在跑）
```

**所以规则是：**

> **任何迁移都必须让"上一个版本的应用代码"继续正常工作。**

推论：**删除或重命名列/表，不能和"停止使用它"放在同一个发布里。**

### 两阶段模式（expand / contract）

以"把 `equipment.location` 改名成 `equipment.storage_location`"为例：

| 发布 | 代码做什么 | 迁移做什么 |
|---|---|---|
| **1（expand）** | 同时读写**两个**列：写时都写，读时优先读新列 | `ADD COLUMN storage_location text` + 把旧列数据回填 |
| **2（contract）** | 只读写新列 | `DROP COLUMN location` |

**中间必须隔一次发布**，因为发布 1 结束时可能还有旧副本在写旧列。

### 各类变更按安全性排序

| 变更 | 安全吗 | 注意 |
|---|---|---|
| `CREATE TABLE` | ✅ 完全安全 | — |
| `ADD COLUMN`（可空，或带默认且 PG 11+） | ✅ 安全 | PG 11 起 `ADD COLUMN ... DEFAULT` 不再重写全表 |
| `ADD CONSTRAINT`（`CHECK` / `UNIQUE`） | ✅ 安全**但**会全表校验 | 数据不干净时会失败，且期间持锁。见 §3.2 |
| `CREATE INDEX` | ⚠️ 会**阻塞写** | 大表必须用 `CONCURRENTLY`，见 §3.1 |
| `ALTER COLUMN TYPE` | ❌ 会重写全表 + 长锁 | 一律走"加新列 + 回填 + 改名"三步 |
| `SET NOT NULL` | ⚠️ 全表扫 | 数据已确认无 NULL 时安全 |
| `DROP COLUMN` / `DROP TABLE` | ❌ **必须等一个发布周期** | 见上面的两阶段 |
| `RENAME COLUMN` | ❌ **等于删除 + 新增** | 旧代码会立刻报错。必须走两阶段 |
| `ALTER ROLE ... SET` | ✅ 安全，立即生效 | 但它影响所有新连接，包括正在跑的旧代码 |

## 3. 三个会真的炸的地方

本系统的量级是**几千行**，所以"大表变更"理论上不是问题。**但下面三条不是关于规模的，是关于"持锁"和"和已定的超时冲突"的。**

### 3.1 `CREATE INDEX CONCURRENTLY` 不能放进事务里

**这是最容易踩、且失败信息最莫名其妙的一条。**

SQLx 的迁移默认**在事务里执行每个迁移文件**。而 `CREATE INDEX CONCURRENTLY` **不能在事务块内运行**：

```
ERROR: CREATE INDEX CONCURRENTLY cannot run inside a transaction block
```

**而且它的失败是"迁移文件整体失败"**，不是"这条语句失败"——因为你没法在一个事务里只回滚这一条。

**两个解法**：

| 解法 | 说明 |
|---|---|
| **每条 `CONCURRENTLY` 索引单独一个迁移文件**，并让该文件不被事务包裹 | SQLx 支持在迁移文件里用 `-- no-transaction` 之类的方式标记（**具体语法待验证**）。推荐 |
| 不用 `CONCURRENTLY` | 几千行加索引是毫秒级，直接 `CREATE INDEX` 不会造成可感知的锁等待 |

**对本系统的实际建议：不要用 `CONCURRENTLY`。** 几千行的表加索引是毫秒级的，而 `CONCURRENTLY` 带来的"必须脱离事务"的复杂度远大于收益。**但要知道它存在**——等到某张表到了几十万行，你会需要它，而那时踩这个坑会很痛。

### 3.2 `ADD CONSTRAINT` 会持有 `ACCESS EXCLUSIVE` 锁做全表校验

`ALTER TABLE ... ADD CONSTRAINT ... CHECK (...)` 需要扫全表来验证**现有数据**。期间它持表级锁，**应用的所有读写都被挡住**。

对几千行是毫秒级，可以接受。但有一个真实的失败模式：

> **如果现有数据违反了新约束，迁移会失败**，而且是**在持锁状态下失败**——期间应用被挡了几十毫秒到几秒。

**所以规则是：加约束前先确认数据干净。** 对 `NOT NULL` 和 `CHECK` 尤其重要：

```sql
-- 不要直接加
ALTER TABLE equipment ADD CONSTRAINT equipment_x_check CHECK (...);   -- 数据不干净就失败

-- 而是先看
SELECT count(*) FROM equipment WHERE NOT (...);   -- 0 再迁移
```

**这是"迁移前自检"的具体形式**——每条新增约束都要配一条验证 SQL，放进迁移文件的注释里。

### 3.3 长时间迁移会撞上 `lock_timeout`（如果角色没分开）

如果违反了 §1.1，用应用角色跑迁移：

```
迁移开始
  → ALTER TABLE 请求 ACCESS EXCLUSIVE
  → 有人在查器材列表，持着 ACCESS SHARE
  → 等锁
  → 5 秒后 lock_timeout 触发
  → ALTER TABLE 失败
  → **如果这是一个多语句的迁移文件，前面已执行的语句已经生效了**
```

**最后一行是真正的问题**：迁移文件的事务性依赖 SQLx 把整个文件包在一个事务里。**如果它确实包了，那失败会整体回滚，是安全的**；如果不包（比如 §3.1 的 `CONCURRENTLY` 场景），就会留下半完成的 schema。

> **⚠️ 待验证**：SQLx 的迁移是否**无条件**把每个迁移文件包在单个事务里（我记得是，且 PostgreSQL 的 DDL 是事务性的所以这可行），以及如何为特定文件关闭它。**这一条要在实现第一步确认**，因为它决定了"迁移失败后现场是什么样"。

## 4. 数据回填：分批，不要一个事务

如果一个迁移需要**改动已有数据**（回填新列、修正历史值），有一个规模阈值之上的做法变化：

| 数据量 | 做法 |
|---|---|
| 几千行 | **一个事务直接 `UPDATE`**。毫秒级，没有理由复杂化 |
| 十万行以上 | 分批：每批 1000–5000 行，**每批一个事务**，可中断可续跑 |

**本系统的量级（几千件器材、十个人）落在第一档**，所以回填就是一个普通 `UPDATE`。

**但要写清一条纪律，因为它将来会变**：

> **回填脚本必须是幂等的、可重复执行的。**

理由：迁移可能因为锁超时或人为中断而失败重跑。如果回填不是幂等的（比如 `UPDATE x SET n = n + 1`），重跑就会算错。

**幂等的写法**：回填的表达应该是"从源头重新算出目标值"，而不是"在目标值上累加"。

```sql
-- ✅ 幂等：重复执行结果相同
UPDATE equipment e SET storage_location = o.location
  FROM equipment_old o WHERE o.id = e.id;

-- ❌ 不幂等
UPDATE equipment SET next_seq = next_seq + 1;
```

**注意最后那条反例正是主稿 3.5 的编号分配语句**——它是**正常运行时代码**的一部分（在事务里，失败会整体回滚），**不是迁移**，所以没问题。但**不要把它抄进迁移里**。

## 5. 回滚：没有"撤销迁移"，只有"向前修"

**决定：不提供 `down` 脚本。** 理由：

| 理由 | 说明 |
|---|---|
| `down` 脚本几乎总是错的 | 它写于变更之前，无法预知变更实际造成的数据状态。`DROP COLUMN` 的 `down` 是"把列加回来"，但**数据回不来** |
| 它会掩盖真正该做的事 | 真正该做的是"写一个把系统带回期望状态的新迁移"，而不是假装上一次没发生 |
| 它给人虚假的安全感 | 有人会以为"有 down 就能随便改" |

**回滚的正确形态是两件不同的事：**

| 场景 | 做法 |
|---|---|
| **代码有问题，schema 是好的** | **回滚应用版本**。这要求 schema 对新旧两个版本都兼容——**这正是 §2 兼容性窗口的作用**。这是唯一真正的"回滚" |
| **schema 有问题** | 写一个**新迁移**把它改对。forward-only |

**所以 §2 那条规则（迁移必须让旧代码继续工作）不只是"部署安全"，它是"回滚能力"的前提。** 没有它，回滚应用版本会让旧代码撞上新 schema。

## 6. 部署流程

```
① 迁移前自检（人/脚本）
   - 每条新约束配的验证 SQL 跑一遍，确认返回 0 行
   - 确认 `lensmax_migrate` 角色存在且不设 lock_timeout

② 跑迁移
   sqlx migrate run --database-url "$MIGRATE_URL"

③ 验证
   - curl /readyz → migrationVersion 是期望值
   - **不就绪就不要继续**

④ 部署新版本应用
   - 滚动/重启，优雅停机 15 秒（运行时篇 R1.10）

⑤ 观察
   - 5xx 计数（运行时篇 R1.8 的告警条件）
   - `23P01` 是否突然出现（那说明预检查出了漏）
   - 未匹配约束的 500（主稿 8.1：没翻译的约束会落 500 并记日志）
```

**第 ① 步是本稿新增的、也是最容易被跳过的一步。** 它的价值在 §3.2：约束在数据不干净时会**持锁失败**，而提前跑一条 `SELECT count(*)` 能让这件事在非持锁状态下被发现。

**第 ⑤ 步里第三条值得单独说**：主稿 8.1 定了"没匹配上的约束一律落 500 但必须记日志"。**所以一次迁移之后应该专门看一眼日志里有没有未匹配的约束名**——新加的约束如果忘了加进 `translate_constraint`，表现就是用户看到 500。

本机无 `cargo`、无 `psql`、无 Docker。以下为推理：

| # | 待验证 | 影响 |
|---|---|---|
| 1 | SQLx 是否**无条件**把每个迁移文件包在单事务里，以及如何为特定文件关闭 | 决定"迁移失败后现场是半完成还是整体回滚"（§3.3）。**实现第一步就要确认** |
