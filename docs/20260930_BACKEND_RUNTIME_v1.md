## R0. 本稿补的是哪些空缺

主设计稿覆盖了数据模型、写路径、文件系统、序列化、错误、认证、部署。以下部分在主稿里**只有一句或者一句都没有**，而它们每一个都能让系统在真实使用中出问题：

| 缺口 | 为什么会出事 | 本稿 |
|---|---|---|
| 可观测性只有「用 tracing」一句 | 出了事没有线索，只能靠用户描述来猜 | R1 |
| 配置散在环境变量里，没有加载与校验策略 | 少一个变量就启动失败在半路；密钥可能进 git | R2 |
| 测试策略只有「Testcontainers 起真 Postgres」一句 | 每个人自己发明测法，最关键的规则没人守 | R3 |
| 并发写只有「锁」，没有字段编辑的语义 | 三个管理员同时改一条记录时，没人知道该发生什么 | R4 |
| CSV 导入的坑全在实现细节里 | Excel 导出的 CSV 是 GBK，第一份真实导入就乱码 | R5 |
| API 没有版本与兼容策略 | 前端和后端一起部署才不出事，而它们不一定一起部署 | R6 |
| 没有故障处理与运维手册 | 磁盘满了、恢复备份、重置密码，每次都是临场发挥 | R7 |

**R5 是本稿里最该先看的一节**——它对应一个必然发生的真实事故（中文乱码），而主稿完全没提。

**R4 的结论是"不处理"**，但这一节仍然重要：它不是空白的，而是明确地把字段编辑排除在并发控制之外，并给出触发重新评估的条件。一个没有被写下来的"不处理"，和"处理了"一样容易在下一次评审里被翻转。

## R1. 可观测性

> **本节是实现面之外的部分**：日志与审计的职责边界、该记什么、轮转与保留、job 日志策略、指标与告警。**字段模式、事件清单、Rust 实现代码和日志测试在 [20260930_LOGGING_v1.md](20260930_LOGGING_v1.md)。** 本届不重复那些内容。

### R1.1 两类日志，先说清关系和边界

这是本系统里最容易做错的一件事：**日志和审计表是两套东西，职责不同，不能互相替代。**

| | 审计（谁改了价格、谁出库了哪件、档期是谁批的） | 日志（为什么这个请求返回 409） |
|---|---|---|
| 存在哪 | 数据库：`equipment_history`、`checkout`、`request`、`field_change` 等 | stdout / 日志文件 |
| 谁看 | 用户、同事、争议仲裁 | 开发者、运维 |
| 保留多久 | 永久（交接稿第 4 节"每一步都留痕，谁也赖不掉"） | 30～90 天 |
| 能改吗 | 只能追加 | 随便丢 |
| 是事实来源吗 | **是** | **不是** |

三条由此推出的纪律：

1. **日志不能作为业务事实的唯一记录。** 任何"以后要查账"的信息必须落库。如果某件事只在日志里，那它会在日志被轮转掉的那天消失。
2. **日志里不要重复业务表的内容。** 出库成功时记 `checkout_id=884` 和件数，不要在日志里铺开每件器材的编号——那是 `checkout_item` 表的事，日志里重复一份只会产生两份会漂移的真相。
3. **日志要能反向指到审计记录。** 出库成功那条日志带 `checkout_id`，用户报"我那天出库的不对"时，你能从日志跳到具体的业务记录。这是两类日志之间唯一需要的连接方式。

### R1.2 格式与上下文

生产 JSON、开发易读，切换由配置决定（`log_format`）。请求入口建一个 `tracing` span：

```
span: http.request
  request_id: 01J8Z…          ← 来自 X-Request-Id，缺失则生成 ULID
  method, path, user_id, role, workspace_id
```

`request_id` 必须回写到响应头，并且和错误体里的 `requestId`（主稿 7.3）是**同一个值**。用户截图给你，你直接捞出那一次请求的全部日志——这是整个日志体系里唯一"用户能帮上忙"的地方，所以它必须可靠。

**span 里放 `user_id` / `role` 而不是每条日志重复一遍。** `tracing` 的 span 会自动附加到其内所有事件上，重复写只是让日志变长。

四条实现约定：

| 约定 | 为什么 |
|---|---|
| **记路由模板，不记实际路径**：记 `PATCH /api/v1/equipment/{id}`，不记 `…/equipment/1284` | 实际路径会让"按端点聚合"变成几千个不同的值，等于不能聚合 |
| **每条请求日志带 `duration_ms`** | 慢请求是"全站变慢"类问题的唯一线索，而它是数字，可排序 |
| **绝不整体记请求体或响应体** | 里面有密码、备注、价格。字段级白名单，不是黑名单 |
| **时间是服务端受理时刻**，不用客户端时间 | 客户端时钟不可信 |

### R1.3 必须能回答的五个问题

日志的价值不取决于记得多，而取决于**能不能回答会真的被问到的问题**。以下五条，每条对应一类会真实发生的事故；实现时逐条对照日志能不能答出来：

| 问题 | 需要哪些字段 |
|---|---|
| **"这个 500 是怎么来的？"** | `request_id`、路由模板、状态码、`error.code`、`error.message`、`duration_ms` |
| **"为什么这件器材出不了库？"** | 业务拒绝的原因（`RESERVED` 要带被哪个项目、哪段时间占用 / `ILLEGAL_TRANSITION` 要带 from→to），不能只记一个 409 |
| **"照片为什么传不上去？"** | 上传流水线**失败在哪一步**（见下表）+ 文件字节数 + 声明的 MIME + 实际魔数 |
| **"这份 CSV 为什么导入失败？"** | 检测到的编码 + 失败行号 + 列名 + 原始值 + 原因，**一行一条**，最多记前 20 行 |
| **"那次部署之后为什么行为变了？"** | 启动日志：版本、git commit、**迁移版本**、配置摘要（密钥脱敏） |

**第二条和第三条是这套日志真正的用处。** "记每次写操作"本身没用——审计表里已经有了。日志的价值在于记下**被拒绝的原因**和**失败的环节**，那些东西不会进业务表。

上传失败要分阶段记录，否则"上传失败"这四个字没法排查：

```
stage: receive | size_limit | magic_bytes | hash | write_tmp | rename
     | decode | exif | thumbnail | encode | persist
```

这十一个值里任何一个出现异常，你立刻知道是网络问题、格式问题、还是磁盘问题。**不记 `stage` 的话，一次上传失败要花半小时去猜。**

### R1.4 级别

| 事件 | 级别 | 说明 |
|---|---|---|
| 业务事实（出库、归还、审批、交付、建档、状态变更） | **INFO** | 一条一次，带业务 ID |
| 启动与配置摘要 | **INFO** | 每个进程一次 |
| 每个 job 的执行结果 | **INFO** | **即使什么都没做也要记**，见 R1.6 |
| 授权拒绝（403） | **WARN** | 十人以内 403 密集出现通常意味着前端 bug |
| 业务拒绝（422 状态流转非法、409 档期冲突） | **INFO** | **不是错误，是业务结果。** 记成 ERROR 会让"错误率"这个信号失效 |
| 排他约束 `23P01` 实际被触发 | **WARN** | 正常路径下不该出现（预检查该先拦住）。出现即说明预检查有漏 |
| 上传失败、导入失败、文件缺失 | **WARN/ERROR** | 见 R1.3 |
| 5xx、占用对账发现偏差、启动时配置校验失败 | **ERROR** | 这三类需要有人看 |

**明确禁止：把 4xx 记成 ERROR。** 用户填错表单会返回 400，那是正常流量。一旦 400 变成 ERROR，你就失去了"哪些错误值得看"的能力——这是日志体系里最常见的一种自毁。

### R1.5 轮转与保留：一个会真的发生的磁盘事故

**这一条在我上一版里完全没写，而它是这套日志唯一会伤到系统的地方。**

日志写到一个固定大小的磁盘上，不轮转就是不限增长。它和主稿 6.5 那条"磁盘满导致照片上传失败"是同一类事故，但更隐蔽：**日志涨得比照片慢，所以它是几个月后才炸，而且炸的时候没人会想到是日志。**

| 项 | 决定 |
|---|---|
| 轮转 | 按天 + 单文件上限（比如 100 MiB） |
| 保留 | 30 天（若走 journald / Docker driver，用它的 `--log-opt max-size` / `max-file`） |
| 实现 | 写到 stdout，轮转交给容器运行时或 journald；**不要自己写文件** |
| 例外 | 只在"必须留文件"时才用 `tracing-appender` 的按天滚动 + 启动时清理超期文件 |

**为什么建议交给容器运行时**：自己写文件意味着你自己要处理轮转、清理、权限、以及"文件被删了但进程还持有句柄"这类问题。`docker compose` 里加两行 `logging.options` 就解决了，而且这些文件的位置和运维习惯一致。

这一条要进 R7.3 的日常维护清单（每周看一眼日志占了多少磁盘）。

### R1.6 job 日志：什么都没做也要记

**每个 job 每次执行必须产出至少一行**，哪怕结果是"处理 0 条"。

理由：如果 job 只在实际做了事的时候才记日志，那么"job 没跑"和"job 跑了但没活干"在日志里**完全一样**。前者是故障，后者是正常——而你会以为一切正常。

```
{ "job": "overdue_scan", "result": "ok", "affected": 3, "duration_ms": 412 }
{ "job": "orphan_cleanup", "result": "ok", "affected": 0, "duration_ms": 88 }
{ "job": "occupancy_reconcile", "result": "failed", "error": "…" }
```

这样"每日 job 没跑"这个告警就退化成一句极简单的检查：**搜今天有没有 `result` 行**。不需要任何指标系统。

### R1.7 绝不记的东西

密码、会话 token、邀请 token 明文（库里本来就只存 hash，日志里也不许出现）、请求体里的 `password` 字段、照片二进制、**内部备注**（可能含客户信息或价格谈判内容）、**搜索词**（器材搜索框里人可能会输入客户名）。

最后两条容易被忽略：它们看起来无害，但都是用户以为"只有我和系统知道"的内容。

**这几条要有测试固定住**，不能靠记性：一个测试用带 `password` 字段的请求打登录接口，断言日志输出里不含该字符串。这类测试写一次管永久。

### R1.8 指标：只留五个

不要一开始就上 Prometheus + Grafana。一个十人以内的工作室没有运维人力看仪表盘。留五个用日志和健康检查就能读到的信号：

| 信号 | 怎么读 | 为什么是它 |
|---|---|---|
| **超期未还件数** | 每日 job 日志 + 总览页本身就查 | 交接稿第 10 节自己点名：逾期是最大的实际损失点 |
| 上传失败率 | 照片上传的成功/失败计数（按 `stage` 分组） | 弱网下最先出问题的就是它，而用户会以为是"系统坏了" |
| 5xx 请求数 | 日志按状态码聚合 | 唯一需要主动告警的东西 |
| 连接池饱和 | `sqlx` 的池指标（等待获取连接的次数） | 池耗尽的表现是"全站变慢"，很难从别处看出来 |
| jobs 执行结果 | 每日一条汇总（R1.6） | 静默失败的任务等于没有任务 |

若要告警，只告警两件事：**5xx 连续出现**、**每日 job 没跑**。其余靠人看。

### R1.9 健康检查要分两个

| 端点 | 查什么 | 用途 |
|---|---|---|
| `GET /healthz` | 进程活着。**不碰数据库** | 容器 liveness。碰库会导致数据库短暂不可用时容器被反复重启，越重启越糟 |
| `GET /readyz` | 数据库可连 + **迁移已应用到最新版本** | 容器 readiness / 负载均衡摘挂 |

`readyz` 查迁移版本这一条很实用：它让"部署了新版本但忘了跑迁移"变成一个立刻可见的状态，而不是等第一个写操作失败（主稿 5.1 那条写路径会在运行中途炸）。

### R1.10 优雅停机

必须有，而且要有 drain 超时。

原因很具体：**主稿 5.1 的写事务可能持续几百毫秒，如果实现里带了重试（批量导入、编号分配），可能到几秒。** 部署时 `SIGTERM` 直接杀进程会中断事务——Postgres 会回滚，不会损坏数据，但用户会看到一个莫名其妙的 500，而且他不知道该不该重试。

做法：收到 `SIGTERM` → 停止接受新连接 → 等待在途请求完成（上限 15 秒）→ 关闭连接池 → 退出。超时未完成的，打一条 WARN 带 `request_id`，方便事后核对用户报的那一次失败。

## R2. 配置与密钥

### R2.1 一个结构体，启动时校验，缺了就退出

```rust
#[derive(Debug, Deserialize)]
pub struct Config {
    pub database_url: String,
    pub data_dir: PathBuf,             // photos/ 与 tmp/ 的父目录
    pub photo_base_url: String,
    pub bind_addr: SocketAddr,
    pub business_tz: Tz,               // 默认 Asia/Shanghai
    pub log_format: LogFormat,         // pretty | json
    pub max_upload_bytes: usize,       // 默认 8 MiB
    pub session_ttl_days: i64,         // 默认 14
    pub pool_max_connections: u32,     // 默认 10
}
```

三条纪律：

1. **启动时一次性加载并校验**，不是用到时再读。缺 `DATABASE_URL` 应该在启动的第一秒失败，不是第一个请求失败。
2. **失败信息写清是哪个变量、期望什么**，例如 `DATABASE_URL 未设置（期望 postgres://…）`。
3. **`data_dir` 启动时要验证**：存在、可写、且 `photos/` 与 `tmp/` 在**同一文件系统**上。最后一条是主稿 6.3 那个原子 rename 的前提——跨文件系统 rename 会失败（`EXDEV`），而且是在第一个用户上传时才失败。

### R2.2 密钥

只从环境变量来。`.env` 仅用于本地开发且必须进 `.gitignore`。生产用 docker secrets / systemd credentials，不要写进 compose 文件。

**`PHOTO_BASE_URL` 有一个不明显的后果**：照片 URL 是内容寻址、被浏览器和 Caddy 永久缓存（主稿 6.6）。改这个变量**不会让旧 URL 失效**——客户端仍会拿着旧域名的 URL。所以它是一次性的决定：若要换域名，要么保留旧域名的重定向，要么接受一次全量缓存失效。写进运维手册（R7.2）。

### R2.3 时区与"今天"

这一条很容易埋雷。规则：

- **审计时间是 `timestamptz`**，存瞬时，与业务时区无关。
- **业务日期是 `DATE`**，是日历日，没有时区。
- **"今天"必须取业务时区的今天**，不是服务器 UTC 的今天。

第三点是关键：`expected_date < today` 这个逾期判断，如果 `today` 取的是 UTC 日期，那么东八区每天 08:00 之前的判断都会**少算一天**——一个已经超期的器材不会被标红。这是那种"看起来只是差几小时"、实际会让用户不信任系统的 bug。

实现上收敛到一个函数：`business_today(cfg) -> Date`，所有地方都调它，不允许出现 `OffsetDateTime::now_utc().date()`。加一条 grep 级的 CI 检查或者 code review 约定。

## R3. 测试策略

### R3.1 分层

| 层 | 范围 | 依赖 | 跑多久 |
|---|---|---|---|
| 单元 | `domain`：状态机、区间计算、可见性集合、编号格式 | 无 | 毫秒级，几百个 |
| 集成 | `db` + `services`：真实 Postgres | 真库 | 秒级 |
| API | 通过 Axum router 打真实请求 | 真库 | 秒级 |
| 契约 | 序列化后的 JSON 形状 | 真库 | 秒级 |

**不 mock 数据库。** 本系统的正确性大量依赖真实 SQL 行为：排他约束、部分唯一索引、`CHECK` 约束、`timestamptz`、`daterange` 与 `infinity`。mock 掉数据库等于把最需要验证的东西验证掉了。

真库的获取：`sqlx::test` 宏（每个测试一个隔离的库）或 Testcontainers。单个测试用事务包裹、结束时回滚会更快，但**会掩盖并发测试**——并发测试必须能用两个连接，所以那几条要单独跑、不包事务。

### R3.2 必须存在的测试，按优先级

| # | 测什么 | 为什么它排前面 |
|---|---|---|
| 1 | **并发互斥**：两个并发任务给同一件器材建重叠占用，断言恰好一个成功、另一个得到 `DomainError::Reserved` 而不是 500 | 这是主稿第 3 节那套设计存在的唯一证据。没有它，`occupancy` 只是个看起来聪明的表 |
| 2 | **`infinity` 语义**：`expected_date = NULL` 的出库占用，阻断该器材此后任何预约 | 主稿 3.1 那张表的最后一行，最容易实现错 |
| 3 | **可见性契约快照**：用申请人身份打每一个读接口，断言 JSON key 集合 ⊆ 白名单 | 交接稿第 3 节的规则靠它守。加字段时它会红 |
| 4 | **状态机全表**：五态两两组合，断言合法的通过、非法的给 `IllegalTransition` | 交界稿第 4 节那张表，机械但必须全覆盖 |
| 5 | **批量的原子性**：批量里混一件出库中的，断言整批回滚且错误里点名了那一件 | 交接稿第 4 节"不做部分成功" |
| 6 | **SQLSTATE 翻译**：手工构造一次 `23P01` 和一次 `23505`，断言翻译成领域错误而非 500 | 主稿第 8 节那套翻译是并发安全的最后一道 |
| 7 | **权限与角色**：申请人访问全库历史 → 403；改主理人权限 → `OwnerImmutable` | 交接稿第 2 节 |
| 8 | **编号并发**：并发建档，断言编号不重复且计数器不跳号 | 主稿 3.5 |
| 9 | **`skip_serializing_if` 不用于权限**（元测试）：断言被禁字段的 key 根本不存在，而不是 `null` | 防止后来者"顺手"用 `Option` 表达禁止 |
| 10 | **日志不含密钥**：见 R1.1 | 一次写对，永久有效 |
| 11 | **并发编辑后写覆盖**：甲改名称、乙改价格（并发提交），断言两者都保住；再并发改**同一**字段，断言后提交者胜出且两条 `UPDATE` 历史都在 | 这是主稿 5.5"不设锁"这个决定的证据。没有它，那个决定就只是没做，而不是有意识地不做 |
| 12 | **历史只记真正变了的字段**：提交一份与当前值完全相同的表单，断言**不产生** `UPDATE` 历史 | 见 R4.2。做漏了这一条，历史列表会被"名称从 X 改成 X"灌满 |

第 9 条值得解释：它不是测功能，是测**约定没有被破坏**。这类测试是文档无法替代的——文档会被跳过，测试不会。

第 11 条是这份文档里唯一一条"证明某个机制**不**存在"的测试。它同时锁住两件事：不设锁的结论，以及将来有人加锁时会被它拦下来（加锁会让"两者都保住"失败），从而必须有人明确地推翻这个决定，而不是悄悄改掉。

### R3.3 测试数据

准备一个 `fixtures` 模块，提供五个场景：空库、单件在库、单件出库中（含 `NULL` 预计归还）、有已批准申请占着档期、以及一件维修中。**大部分集成测试都从这五个之一开始**，避免每个测试自己造一堆数据、也避免数据不一致导致测试之间互相污染。

## R4. 并发控制

主稿第 5 节讲了"同一件器材不能被两个流程同时改状态"，靠锁和约束。本节定的是**字段编辑**的并发语义——两个管理员同时编辑同一件器材的描述性字段。

**结论：不设编辑锁，不做在线状态，不做协同合并。后写覆盖，变更写进历史留痕。** 完整的论证和"将来要加时的顺序"在主稿 5.5，本节只记工程约束和运维侧的后果。

### R4.1 三类并发必须分清

实现时最容易出错的地方是把这三种混为一谈，它们各自的处理方式完全不同：

| 类型 | 处理 | 实现位置 |
|---|---|---|
| **状态流转竞争**（两人同时点「确认出库」） | 行锁 `SELECT ... FOR UPDATE` | 主稿 5.1 第 1 步 |
| **档期占用竞争**（两人要同一件器材的同一段时间） | 排他约束 | 主稿第 3 节 |
| **字段编辑冲突**（两人改同一件器材的字段） | **不处理**，后写覆盖 + 留痕 | 主稿 5.5 |

前两类是正确性机制，**不许因为"第三类不用处理"而顺手削弱它们**。检查时看三条：`lock_many` 在不在、排他约束在不在、批量取锁顺序是不是按 `equipment.id` 升序。

### R4.2 留痕的工程约束

字段变更写进 `equipment_history` 的 `UPDATE` 动作，`detail.changed` 是数组（主稿 5.5）。

两条实现约束：

- **一次提交写一条历史，不是每个字段一条。** 一个表单改了五个字段，应该是 1 条历史带 5 个元素的 `changed` 数组。按字段拆会把历史列表冲垮。
- **只记真正变了的字段。** 表单提交是整份快照，客户端会把没改的字段也发上来；服务端必须与当前值对比，只把差异写进 `changed`。不对比的话，每次保存都会产生一条"名称从 Sony FX3 改成 Sony FX3"的记录。

第二条如果做漏了，历史列表会迅速变成噪音——而那是这个机制唯一的产出，等于白做。

### R4.3 事务隔离级别

用默认的 `READ COMMITTED`，**不要**设成 `SERIALIZABLE`。

理由：所有"不能被并发破坏"的东西都已经由显式机制保证——排他约束（档期）、部分唯一索引（主理人唯一、一条未关闭维修）、行锁（状态流转、编号分配）。在这些之上再要求 `SERIALIZABLE`，收益为零，代价是引入序列化失败错误和配套的重试逻辑——**一段为了修不存在的问题而引入的、自己会出错的代码**。

### R4.4 幂等

弱网下的重试有两个真实场景：用户连点两次「确认出库」；客户端超时后自动重试。

第一种靠前端禁用按钮（交接稿第 7 节已有"提交中禁用并转圈"）。第二种需要后端配合：**对创建型接口接受一个可选的 `Idempotency-Key` 头，同 key 的重复请求返回第一次的结果。**

不要一开始就给所有接口加。**只加在三个地方**：出库、照片上传、CSV 导入提交。这三个都是"重试会造成实际损害或重复数据"的操作，其余接口重试一次最多是返回一次业务错误。

照片上传本来就已经幂等（内容寻址，主稿 6.2），所以实际上只有出库和导入两处需要这个头。

### R4.5 运维侧的后果

既然不做编辑锁，就没有"过期占据"要清理，也没有 TTL 要调。**运维手册里不需要这一项**（这一点曾经在两版设计里需要，见 R8 的记录）。

但要留一个观察口径：如果出现"我改的东西不见了"的报告，正确的处理是**查 `equipment_history` 的 `UPDATE` 记录**，看那个字段在什么时间被谁改成了什么。这条排查路径要写进运维手册——没有它，这类报告无法定性，而它恰好是决定"要不要加字段级冲突检测"的唯一依据（主稿 5.5）。

## R5. 批量导入的工程细节

主稿 5.3 定了"全有或全无"，但 CSV 导入的真实麻烦在编码、金额解析、以及"预览期间数据变了"这三件事上。

### R5.1 编码：中文 Windows 的 Excel 会给你 GBK

**这是第一份真实导入文件最可能踩的坑。** 中文 Windows 上 Excel 另存为 CSV，默认是 GBK（代码页 936），不是 UTF-8。直接按 UTF-8 读会得到乱码器材名，而且**不会报错**——导入"成功"了，只是所有中文都是问号。

处理顺序（`encoding_rs`）：

1. 有 UTF-8 BOM（`EF BB BF`）→ 按 UTF-8 读，**并且把 BOM 从首行表头里剥掉**（否则第一列列名会变成 `\u{FEFF}器材编号`，列匹配失败）。
2. 无 BOM → 先试严格 UTF-8。
3. 严格 UTF-8 失败 → 按 GBK 读。

**并把实际检测到的编码回显在预览界面**（"检测到编码：GBK"）。不是为了炫技，是为了让用户在预览里就能发现乱码，而不是导入完才发现。这一条是 R5 里性价比最高的实现。

### R5.2 金额和日期

`购买价格` 一列在人手填的 Excel 里会长成各种样子：`1280`、`1280.00`、`¥1,280.00`、`1280元`、`1,280`。统一在导入时规范化成**整数分**（主稿 7.2：金额不碰浮点）：

- 去掉货币符号和千分位分隔符
- 按小数处理成整数分，**四舍五入而不是截断**
- 解析失败 → 该行标红，**不静默当 0**。把 1280 静默存成 0 比导入失败严重得多

日期同理：接受 `2024-03-01` 和 `2024/3/1` 两种常见格式，其余标红。

`器材编号` 一列如果留空 → 走主稿 3.5 的自动生成。

### R5.3 预览期间数据变了怎么办

主稿 5.1 的流程是"先预览（前 12 行）、确认、提交"。用户在看着预览的这几分钟里，别处可能已经出库了某件器材、或建了同编号的器材。

两个选项：

| 方案 | 做法 | 取舍 |
|---|---|---|
| **重校验**（建议） | 提交时重新跑一遍校验；若与预览结果不一致，拒绝并让用户重新预览 | 安全，用户在长预览后会遇到一次"请重新确认" |
| 快照 | 把解析结果存到服务端，提交时按快照执行 | 用户不会被打断，但可能导入一份过时的判断 |

**建议重校验。** 导入是低频、批量、易错的操作；被打断一次的代价远小于导入一批与现状冲突的数据。而且实现上重校验就是"把预览那一步的校验函数再调一次"，不增加代码。

### R5.4 资源上限

除了主稿 5.1 的 1000 行上限，还要有：

- **请求体上限**（5 MiB 左右）：否则一个 500 MB 的 CSV 会在解析前就把内存吃掉。这个限制要在**读流的时候**生效，不是解析完再检查。
- **单字段长度上限**：一行里塞一个 1 MB 的备注不该拖垮解析。
- **批量插入分块**：不要一行一次 INSERT，也不要一次拼 1000 行的巨型语句。500 行一批。
- **一次性预取**：导入开始时把已有分类名、已有编号全部读进内存（1000 行的规模下这很便宜），导入中不再逐行查库——否则 1000 行会变成几千次往返。

## R6. API 治理

### R6.1 版本

路径带版本：`/api/v1/...`。

主稿没写这一条，理由是"只有一个客户端"。但**成本是零，收益是"当你要破坏兼容时不用改前端的同时还要改部署顺序"**。单工作室系统里前后端通常一起发，但"通常"不是"总是"——一次热修复、一次回滚，就可能出现旧前端配新后端。

### R6.2 兼容性规则

三条，够用：

1. **加可选字段**：安全。
2. **改字段语义**（比如把秒改成毫秒、把分改成元）：**禁止**。要改就加新字段，旧的标废弃。
3. **删除或重命名字段**：需要新的 `/v2`，且旧版本至少保留一个发布周期。

### R6.3 契约漂移的自动检查

主稿第 7 节说了用 utoipa 生成 OpenAPI 再生成前端类型。要补的是**CI 检查**：

```
cargo run -p xtask -- gen-api      # 产出 openapi.json + schema.d.ts
git diff --exit-code               # 有差异就红
```

没有这一条，生成出来的类型会慢慢和实际实现分家，而分家是静默的——前端编译通过、运行时字段对不上。**这条检查是主稿 D8（服务端下发 `actions`）能成立的前提**：如果类型和实现对不上，`actions` 数组的枚举值哪天变了前端也不会知道。

## R7. 故障与运维

### R7.1 会真的发生的故障，以及那时的行为

| 故障 | 系统的行为 | 用户看到 | 你要做的 |
|---|---|---|---|
| 数据库不可用 | 所有请求 503（不是 500，这样前端能区分"稍后重试"和"出错了"） | "服务暂时不可用" | 重启数据库；`readyz` 已经把它摘出负载 |
| **磁盘满** | 照片写失败、数据库仍可写 | 出库归还正常，**只有上传照片失败** | 这是最隐蔽的一种：主流程看着正常。所以上传失败要告警，日志（含 `stage` 和剩余空间）要能指出是磁盘问题 |
| **日志把磁盘写满** | 与上一条同样的表现，但**慢几个月才发生** | 同上 | 见 R1.5：轮转 + 保留交给容器运行时 |
| `photos/` 里的文件丢了（误删、只恢复了库没恢复文件） | 数据库正常，图片 404 | 器材列表出现破图 | 见 R7.2 的一致性检查 |
| `jobs` 静默死了 | 无人察觉 | 逾期提示不再更新 | 搜当天有没有 job 的 `result` 行（R1.6） |
| 连接池耗尽 | 全站变慢，最终超时 | "很慢"或超时 | 加池大小、查长事务；日志里的等待次数能看出趋势 |

**磁盘满那一条值得单独说**：它不会让系统"坏掉"，只会让一个功能坏掉，而那个功能的失败信息是"上传失败"——用户会以为是照片格式问题。日志里带上磁盘剩余空间，能让这件事从"玄学"变成"一眼看出"。**日志写满磁盘是同一类事故的另一种来源，而且它慢到没人会怀疑它**（R1.5）。

### R7.2 文件与数据库的一致性

备份要一致（主稿 11.2：先文件后库），但恢复之后仍需验证。加一个每日轻量检查：

- 从 `photo` 表按 `uploaded_at` 取最近 N 条（比如 50 条），逐个 `stat` 文件是否存在。
- 缺文件 → ERROR 日志 + 告警，附缺失的 `rel_path`。

抽样而非全扫：**恢复事故的特征是"一批文件整体不见了"，不是"某一个文件不见了"**，所以抽查最近记录就足以发现。全扫留给每周的孤儿清理任务（主稿 6.5）。

反向（文件在、库里没有）是安全的，孤儿清理会处理，不需要检查。

### R7.3 日常维护清单

| 频率 | 做什么 |
|---|---|
| 每日 | 搜当天有没有各 job 的 `result` 行（R1.6）；确认备份产物存在且大小正常 |
| 每周 | 看孤儿清理删了多少（突然变多说明有 bug）；看 `23P01` 告警有没有出现过（出现过就是预检查有漏）；**看一眼日志占了多少磁盘**（R1.5） |
| 每月 | 演练一次恢复：拉最新备份到临时环境，起服务，打开一件器材看照片在不在 |
| 按需 | 轮换会话密钥、清理过期邀请 |

**恢复演练是这里面唯一不能省的一项。** 主稿 11.2 说了"只备份不演练等于没备份"，本稿把它落到具体动作：恢复 + 起服务 + **看一眼照片**（这一步会同时验证 R7.2 那条一致性问题）。

### R7.4 需要写进运维手册的操作

这些操作在系统生命周期里一定会被做，而且**在没有文档的情况下一定会做错**：

1. **恢复备份**：顺序（先文件后库）、如何验证、恢复后要跑哪些检查。
2. **重置某人的密码 / 停用账号**：停用账号必须同时删除其会话（主稿第 9 节）——只改 `disabled_at` 不会让已登录的会话失效，用户会以为"停用没生效"。
3. **主理人交接**：目前无设计（主稿 13.7）。**在它被设计之前，这个操作是不存在的**，手册里要明确写"当前不支持"，否则有人会直接改数据库，而 `app_user_one_owner` 唯一索引会让那个改动失败在一半。
4. **轮换 `PHOTO_BASE_URL`**：见 R2.2 的后果。
5. **加一个管理员**：走邀请还是直接建号；邀请链接的有效期。

### R7.5 上线前的验收清单

实现完成、上线之前必须逐条过一遍。每一条都对应上面某一节的机制：

- [ ] `readyz` 在迁移未应用时返回不健康
- [ ] 优雅停机：部署过程中有在途请求，无 500
- [ ] 并发互斥测试通过（R3.2 #1）
- [ ] 可见性契约测试通过，且**故意加一个字段会失败**（证明它真的在工作，而不是恒真）
- [ ] 手工触发一次 `23P01`，确认返回 409 + 中文人话，不是 500
- [ ] 手动灌满磁盘（或把 `data_dir` 指向只读目录），确认只有上传失败、主流程正常、日志有剩余空间
- [ ] 用一份 GBK 编码、带 `¥1,280.00` 的 CSV 走一遍导入
- [ ] 两个浏览器同时改同一件器材的**不同**字段，确认两者都保住（R3.2 #11）
- [ ] 随便改一个字段再改回原值，确认历史里**没有**多余的 `UPDATE` 记录（R3.2 #12）
- [ ] 恢复一次备份，确认照片能打开
- [ ] 日志里搜不到密码和 token
- [ ] **故意上传一个非 JPEG 文件**，确认日志里有 `stage` 字段并指出失败环节（R1.3）
- [ ] 用一份有坏行的 CSV 导入，确认日志里能读到行号、列名和原始值（R1.3）
- [ ] **停掉一个 job 不跑**，确认"当天没有该 job 的 `result` 行"这件事是可判断的（R1.6）
- [ ] 确认日志轮转生效：连打 200 MiB 日志，检查是否被切分且总量有上限（R1.5）
- [ ] 启动日志里能看到版本、commit 和**迁移版本**（R1.3 第五条）

### R8.1 一个被反复设计的决定的记录

R4 这一节在本稿的评审过程中改写过两次，记录在这里，目的是**避免同一个决定被重新讨论第四遍**：

|---|---|---|
| 第一版 | 行级乐观并发（`version` + `If-Match` + 409） | 太粗暴：甲改名称、乙改价格也会互相挡。而且它假设"冲突罕见所以让人重来可以接受" |
| 第二版 | 硬闸门：别人正在编辑就不允许打开修改界面 | 把可用性换成了可靠性，而且引入 TTL、续期、接管、崩溃残留一整套问题。参照物是 Google Docs——**它从不阻止任何人编辑**，靠的是可见性 + 合并 + 版本历史 |
| 第三版 | 在线状态（显示谁在改）+ 字段级冲突检测 | 在十人以内、实际 2～3 人编辑同一记录的规模下，收益低于它引入的两张表和心跳机制 |

**最终结论：三者都不做，后写覆盖 + `UPDATE` 留痕。** 触发重新评估的条件写在主稿 5.5 的"如果将来要加"，以及 R4.5 的排查口径（出现"我改的东西不见了"的报告，先查历史再决定）。

这个记录本身是有价值的：**它说明这个决定是基于使用规模做的，而不是"没想到"。** 没有这段记录，下一个接手的人看到"编辑不加锁"会以为是遗漏。
