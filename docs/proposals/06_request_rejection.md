## 1. 缺口描述

### 1.1 待回答的核心问题

器材申请流程（申请人提交 → 管理员审批 → 办理交付 → 逐件归还）里，「部分通过」的实现方式是**管理员在卡片上逐件取消勾选**（主稿 3.1 第 131 行：「批准时取消勾选某件（= 拒绝）→ 不 INSERT。**这就是"部分通过"的实现方式**」）。这条机制只决定了 `occupancy` 不插行，**没有决定申请人能看到什么**。

于是核心问题是：

> **申请人看到自己被拒时，能看到原因吗？**

如果看不到，「申请」这个流程的体验会明显残缺——申请人只知道「我要的 FX3 没批」，不知道为什么、接下来该换什么，唯一出路是跑去问管理员。而这个答案决定 `request_item` 要不要 `reject_reason` 列。

同时注意一个**与占用相关的实际后果**：`occupancy.source_request_id bigint REFERENCES request(id)`（主稿第 112 行）**没有 `ON DELETE CASCADE`**（主稿里只有 `app_user_session`、`request_item`、`checkout_item` 三处带 CASCADE，见第 200 / 327 / 358 行）。所以「撤回」如果按第 134 行字面理解成"删申请单"，外键会直接拦住，必须先删 `occupancy` 行——**顺序反了就是一次 500**（并撞上运行时篇 R7.1「数据库不可用 → 503」那套错误语义里最不该出现的一种：一个用户可预期的业务动作返回了内部错误）。（这一点在第 5 问里展开。）

#### ⑤ 主稿没有说「全单被拒」怎么操作 —— 确认

主稿 3.1 那张映射表里的两个事件是：

| 业务事件 | 对 `occupancy` 的操作 |
|---|---|
| 管理员批准某件器材 | INSERT |
| **批准时取消勾选某件（= 拒绝）** | 不 INSERT。这就是"部分通过"的实现方式 |

**它的主键是 `(request_id, equipment_id)` 唯一约束下的逐件动作**，没有任何一处描述「全部取消勾选」和「一键拒绝整单」的区别，也没有说两者是否产生同一种状态。`grep` `全单|整单|一键拒绝|全部取消|拒绝按钮` **零命中**。

这个缺口的性质是**语义上的**，不只是界面上的：在「取消勾选 = 拒绝」这个操作模型里，**"管理员一件都没勾"和"管理员还没审"在 `request_item` 上没有区分手段**。具体地：

- 若「提交审批」把所有未勾选的件写成 `approved = false`（这是最自然的实现），那么"一件都没勾然后提交"和"还没审"就**都会表现为全部行 `approved = false`**，服务端再也分不出 `REJECTED` 和 `PENDING`；
- 若「提交审批」只写被勾选/明确点掉的件、其余留 `NULL`（即 `NULL` 兼作"未审"与"未勾"），那么"全单拒绝"就**根本落不到 `REJECTED`**——因为没有任何一行的 `approved` 变成 `false`；
- 两条路都指向同一个结论：**需要一个独立的判别位来表示"这次审批提交了"**。`request.reviewed_by` / `reviewed_at`（第 319–320 行）是现成的载体，但主稿**没有说它们在哪个时点被写**。

顺带澄清一个与本问相邻、但主稿同样没写的规则：`UNIQUE (request_id, equipment_id)` 只保证"同一件器材不重复"，**它并不保证一张申请单至少有一件器材**（子表没有行时唯一约束无从生效）。若 `status` 要靠逐件结果推导，就必须先有一条"申请单至少一件"的前置规则——`grep` 全库 `至少一件|空申请|无器材` **零命中**，主稿没有这条。

#### ⑥ 被拒之后能做什么没有定义 —— 确认

`grep` 没有任何关于"重新提交"、"改申请"、"再申请一次"的描述。主稿 7.6 的 PATCH 语义（`Option<Option<T>>`）只针对器材字段编辑（第 824–837 行）。

两个已存在的数据约束会约束答案：

- `UNIQUE (request_id, equipment_id)`：同一张申请单里同一件器材不能出现两次。所以"把被拒的那件再要一次"**不能**在同一张单里做（会被 23505 拦住，而它会走到运行时篇 RUST_IMPL 第 333–337 行那套 `23505` 翻译里，落到一个与"重复编号"同级的错误上——那句话对申请人毫无意义）；
- `request.project_id` 是 `NULL` 且主稿第 311 行注明是"提交时的自由文本，**批准/交付时关联 project**"——即 `project_id` 的回填是审批/交付流程的一部分，但**谁在哪一步回填、找不到匹配 project 时怎么办，主稿没有写**。这条和第 1 问的理由字段是同一个界面的两个输入框，值得一起定。

#### ⑦ 一条顺带的观察：`request` 的状态变更不进任何审计主线

主稿第 10.1 节定了「`equipment_history` 是唯一的叙事主线」，而 `equipment_history.action` 的 `CHECK`（第 389–391 行）是封闭集合，**里面没有申请相关的动作**。所以申请单的「谁在什么时候批了/拒了/撤回了」目前只能：
- 落在 `request.reviewed_by` + `reviewed_at` 两个字段上（只有最后一次），
- 或者只在日志里（日志稿 `biz.approve`）。

而运行时篇 R1.1 的硬规则是「**任何"以后要查账"的信息必须落库。只在日志里的事，会在日志被轮转掉的那天消失。**」——日志稿第 9.5 节的保留窗口是 `max-size × max-file`（约 500 MB，实际约 100 天）。「半年前这单是谁拒的、当时写了什么理由」这个问题在本设计下**答不出来**。这不是第 1 问问的，但它是第 3 问「加在 `request_item` 上还是新建表」时必须一起想的事。

## 2. 逐问的选项表

每条都标为**待产品拍板**。推荐是推荐，不是结论。

### 第 1 问：申请人能不能看到「这件为什么没批」？

| 选项 | 实现成本 | 体验影响 | 建议 |
|---|---|---|---|
| **(a) 完全不告诉**，只有状态变化 | **最低。** DDL 零改动。仍需新增申请单视图（缺口 ③），且视图里不放 `approved` 明细——但"不放"是个决定，要用测试钉住，否则将来顺手带上 | 申请人看到「未通过」，不知道哪几件、为什么。他唯一的出路是问管理员。**对"整单被拒"勉强可接受**（还能靠 `review_note` 一句）；**对"部分通过"不可接受**——界面上会出现"申请已通过"却拿不到他真正想要的那件，而且他看不出来是哪件没批 | 不推荐。**"部分通过"这个机制的产品价值，恰恰建立在申请人知道哪件没批之上**；连哪件都没告诉他，这个机制对申请人是不可见的，等于只服务于管理员 |
| **(b) 能看到哪些件被拒，但没有理由** | 中。DDL 零改动（`approved = false` 就是答案）。**但必须新增**：申请单视图（含逐件 `approved`）、申请人专用的申请单契约测试、以及申请单的 `actions` key 词表（缺口 ④） | 申请人知道"是 CAM-003 没批"，但不知道"因为 10-01～10-05 被《宣传片A》占住了，建议换 CAM-005"。他仍要去问。**对"档期冲突"这一类原因，缺理由的损失最大**——这类拒绝本身是可解释、可自助解决的 | 可作为**最小可上线版本**。若产品要的是"先跑起来"，选它、并且明确记下"逐件理由留到二期" |
| **(c) 能看到哪些件被拒 + 管理员填的逐件理由** | 中高。**需要加列**（第 3 问的 DDL）、必填性策略（见下）、审批界面加逐件理由输入框、申请单视图加该字段、契约测试。若还要"替代器材"则进一步提高（第 2 问） | 申请人能自助决定"换一件"还是"换日期"。这是我推荐的形态，但**它的成本不在数据库，而在审批界面的录入摩擦**——见下方警告 | **推荐 (c)**，理由：`approved = false` 这个字段存在的意义就是让申请人看到，而**只给结论不给原因是把解释成本推给了人**（管理员会被反复问同一句话）。但采纳前请先读下面的"录入摩擦" |

> **采纳 (c) 之前必须接受的代价（这一条比 DDL 重要）。**
> 逐件理由要在**审批当时**由管理员手打。十件器材被拒八件，就是八次输入。**如果界面不强迫、不提供快捷语，这个字段会在两周内退化成空格或"无"**，而那时它的成本（一列 + 一个界面 + 一条契约测试）已经付掉了、收益是零。
>
> 三个缓解手段，成本从低到高，产品可任选：
> 1. **允许留空**（DDL 不加 `NOT NULL`），并把「留空」在申请人界面上显示成"未填写原因"而不是空白（诚实但难看，好处是它把管理员的偷懒暴露出来）；
> 2. **给快捷原因**：审批界面上放几个可选原因（「档期已占用」/「该器材维修中」/「不外借」/「其他」），点一下填进去，管理员仍可改写。这是**纯前端 + 一个枚举常量**的成本，不需要新表；
> 3. **只在「部分通过」时必填**，全单拒绝时用全单级的 `review_note` 兜（见第 2 问）。
>
> 我倾向 **2 + 1 组合**：给快捷语降低摩擦，同时允许留空以免把审批卡死。这也是为什么下面的 DDL 里 `reject_reason` **不加 `NOT NULL`**。

### 第 2 问：`review_note` 够不够？需要结构化的「替代器材」吗？

先看 `review_note` 现在的形状：`review_note text`（主稿第 318 行），整单一段自由文本，与 `reviewed_by` / `reviewed_at` 同级。

管理员那句真实的话——「AM-002 没批是因为已经被《宣传片A》占住了，建议换 AM-005」——拆开是**四段信息**：被拒的件（AM-002）、原因（被《宣传片A》占档期）、**可执行的建议**（换 AM-005）、以及那件替代品是否真的可用。

| 选项 | 实现成本 | 体验影响 | 建议 |
|---|---|---|---|
| **(a) 只有整单 `review_note`** | 零。DDL 不动 | 一句话只能说清一件器材。被拒三件时管理员要么写三段（申请人分不清哪段对应哪件），要么只写最要紧的那件（另两件没解释）。**而且这句是整单级的，后来者无法审计"当时那件为什么没批"**：下一轮审批改了 `review_note`，上一轮的理由就没了 | 不推荐作为唯一载体。**但它是全单拒绝时最自然的载体**（见下） |
| **(b) 逐件自由文本理由**（= 第 1 问的 (c)） | 一列 + 界面 + 契约测试 | 管理员能一句话说清「已被《宣传片A》占住，建议换 AM-005」——**"建议换什么"放进自由文本是够用的**，因为申请人读到的是一个句子，不是要拿它去 join 什么 | **推荐。这是本问的答案：自由文本够了**，不必为"替代器材"单独建字段 |
| **(c) 结构化「替代器材」字段**（如 `request_item.alternate_equipment_id bigint REFERENCES equipment(id)`） | 一列 + 外键 + **一个"这件替代品当前是否可用"的读模型**（否则推荐一件同样被占住的器材，比不推荐更糟）+ 申请人界面上的可点击跳转 | 表面体验最好，实际引入了新问题：**替代品本身也可能冲突**，而主稿第 3 节那套 `occupancy` 是"谁占着谁说了算"，审批界面上若不做实时冲突检查，这个字段就是个会骗人的字段 | **不推荐在 v1 做。** 若要做，建议顺序是：先有 (b) 的自由文本 → 观察管理员是否反复在文本里写器材编号 → 是，再加结构化字段。**这个触发条件不成立就不要加** |

**结论（待拍板）：** `review_note` 单独用不够（它只能表达一件事，且会随下一次审批被覆盖）；**逐件自由文本够用，不需要结构化的替代器材字段**。`review_note` 保留，定位改为**整单级补充**（全单拒绝的理由、或对整单的说明），不与逐件理由重复。

### 第 3 问：如果加逐件理由，加在 `request_item` 上还是新建表？

| 选项 | 实现成本 | 体验影响 | 建议 |
|---|---|---|---|
| **(a) `request_item` 加一列** | 最低。一个 `ALTER TABLE ... ADD COLUMN`。**结构性理由更强**：`approved = false` 这件事**只存在于 `request_item` 上**，理由与它的主体同表就不会出现"有 `approved=false` 却没有理由行"或反之 | 无差异 | **推荐** |
| (b) 新建 `request_item_review` 表 | 高。新表 + 外键 + 唯一约束（`UNIQUE (request_id, equipment_id)`）+ 两处 join + 一条"那张表存在行但这条没被拒"的对账规则（主稿第 1056 行的占用对账已经够多了，不必再加一条） | 无差异。**它唯一能多给的是"每一轮审批的完整历史"**——但那是缺口 ⑦ 的问题（`review_note` 被覆盖），用一个字段解决它更便宜 | 不推荐。**除非产品要"保留每一次审批的完整快照"**（多次审批、理由要留档），那才值得建表 |
| (c) 理由进 `equipment_history.detail` | 低（复用 JSONB） | **不推荐**：`equipment_history` 是针对**器材**的（外键指向 `equipment(id)`，且不可级联删，主稿第 413 行），一件器材在两张申请单里被拒是两条不同的记录，混进器材历史会污染"这件器材发生过什么"这条主线（主稿 10.1）。而且运行时篇 R4.2 定的 `changed` 数组语义是"字段变更"，硬塞审批理由会让那个结构有两种含义 | 不推荐 |

**与 `occupancy` 插入逻辑的关系（重要，这里要澄清一个容易混的点）：**

> **拒绝 = 不 INSERT `occupancy`。所以逐件理由和占用完全无关，是纯记录。**
> 加 `reject_reason` **不会**触碰主稿 3.1 的排他约束、`occupancy_no_overlap`、也不影响主稿 11 节那条占用对账（对账的规则是"每条 `RESERVATION` 应有一条 `approved = true` 的 `request_item`"，拒绝件本来就不该有 `RESERVATION`，加一列不改变这个谓词）。
>
> 唯一的间接影响：如果采纳 (c) 里"替代器材需要实时冲突检查"那条，它会**读** `occupancy`；但这是读，不是写。

**理由会不会被后续操作清掉？** 建议加一条硬规则（不是 DDL，是服务层 + 测试）：**`approved` 一旦不是 `NULL`，审批不可重复提交**。否则同一个管理员第二次提交审批会把第一次的逐件理由覆盖掉——这正是缺口 ⑦ 说的"理由只在 `review_note` 里会被覆盖"的同一个毛病，只是换到了行级。

### 第 4 问：「未通过」和「部分通过」是怎么产生的？操作一样吗？

**主稿在这里是含糊的，而且含糊的具体位置可以指名。**

主稿 3.1 那张表（第 128–137 行）列的是**对 `occupancy` 的操作**，不是**界面上的操作**。它说「批准时取消勾选某件（= 拒绝）」——这句话描述的是**逐件的勾选状态**，它**没有**说：

1. 审批界面上除了卡片上的一排勾选框，有没有一个独立的「拒绝整单」按钮；
2. 如果有，它和"把所有勾选框都取消"是不是同一个请求；
3. `REJECTED` 这个状态是**推导**出来的，还是操作直接指定的。

对应到数据上，就是缺口 ⑤ 说的那个同构问题。**两种操作模型，后果完全不同：**

| 模型 | 操作 | 状态怎么来 | 代价 |
|---|---|---|---|
| **A. 只有勾选框** | 全单拒绝 = 管理员逐个取消勾选（或有个"全不选"的前端开关，但请求体与逐件取消完全一致） | **必须能推导。** 服务端只能靠"所有 item 的 `approved` 都不为 `NULL`"来判断"审完了"，而"一件都没勾"和"勾完又全取消"在请求体里长得一样 | 服务端**无法区分**「还没审」和「审了、全拒」。要么在请求体里额外带一个标志，要么把 `reviewed_at` 的写入时机定成"提交审批即写"（这样"审完了"就有了独立判别位），要么干脆放弃逐件模型的纯粹性 |
| **B. 有独立的「拒绝整单」按钮**（另加"部分通过"= 逐个勾选后提交） | 两个不同的操作 | 直接写 `status`。**不需要推导** | 简单、无误判。代价是**同一个事实有两个来源**（`status` 字段 与 逐件 `approved`），而主稿 5.4 对"部分归还"明确反对这种做法：「加一个状态字段反而会引入'到底哪个字段为准'的问题」（第 563 行）——**本问面对的是同一个问题的镜像**，值得产品知道这个先例 |

**我的建议（待拍板）：**

- **界面上给两个操作，但服务端只有一个写路径**：请求体里始终是逐件 `approved: true/false` 的完整列表，「拒绝整单」按钮只是**前端把全部 item 置为 `false`** 的快捷方式。这样界面上管理员省事，数据上没有第二个来源。
- **`status` 一律推导，不直接写**（`DELIVERED` / `RETURNED` / `WITHDRAWN` 除外，它们各自由交付、归还、撤回流程写）。推导规则：

  ```
  设 items = 该申请单的全部 request_item
  若存在 approved IS NULL              → PENDING      （还没审完）
  否则若全部 approved = true           → APPROVED
  否则若全部 approved = false          → REJECTED
  否则（既有 true 又有 false）          → PARTIAL
  ```

  这条规则有个**必须补的前提**：**申请单至少要有一件器材**。`request_item` 上没有 `CHECK` 能保证这一点（它是个子表），所以要么在提交申请时校验，要么在推导时把"0 件"显式当作非法状态。主稿对此没有规定（核实过：`grep` 无"至少一件"之类的描述）——**这是一条要写进主稿的新规则，不是一个已有规则的应用。**
- **需要补一个判别位**：若要区分「还没审」和「审了、全拒」，`reviewed_at` 是最便宜的载体：**提交审批时（无论结果如何）写 `reviewed_at` 与 `reviewed_by`**。但要产品确认一件事——这会让 `reviewed_at` 的语义从"最后一次审核时间"变成"审核完成时间"。**它现在没有任何语义**：`grep` 全库 `reviewed_at|reviewed_by` 只有两处命中，都在第 319–320 行的 DDL 里，没有一个字说它们何时被写、被谁写、能不能为空。**空着的地方正好可以定义，但定义权在产品。**

### 第 5 问：申请人能不能撤回？

**核实结果：主稿内部不一致。** `WITHDRAWN` 是合法的状态值（第 317 行），`occupancy` 的映射表里也写了「撤回申请 / 申请作废 → DELETE 相关行」（第 134 行），但**全库没有第三个地方提到撤回**——没有接口、没有流程、没有权限、没有界面动线、没有状态转移规则。而且：

- 主稿 7.4 的 `actions` 数组定义了"服务端决定能做什么"的机制，但**没有申请单的 key 词表**，所以连按钮叫什么都是空的；
- `occupancy.source_request_id` 的外键**没有 CASCADE**，所以"删申请单"这个字面实现会被外键拦住（必须先删 `occupancy`）。而主稿 5.1 那条写路径的形状（状态变更 + 写历史 + 写日志同事务）已经给了正确做法：**撤回必须是一个事务**。

| 选项 | 实现成本 | 体验影响 | 建议 |
|---|---|---|---|
| **(a) 完全不支持撤回**，`WITHDRAWN` 变成永不会出现的死枚举值 | 零 | 申请人填错了申请单（选错器材、日期写错）只能等管理员拒掉它，或者干脆再提一张——而**两张单会同时占住档期**（若第一张已被批准），这正是最坏的结果 | 不推荐。**留一个永远不会出现的状态值比不写它更糟**：下一个人看到它，会以为是"实现了但没找到" |
| **(b) 只在 `PENDING` 时可撤回** | 低。一个 handler + `status` 转移 + 审计。**无需碰 `occupancy`**（`PENDING` 必然没有 `RESERVATION`，因为主稿 3.1 规定只有批准才 INSERT） | 覆盖了主要用例（填错了、不要了）。**但不覆盖最需要撤回的场景**：申请人提交后管理员批了，而项目黄了——这时他撤不了，只能等交付后走归还，或者求管理员再操作 | **推荐作为 v1**。理由很硬：**这个选项的实现风险最低，因为它不碰 `occupancy`** |
| **(c) `PENDING` 与 `APPROVED` 都可撤回**（`APPROVED` / `PARTIAL` 时撤回要连带 `DELETE` 对应的 `RESERVATION` 行） | 中。多一条 `DELETE occupancy WHERE source_request_id = $1`（在主稿 3.1 里已经有了对应的业务事件，只是没写实现）+ **一条并发上的新问题**：删除占用与别人同时抢这个档期之间的竞争。**但这个问题比看起来小**——排他约束是"插入时检查重叠"，`DELETE` 之后别人自然能插入；真正的风险是**申请人撤回的同一瞬间管理员正在交付**（`RESERVATION` → `CHECKOUT`），这需要按主稿 5.2 的规则**锁住 `request` 行**（`SELECT ... FOR UPDATE`）来串行化两个状态流转 | 体验完整 | **推荐作为 v2**，或如果产品认为"项目取消"是高频场景，就直接做 (c)。**如果做 (c)，必须在主稿里补一句"撤回与交付都锁 `request` 行"**——这是主稿第 5 节唯一没覆盖到的状态流转竞争 |
| (d) `DELIVERED` 也可撤回 | 高，且语义上不对 | 已交付的器材已经在别人手上，应该走归还而不是撤回 | 不推荐 |

**另外两个要一起定的细节（都属于 (b)/(c) 的实现成本，不是额外的可选功能）：**

1. **撤回要不要理由？** 建议**要，且随撤回一起落库**（`withdraw_reason text`，可选、允许留空）。理由和 `reject_reason` 一样：**三个月后有人问"这单怎么没了"，答案不能只在日志里**（运行时篇 R1.1 + 日志稿 9.5 的保留窗口）。
2. **撤回后申请单是"删"还是"留着标记 `WITHDRAWN`"？** 主稿第 134 行写的是"DELETE 相关行"，但那一行的主语是 **`occupancy` 的行**，不是申请单。申请单本身**必须留着**，否则 `request_item` 会被 `ON DELETE CASCADE`（第 327 行）连带删掉，申请人的历史里就没有这单了，而"我提过一单被我自己撤了"是申请人应该看得见的。**建议：`occupancy` 行 DELETE，`request` 行保留并标记 `WITHDRAWN`。** 主稿第 134 行的表述需要在这里补一个澄清。

   > **与提案 [07_cascade_rules.md](07_cascade_rules.md) 的交叉印证**：那份提案独立建议**推翻 `request_item.request_id → request(id)` 的 `ON DELETE CASCADE`，改为 `RESTRICT`**，理由正是"一次 `DELETE FROM request` 会静默抹掉审批事实（`approved`、`delivered_at`、`returned_at`）"。本提案从另一个方向（"撤回不能丢申请人的历史"）得到同一个结论。**两份提案是独立收敛的，不是互相引用出来的**——这一点值得在拍板时作为证据。

3. **撤回入口不能被别的开关关掉。** 提案 [05_owner_toggles.md](05_owner_toggles.md) 的 E7 行把「撤回申请」标为推导项并单独点出：它是"该提案里最容易被实现者做错的一处"——如果"关闭浏览 = 整个入口不可用"，撤回就没了，主稿 3.1 的释放路径也断一条。**本提案的决策 3 如果采纳，必须把"撤回入口独立于 `requester_can_browse` / `requester_can_request` 两个开关"写成硬规则**，否则两个提案会打架。

### 第 6 问：被拒之后的动线——能不能直接改成申请别的器材？

| 选项 | 实现成本 | 体验影响 | 建议 |
|---|---|---|---|
| **(a) 什么都不做**（申请人看到被拒，自己去申请页重填） | 零 | 申请人要**重新选日期、重新填项目名、重新挑全部器材**——即使原单里 8 件批了 2 件被拒。这是最容易被骂的一步：他刚刚才填过一遍 | 不推荐 |
| **(b) "再次申请"= 复制原单另开一张新单**（可调整器材和日期） | 低。**不需要新接口语义、不需要新列**——它就是一次 `POST /api/v1/requests`，只是界面上预填了原单的内容。唯一的后端工作是让申请单视图能被"复制"。**关键：`UNIQUE (request_id, equipment_id)` 不会挡路**，因为 `request_id` 是新的 | 体验好；而且它**天然绕开了"改已存在的单"这个复杂问题**——原单保持冻结（它的 `approved` / 理由是一份历史记录），新单是一份新申请，占用各自成立 | **推荐** |
| (c) 允许修改原申请单（加件、改日期后重审） | **高**。`request` 要加"可编辑窗口"的概念；`request_item` 要区分"上一轮被拒的件"和"这一轮新加的件"（这正是第 3 问选项 (b) 里"新建表"想解决的问题）；`status` 要能回退到 `PENDING`；已批准的件要不要重新审；已插入的 `occupancy` 行怎么与改后的日期对齐——**每一个都是新的未决项** | 体验略好（少一次跳转） | **不推荐。** 它把"一次审批"变成"多轮审批"，而多轮审批的完整语义（缺口 ⑦）本提案都还没有载体 |
| (d) 允许对单个被拒件"换一件再问"（部分重提） | 中高 | 表面最贴心 | 不推荐。**它等价于 (c) 的复杂度**，因为"换一件"意味着日期还是原来那段，而 `request.use_start / use_end` 是单级的——申请人其实想改的是"这一件的日期"，那就要 `request_item` 级日期，而主稿的 `request_item` 没有日期列（日期只在 `request` 上） |

**推荐 (b)，并明确它的边界（待拍板）：**

- 原申请单**只读**：`approved` 的逐件结果与理由永不改写（配合第 3 问那条"审批不可重复提交"）。
- 新单是一张普通申请单，走同一条提交路径，**不引入任何新接口**。
- 界面上"再次申请"的预填内容建议是**未获批的那些件**（而不是原单全部）——否则申请人会把已经批过的件再要一遍，而如果原单还没交付，那件器材的两个 `RESERVATION` 会**互相冲突**（主稿 3.1 的排他约束会拦住，但错误信息对申请人毫无意义："已被占用"，占用者是他自己）。**这一点如果处理不好，会变成一批"神秘冲突"的支持工单**，值得在界面上做掉（前端预填时排除，或后端在提交时把"已被你自己的在途申请占用"单独给一句人话）。

## 3. 建议拍板清单

压缩成 **四个决策**。每条给推荐答案。**全部待产品拍板**；推荐被否决时，第 4 节的 DDL 需要相应删减。

### 决策 1（决定第 1、2、3 问）—— 申请人能看到什么理由？

> **推荐：申请人能看到"哪些件被拒" + 管理员为该件填写的自由文本理由；理由允许留空；不给结构化的"替代器材"字段；`review_note` 保留为整单级补充（主要服务全单拒绝）。**

- 若否决成「不给逐件理由」→ DDL 不需要任何改动（但**仍需新增申请单视图 + 契约测试**，见缺口 ③）。
- 若在推荐之上还要「替代器材」→ 需要额外一列 + 一个"替代品当前是否可用"的读模型（见第 2 问 (c)）。

### 决策 2（决定第 4 问）—— 「未通过」和「部分通过」怎么产生？

> **推荐：界面上两个操作（逐件勾选 = 部分通过；一个"拒绝整单"快捷按钮），但服务端只有一个写路径（请求体是逐件 `approved: true/false` 的完整列表）；`status` 一律由逐件结果推导，不直接写。提交审批时写 `reviewed_at` / `reviewed_by`，用它区分"未审"和"审完全拒"。**

- 需要产品同时确认一条新规则：**申请单至少要有一件器材**（主稿现在没有这条约束，推导规则缺了它会有歧义）。
- 若不接受"推导"，改为"操作直接写 `status`"→ 请产品知道这与主稿 5.4 对"部分归还"的处理立场相反（第 563 行）。

### 决策 3（决定第 5 问）—— 能不能撤回？

> **推荐：`PENDING` 时可撤回（v1 必做，不碰 `occupancy`）；`APPROVED` / `PARTIAL` 时也可撤回（v2，或若"项目取消"是高频场景就一并做）。撤回要理由（可留空）；撤回后 `request` 行保留并标记 `WITHDRAWN`，只 `DELETE` 对应的 `occupancy` 行。**

- 若只做 v1：`WITHDRAWN` 不再是死枚举值，但"已批准后项目黄了"的场景无解——请产品确认这个场景的频率。
- 若两个状态都做：**必须在主稿补"撤回与交付都锁 `request` 行"**，这是主稿第 5 节没覆盖到的一处状态流转竞争。同时要接住提案 05 的 E7 那条约束：**撤回入口独立于两个开关**。

### 决策 4（决定第 6 问）—— 被拒之后怎么再申请？

> **推荐：不动原申请单。"再次申请" = 复制原单（预填未获批的件）另开一张新单，走同一条 `POST /api/v1/requests`。原单只读，理由与结果永不改写。**

- 若产品想要"改原单重审"（第 6 问 (c)/(d)）→ 这是一个**新的、比本提案大得多的设计任务**（多轮审批 + `request_item` 级日期 + `status` 回退 + `occupancy` 对齐），建议单独开一份提案，不要并进来。

### 顺带要拍的一条（不属于上面四问，但被它们逼出来）

> **推荐：申请单的审批动作要留痕到库里，不能只在日志里。** 主稿 10.1 说 `equipment_history` 是唯一叙事主线，但它的 `action` 枚举（第 389–391 行）里没有申请相关动作，而运行时篇 R1.1 规定"只在日志里的事会在日志被轮转掉的那天消失"。**另有一条可佐证的旁证**：运行时篇 R7.5 的上线验收清单（第 461–476 行，共 16 条）里**没有任何一条与申请审批有关**。16 条覆盖的是 readiness、优雅停机、并发互斥、可见性契约、`23P01`、磁盘满、CSV 编码、字段编辑、备份、日志——**没有"走一遍申请 → 审批 → 交付"这条动线**。它和缺口 ② 是同一件事在两个文档里的两次留白。
>
> 三个候选（待拍板，**本提案不推荐具体哪一个**，因为它牵动主稿第 10 节整体）：
> 1. `equipment_history.action` 加 `REQUEST_REVIEW` —— 但这会污染"这件器材发生过什么"的主线（一次审批会为每件被拒器材写一条）；

## 4. 若采纳，需要的 DDL 变更与主稿改动位置

### 4.1 DDL 变更（完整 SQL）

以下全部是**增量、可空、有默认语义**的改动，与主稿第 3.3 节的现有 DDL 相容：列名沿用 `snake_case`（与 `review_note` / `return_note` 一致），约束显式命名（运行时篇 RUST_IMPL 第 346 行那条硬规则：**约束名必须在迁移里显式命名**，不要依赖 Postgres 默认名），外键风格沿用现有写法。

```sql
-- migrations/0002_request_review.sql
-- 前提：0001 已应用（主稿第 3.3 节）。本迁移是纯增量，不改任何现有列。

-- ---------- 决策 1：逐件拒绝理由 ----------
ALTER TABLE request_item ADD COLUMN reject_reason text;

-- 语义约束：只有"被拒"的行才允许有理由。
-- 反对偶（approved = false 却没有理由）不加约束——理由允许留空，
-- 强迫填写会把审批流程卡死，也会让人随手填"无"。
-- 不加 NOT NULL、不加 DEFAULT：NULL 就是"未填写"（与 review_note 语义一致）。
ALTER TABLE request_item ADD CONSTRAINT request_item_reject_reason_only_when_rejected
  CHECK (approved IS NOT TRUE OR reject_reason IS NULL);
  -- 读法：approved = true 时理由必须为空；approved = false 或 NULL 时理由可空可非空。
  -- 逐行语义（与上面注释对应）：
  --   (NULL,   NULL) 合法 —— 未审、无草稿理由
  --   (NULL,   '…')  合法 —— 未审但已写了草稿理由，提交审批时转正（不拦这种半成品状态）
  --   (false,  NULL) 合法 —— 被拒、未填写原因（决策 1 允许留空）
  --   (false,  '…')  合法 —— 被拒 + 理由，这是本列存在的主用例
  --   (true,   NULL) 合法 —— 批准
  --   (true,   '…') 非法 —— 批准了却有拒绝理由，是一条自相矛盾的行
  -- 如果决策 2 定了"审批一次性原子提交、不存在草稿"，可以把条件收紧为
  -- approved IS NOT FALSE → 理由必须为空，但**没有必要**：收紧只增加一个将来会被绕过的约束。

-- ---------- 决策 3：撤回 ----------
ALTER TABLE request ADD COLUMN withdrawn_at   timestamptz;
ALTER TABLE request ADD COLUMN withdraw_reason text;

-- 状态与时间戳必须一致，否则查询会出现两个真相。
ALTER TABLE request ADD CONSTRAINT request_withdrawn_at_matches_status
  CHECK ((status = 'WITHDRAWN') = (withdrawn_at IS NOT NULL));
  -- 注意：WITHDRAWN 的撤回人就是 requester_id，所以不需要 withdrawn_by。

-- 申请单：按申请人查"我的申请"
-- 现有 request_queue_idx（主稿第 336 行）是 (workspace_id, status, created_at)，三条列上没有
-- requester_id，所以它对申请人页面**用不上**（会退化成 workspace + status 扫描再过滤）。
-- 这不是本提案的必需品，但如果决策 4 选了"再次申请"，这个页面会被频繁打开。
CREATE INDEX request_requester_idx ON request (requester_id, created_at DESC);
```

**是否要迁移旧数据 / 默认值是什么：**

| 列 | 现有行怎么办 | 默认值 |
|---|---|---|
| `request_item.reject_reason` | **无旧数据需要迁移**（主稿声明代码未实现，库里没有被拒的行）。这条留给将来：现在起就该约定，`NULL` 在界面上显示成"未填写原因"——**这正是第 1 问选项 (b) 的显示，所以"理由还没填"和"理由是空的"对申请人看起来是同一件事，不会产生新的界面状态** | `NULL`（= 未填写） |
| `request.withdrawn_at` / `withdraw_reason` | 无需回填 | `NULL` |
| `request_withdrawn_at_matches_status` 约束 | **这是唯一需要在迁移里想一下的一条**：若线上已有 `status = 'WITHDRAWN'` 的行（当前不可能——主稿说代码未实现，`WITHDRAWN` 也没有任何产生路径，见缺口 ④），`ADD CONSTRAINT` 会失败。**因为系统未实现、库里没有数据，直接 `ALTER TABLE ADD CONSTRAINT` 即可**；若将来在有数据的库上应用这条约束，必须先 `UPDATE request SET withdrawn_at = COALESCE(reviewed_at, created_at) WHERE status = 'WITHDRAWN'` 再添加 | — |

**这一节不包含的改动（如果产品选了它们，需要另写）：**

- 「替代器材」字段（第 2 问 (c)）：`request_item.alternate_equipment_id bigint REFERENCES equipment(id)`。
- 多轮审批历史表（第 3 问 (b)）：整张 `request_item_review` 表 + 唯一约束。
- 申请单事件表（第 3 节最后那条）：`request_event` 表。
