## 1. 这份日志要解决的问题

日志的价值不取决于记得多，而取决于**能不能回答会真的被问到的问题**。按运行时篇 R1.3，五个问题：

| # | 问题 | 谁会问 | 本稿怎么保证答得出来 |
|---|---|---|---|
| Q1 | 这个 500 是怎么来的？ | 开发者，用户发来一张截图 | `request_id` 贯穿响应头、错误体、日志（第 5 节） |
| Q2 | 为什么这件器材出不了库？ | 管理员 | 业务拒绝事件带**原因明细**（第 6 节 `biz.reject`） |
| Q3 | 照片为什么传不上去？ | 管理员 | 上传失败事件带 **11 个阶段之一**（第 6 节 `upload.fail`） |
| Q4 | 这份 CSV 为什么导入失败？ | 管理员 | 导入事件带编码 + 行号 + 列名 + 原始值（第 6 节 `import.reject`） |
| Q5 | 那次部署后为什么行为变了？ | 开发者 | 启动事件带版本、commit、**迁移版本**（第 6 节 `boot`） |

**Q2、Q3、Q4 是本设计真正的用处。** "记录每次写操作"价值不大——那是 `equipment_history` 和 `checkout` 表的职责。日志不可替代的地方在于记录**被拒绝的原因**和**失败的环节**，那些东西不会进业务表。

## 2. 两条不可越过的边界

### 2.1 不替代审计表

运行时篇 R1.1 定了职责划分，实现上表现为一条硬规则：

> **任何"以后要查账"的信息必须落库。** 只在日志里的事，会在日志被轮转掉的那天消失。

推论：出库成功时日志记 `checkout_id=884` 和件数，**不铺开每件器材的编号**——那是 `checkout_item` 的事。日志里重复一份业务数据，只会产生两份会漂移的真相。

### 2.2 字段名不是自由的

自由形式的日志（哪里需要就 `tracing::info!(equipment_id = %id, ...)`）会在半年内长成这样：

```json
{"equipment_id": 1284}
{"eq_id": 1284}
{"id": "1284"}
{"equipmentId": 1284}
```

**这四种写法让"按器材查历史"这件事直接不可用。** 本设计用两个机制防止它：一个**唯一的事件出口模块**（第 7 节），和一条**顶层字段白名单测试**（第 9 节）。字段名的约束不靠自觉，靠测试。

## 3. 字段模式

### 3.1 顶层字段白名单（封闭）

除 `ids` 和 `data` 之外，所有顶层字段必须来自这张表。**不在表里的字段名不能出现在日志里**，由测试强制（第 9.3 节）。

| 字段 | 类型 | 出现时机 | 说明 |
|---|---|---|---|
| `ts` | string | 恒有 | RFC 3339，**UTC**。见 3.4 |
| `level` | string | 恒有 | `INFO` / `WARN` / `ERROR` |
| `kind` | string | 恒有 | 事件名，取自第 6 节的封闭集合 |
| `msg` | string | 恒有 | 一句话，给人读的。**允许中文** |
| `request_id` | string | 有请求上下文时 | ULID，贯穿响应头与错误体 |
| `route` | string | 有请求上下文时 | **路由模板**，如 `/api/v1/equipment/{id}` |
| `method` | string | 有请求上下文时 | `GET` / `PATCH` / … |
| `status` | number | 请求完成时 | HTTP 状态码 |
| `duration_ms` | number | 请求完成时 | 服务端处理耗时 |
| `actor_id` | string | 已认证时 | 账号 ID |
| `role` | string | 已认证时 | `OWNER` / `ADMIN` / `REQUESTER` |
| `ids` | object | 按需 | 业务标识（第 3.2 节） |
| `data` | object | 按需 | 事件详情（第 3.3 节） |
| `error` | object | 出错时 | `{ code, kind, message }` |

### 3.2 `ids`：业务标识

为什么把 ID 收进一个对象而不是平铺在顶层：**顶层字段必须封闭**（才能用测试守住），而业务标识的种类会随功能增长。收进 `ids` 后，顶层保持稳定，里面可以自由加。

约定：**键名是数据库列名的下划线形式**，值一律字符串或数字。

```json
{ "ids": { "equipment_id": 1284, "checkout_id": 884, "request_id": 12 } }
```

⚠️ 注意 `ids.request_id` 与顶层的 `request_id` 是两个不同的东西——前者是主稿里的**申请单**（`request` 表），后者是**HTTP 请求关联 ID**。这个撞名是主稿数据模型带来的（申请单叫 `request`），**不要为了避开它去改数据模型**；日志里靠位置区分（顶层 vs `ids` 内），并且这张表就是这个约定唯一的文档位置。

### 3.3 `data`：事件详情

结构按 `kind` 决定，见第 6 节。两个限制：

- **深度不超过 2 层**，数组长度有上限（具体见各事件）。
- **不放自由文本的原文**：内部备注、请求体、照片字节都不进 `data`。

### 3.4 时间必须是 UTC

`ts` 一律 UTC RFC 3339（`2026-09-30T06:22:31.482Z`）。

即使业务时区是 `Asia/Shanghai`（运行时篇 R2.3），日志也不要用本地时间。理由：日志要跨重启、跨部署、可能跨机器比较，"同一时刻的两条日志时间戳能不能直接比"必须是显然的。业务日期（`DATE` 类型）仍然是本地日历日——**这是两个不同的问题，不要混**。

### 3.5 字段命名约定

| 规则 | 例子 |
|---|---|
| 顶层和 `ids` 用 `snake_case` | `request_id`、`equipment_id` |
| 枚举值用 `SCREAMING_SNAKE`，与 API 一致（主稿 7.2） | `IN_STOCK`、`ILLEGAL_TRANSITION` |
| `kind` 用点分层级 | `biz.reject`、`upload.fail` |
| 布尔用 `true`/`false`，不写 `"yes"` | |
| 缺失即省略，**不写 `null`** | |
| 数量用 `count` 后缀，金额用 `_cents` 后缀（主稿 7.2） | `item_count`、`price_cents` |

最后一条是为了避免"这个 128000 是元还是分"这种必须翻代码才能回答的问题。

## 4. 实际输出长什么样

### 4.1 一次成功的出库

```json
{"ts":"2026-09-30T06:22:31.482Z","level":"INFO","kind":"http.end",
 "msg":"POST /api/v1/equipment/checkout 200","request_id":"01J8ZQ7K3M9WX2P4","route":"/api/v1/equipment/checkout",
 "method":"POST","status":200,"duration_ms":148,"actor_id":"7","role":"ADMIN"}

{"ts":"2026-09-30T06:22:31.480Z","level":"INFO","kind":"biz.checkout",
 "msg":"出库 3 件","request_id":"01J8ZQ7K3M9WX2P4","route":"/api/v1/equipment/checkout",
 "actor_id":"7","role":"ADMIN",
 "ids":{"checkout_id":884,"project_id":31},
 "data":{"project_name":"宣传片A","user_name":"王五","checkout_date":"2026-09-30","expected_date":"2026-10-05","item_count":3}}
```

> **注**：本示例原先写成了 `msg: "PATCH …"` 而同一行的 `method` 是 `POST`——**同一行日志里方法自相矛盾**，且路径与任何一侧都不一致。已修正为 `POST`。
>
> **路径以接口清单（主稿 7.10）为准。** 出库**不是 `PATCH`**：PATCH 的三态语义（主稿 7.6）是为描述性字段的局部更新定义的，出库是一个动作。
>
> ⚠️ **待定**：出库端点的最终路径取决于接口清单 §0.1 的命名风格取舍。本节示例用的是**动作端点**形式（`/api/v1/equipment/checkout`），而提案 01 论证并采用的是**嵌套式**（`POST /api/v1/equipment/{id}/checkout`，逐件）。合并时两处必须统一——注意 `route` 字段一旦记错，日志按端点聚合就会失效（运行时篇 R1.2 第一条），所以这不是文风问题。

注意两点：

- **两行都有 `request_id`**，且最后一行（`biz.checkout`）在时间上**早于** `http.end`（span 关闭时记录），所以按 `request_id` 筛选后需要按 `ts` 排序，或者干脆**按 `kind` 分组读**。这不是缺陷——业务事实在事务提交成功时记，HTTP 摘要在响应发出时记，顺序反过来才说明有问题。
- `biz.checkout` **没有** `status` 和 `duration_ms`（那是请求级的），也**没有**每件器材的编号（那是 `checkout_item` 的事，见 2.1）。

### 4.2 一次档期冲突（Q2）

```json
{"ts":"2026-09-30T06:25:02.011Z","level":"INFO","kind":"biz.reject",
 "msg":"档期冲突：CAM-003 已被占用","request_id":"01J8ZR2A7B1CD9E5",
 "route":"/api/v1/equipment/checkout","actor_id":"7","role":"ADMIN",
 "ids":{"equipment_id":1284},
 "data":{"error_code":"RESERVED","equipment_code":"CAM-003",
         "conflict_project":"宣传片A","conflict_start":"2026-10-01","conflict_end":"2026-10-05",
         "requested_start":"2026-10-03","requested_end":"2026-10-08"}}
```

**`level` 是 INFO，不是 WARN 或 ERROR。** 用户要了一台已经被预约的机器、系统礼貌地拒绝了它——这是业务结果，是系统在**正常工作**。把它记成 ERROR 会污染错误率，运行时篇 R1.4 把这条列为明确禁止。

`data` 里的六个字段是"能不能回答 Q2"的全部内容。缺少 `conflict_project` / `conflict_*` 的话，你只知道"冲突了"，不知道跟谁冲突——那就等于没记。

### 4.3 一次上传失败（Q3）

```json
{"ts":"2026-09-30T06:30:11.884Z","level":"WARN","kind":"upload.fail",
 "msg":"照片上传失败：魔数校验不通过","request_id":"01J8ZS5F2G3HI7J8",
 "route":"/api/v1/photos","actor_id":"9","role":"ADMIN",
 "data":{"stage":"magic_bytes","bytes_received":204800,"declared_mime":"image/heic",
         "detected_magic":"ftypheic","max_upload_bytes":8388608}}
```

`stage` 取值是封闭集合：

```
receive | size_limit | magic_bytes | hash | write_tmp | rename
        | decode | exif | thumbnail | encode | persist
```

**没有 `stage` 的话，"上传失败"这四个字要花半小时去猜**——是网络断、格式不对、还是磁盘满。`detected_magic` 和 `declared_mime` 放在一起，能立刻看出是 HEIC 这类"前端没转成 JPEG"的情况（主稿 6.7）。

### 4.4 一次导入失败（Q4）

```json
{"ts":"2026-09-30T06:40:00.100Z","level":"INFO","kind":"import.reject",
 "msg":"CSV 导入被拒绝：3 行有问题","request_id":"01J8ZT8H4K5LM9N0",
 "route":"/api/v1/equipment/import/commit","actor_id":"7","role":"ADMIN",
 "data":{"stage":"commit","encoding_detected":"GBK","row_count":412,"rejected_count":3,
         "rejected":[{"row":7,"column":"分类","value":"摄影机","reason":"分类不存在"},
                     {"row":19,"column":"购买价格","value":"¥1,28O.00","reason":"金额无法解析"},
                     {"row":88,"column":"器材名称","value":"","reason":"必填为空"}]}}
```

> **本示例原先的 `route` 是 `/api/v1/equipment/import`（没有阶段后缀）。** 但导入是**两阶段**的（运行时篇 R5.1 的预览 + R5.3 的提交），一个 route 无法区分「预览被拒绝」与「提交被拒绝」——而这两件事的排查方式不同。所以 `route` 改成实际的两个端点，并**加了 `data.stage` 字段**（`preview` | `commit`）作为第二重保险：即使将来路径再变，阶段仍然明确。

三条约定：

- **`encoding_detected` 必带。** 编码检测是运行时篇 R5.1 的核心，日志里没有它就无法事后判断"用户说的乱码"是哪一环。
- `rejected` **最多 20 条**，超出时加 `"truncated": true`。1000 行全列出来会让日志行超过任何采集器的单行上限。
- **`value` 是原始输入**（`¥1,28O.00` 里那个字母 O 就是原因），不要规范化后再记。

## 5. 关联：`request_id` 怎么贯穿

这是 Q1 的全部机制。四个位置必须是**同一个值**：

```
1. 客户端（可选）带 X-Request-Id          → 若合法则沿用，否则生成 ULID
2. 服务端 span 字段 request_id
3. 响应头 X-Request-Id                      → 客户端/代理能看到
4. 错误体 error.requestId（主稿 7.3）       → 用户截图里有它
```

用户发来一张带 `01J8ZQ7K3M9WX2P4` 的截图 → 你 `grep` 这一个值 → 得到那一次请求的**全部**日志（`http.end` + 所有业务事件），因为业务事件在同一个 span 里，自动带上这个字段。

三条实现约定：

| 约定 | 理由 |
|---|---|
| 校验来信的 `X-Request-Id`：可打印 ASCII、长度 ≤ 128，不合法就生成 | 防止有人塞 `\n` 到日志里伪造行 |
| **span 字段用 `String`，不用 `&str`** | `span!` 的字段类型会进 `FormattedFields`，借用型字段容易撞上生命周期问题；这点分配完全不值得省 |
| `on_response` 必须是 `Fn`，不能变成 `FnMut` | `tower_http` 要求闭包可并发共享；想在里面累加状态会在编译期失败（这是好事） |

**没有网关也要接受 `X-Request-Id`。** 现在没人发它，成本为零；而将来一旦前面加了 Caddy 之外的代理或客户端要重试关联，有了它就能端到端串起来。

## 6. 事件清单（封闭集合）

`kind` 只能取以下值。**新增 `kind` 必须同时更新这张表和字段白名单测试**，否则第 9.3 节的测试会红——这是有意的摩擦。

| `kind` | 级别 | 何时记 | `data` 关键字段 |
|---|---|---|---|
| `boot` | INFO | 进程启动，一次 | `version`, `git_commit`, `migration_version`, `bind_addr`, `data_dir`, `pool_max_connections` |
| `http.end` | INFO/WARN/ERROR | 每个请求一次，响应发出时 | `status`, `duration_ms` |
| `biz.create` | INFO | 建档 | `equipment_code`, `category` |
| `biz.update` | INFO | 字段编辑 | `changed_count`, `fields[]` |
| `biz.checkout` | INFO | 出库（含交付） | `project_name`, `user_name`, `checkout_date`, `expected_date`, `item_count` |
| `biz.return` | INFO | 归还 | `item_count`, `closed`（该出库单是否已全还） |
| `biz.maintenance` | INFO | 送修 / 完成 | `fault_len`, `vendor`, `outcome` |
| `biz.approve` | INFO | 申请审批 | `approved_count`, `rejected_count`, `result`（`APPROVED`/`PARTIAL`/`REJECTED`） |
| `biz.deliver` | INFO | 办理交付 | `item_count` |
| `biz.archive` | INFO | 归档 / 恢复 | `restore`(bool) |
| `biz.reject` | INFO | **业务规则拒绝了请求** | `error_code` + 各事件专有明细（见 4.2） |
| `biz.conflict` | **WARN** | **排他约束 `23P01` 被实际触发** | `equipment_id`, `during`, `pre_check_passed`(bool) |
| `biz.retry` | **WARN** | 一次事务重试（见实现契约 §4） | `attempt`, `max_attempts`, `error_class`(SQLSTATE), `error_kind`, `elapsed_ms` |
| `tx.idle` | **WARN** | 事务在两条语句之间空闲超过 500ms（应用侧探针） | `idle_ms`, `last_statement` |
| `pool.stat` | **WARN** | 连接获取等待超过阈值 | `wait_ms`, `pool_size`, `idle_count` |
| `auth.login` | INFO | 登录成功 | — |
| `auth.fail` | WARN | 登录失败 | `reason`（**不含用户名原文**，见 8.2） |
| `auth.deny` | WARN | 授权拒绝（403） | `required_role`, `path_group` |
| `auth.logout` | INFO | 登出 | — |
| `upload.ok` | INFO | 上传成功 | `stage`=`persist`, `sha256`, `bytes`, `width`, `height`, `deduped`(bool) |
| `upload.fail` | WARN/ERROR | 上传失败 | `stage` + 该阶段相关字段（见 4.3） |
| `import.accept` | INFO | 导入提交成功 | `encoding_detected`, `row_count` |
| `import.reject` | INFO | 导入被拒绝 | `encoding_detected`, `row_count`, `rejected_count`, `rejected[]` |
| `export` | INFO | 导出 | `kind`（数据/模板）, `row_count`, `masked`(bool) |
| `job.end` | INFO/ERROR | 每个 job 每次执行 | `job`, `result`(`ok`/`failed`), `affected`, `duration_ms` |
| `store.inconsistent` | ERROR | 占用对账发现偏差 | `occupancy_id`, `expected`, `actual` |
| `file.missing` | ERROR | 照片文件不存在 | `rel_path`, `photo_id` |

### 6.1 `biz.conflict` 值得单独解释

它是唯一一个**正常路径下不应该出现**的 WARN。

主稿第 3 节里，排他约束是"正确性兜底"，预检查负责给人话。所以：

- 预检查**先拦下** → 记 `biz.reject`（INFO）→ 正确。
- 预检查漏了、约束拦住 → 记 `biz.conflict`（WARN）→ **说明预检查有 bug**。

它出现一次就值得看一眼代码。**不写下来，运维看到它会以为"数据库起作用了"，是好事**——而它实际是缺陷信号。这也是运行时篇 R7.3 把它列进每周检查项的原因。

### 6.2 `job.end`：什么都做也要记

即使 `affected = 0` 也记一行，`result` 恒有值。

理由：如果只在真做了事的时候才记，那么"job 没跑"和"job 跑了但没活干"在日志里**完全一样**。前者是故障，后者正常，而你会以为一切正常。加上这条之后，"每日 job 没跑"的告警退化成一句话：**搜当天有没有 `job.end` 行**。

`job.end` 不带 `request_id`（它不在请求里），靠 `data.job` 分组。

## 7. Rust 实现

### 7.1 依赖

```toml
[dependencies]
tracing = "0.1"
tracing-subscriber = { version = "0.3", features = ["env-filter", "json"] }
tower-http = { version = "0.6", features = ["trace", "request-id"] }
ulid = "1"
time = { version = "0.3", features = ["formatting", "macros"] }
```

不要引入 `log` 或 `slog`。`tracing` 的 span 是"请求上下文自动附加到所有事件"这个能力的来源（第 5 节），换掉它就等于手写上下文传递。

### 7.2 初始化

```rust
pub fn init(cfg: &Config) -> anyhow::Result<()> {
    let filter = EnvFilter::builder()
        .with_default_directive(LevelFilter::INFO.into())
        .from_env_lossy();

    // SQLx 的查询日志在 debug 下非常吵，默认压到 WARN
    let filter = filter.add_directive("sqlx=warn".parse()?);

    let registry = tracing_subscriber::registry().with(filter);

    match cfg.log_format {
        LogFormat::Json => registry.with(
            fmt::layer()
                .json()
                .with_current_span(true)     // span 字段平铺进每条记录
                .with_span_list(false)       // 只带当前 span，不带祖先链
                .with_timer(UtcTime::rfc_3339())
                .flatten_event(true),        // 事件字段与 span 字段同一层
        ).init(),
        LogFormat::Pretty => registry.with(
            fmt::layer().with_timer(UtcTime::rfc_3339()).compact()
        ).init(),
    }
    Ok(())
}
```

四个设置都是有意的：

| 设置 | 为什么 |
|---|---|
| `.with_current_span(true)` | 这是 `request_id` 自动出现在每条业务日志上的机制。关掉它，第 5 节的关联就断了 |
| `.with_span_list(false)` | 带上祖先 span 链会让每条日志多几个无用的嵌套对象 |
| **UTC 时间** | 第 3.4 节 |
| `sqlx=warn` 默认压级 | 不压的话，debug 级别下每条 SQL 都会打出来，把业务日志淹掉 |

### 7.3 事件词汇表：唯一的出口

**所有日志都从这个模块出，业务代码里不出现裸 `tracing::info!`。** 这是第 2.2 节那个"字段名不是自由的"在代码层的落点。

```rust
pub mod log {
    use super::*;

    /// 从 event 字段里自动补 request_id / route / actor_id / role
    macro_rules! biz_event {
        ($kind:literal, $msg:expr $(, $k:ident = $v:expr)* $(,)?) => {
            tracing::info!(
                kind = $kind, msg = $msg $(, $k = $v)*
            )
        };
    }

    pub fn checkout(actor: &Actor, v: &CheckoutView, cmd: &CheckoutCmd) {
        tracing::info!(
            kind = "biz.checkout",
            msg = %format!("出库 {} 件", v.item_count),
            ids = ?ids! { checkout_id = v.id, project_id = v.project_id },
            data = ?data! {
                project_name = cmd.project_name,
                user_name = cmd.user_name,
                checkout_date = %cmd.checkout_date,
                expected_date = ?cmd.expected_date,
                item_count = v.item_count,
            },
        );
    }

    pub fn reject_reserved(actor: &Actor, req: &CheckoutCmd, c: &Conflict) {
        tracing::info!(
            kind = "biz.reject",
            msg = %format!("档期冲突：{} 已被占用", c.equipment_code),
            ids = ?ids! { equipment_id = c.equipment_id },
            data = ?data! {
                error_code = "RESERVED",
                equipment_code = c.equipment_code,
                conflict_project = c.project_name,
                conflict_start = %c.start,
                conflict_end = %c.end,
                requested_start = %req.checkout_date,
                requested_end = ?req.expected_date,
            },
        );
    }

    pub fn upload_failed(actor: &Actor, stage: UploadStage, detail: &UploadDetail) {
        let level = if stage == UploadStage::Receive { Level::WARN } else { Level::ERROR };
        tracing::event!(level, kind = "upload.fail",
            msg = %format!("照片上传失败：{}", stage.zh()),
            data = ?detail);
    }

    pub fn job_end(job: &str, r: &JobResult) {
        let level = if r.ok { Level::INFO } else { Level::ERROR };
        tracing::event!(level, kind = "job.end",
            msg = %format!("{} {}", job, if r.ok { "完成" } else { "失败" }),
            data = ?data! { job = job, result = r.result_str(),
                            affected = r.affected, duration_ms = r.duration_ms },
            error = ?r.error);
    }
}
```

`ids!` / `data!` 两个小宏产出 `serde_json::Value`（或一个实现了 `serde::Serialize` 的 `Vec<(&str, Value)>`），保证嵌进日志时是对象而不是调试字符串。

**为什么不用 `tracing` 的 `#[instrument]` 直接铺业务字段**：`#[instrument]` 记录的是函数入参，它会把整个 `CheckoutCmd` 打出来（可能含备注原文）。这个设计要的是**显式挑选的字段**，所以宁可多写几行。

### 7.4 HTTP span 中间件

```rust
pub fn trace_layer() -> TraceLayer<...> {
    TraceLayer::new_for_http()
        .make_span_with(|req: &Request<_>| {
            let request_id = req
                .headers()
                .get("x-request-id")
                .and_then(|v| v.to_str().ok())
                .filter(|s| is_safe_id(s))
                .map(str::to_owned)
                .unwrap_or_else(|| ulid::Ulid::new().to_string());

            // Axum 在路由匹配之后才会把 MatchedPath 放进 extensions；
            // 这个中间件挂在 route_layer 上时能拿到，挂在外层时拿不到（见下方说明）
            let route = req.extensions().get::<MatchedPath>()
                .map(|m| m.as_str().to_owned())
                .unwrap_or_else(|| req.uri().path().to_owned());

            let actor = req.extensions().get::<Actor>();

            tracing::info_span!("http",
                request_id = %request_id,
                route = %route,
                method = %req.method(),
                actor_id = actor.map(|a| a.id.to_string()).unwrap_or_default(),
                role = actor.map(|a| a.role.as_str()).unwrap_or(""),
                status = tracing::field::Empty,      // 在 on_response 里填
                duration_ms = tracing::field::Empty,
            )
            .also(|_| { /* 见下：request_id 需要塞回 extensions 供响应头用 */ })
        })
        .on_response(|res: &Response<_>, latency: Duration, span: &Span| {
            span.record("status", res.status().as_u16());
            span.record("duration_ms", latency.as_millis() as u64);
            tracing::info!(kind = "http.end",
                msg = %format!("{} {} {}", span.field("method")...),
                status = res.status().as_u16(),
                duration_ms = latency.as_millis() as u64);
        })
}
```

这段伪代码里有**三个必须做对的细节**，实现时容易踩：

**① `MatchedPath` 的可见性取决于中间件挂在哪一层。**
- 挂在 `route_layer`（路由之后）→ 能拿到模板，`route` 是 `/api/v1/equipment/{id}`。✅
- 挂在 `ServiceBuilder` 外层（路由之前）→ 拿到的是实际路径 `/api/v1/equipment/1284`，**高基数，等于不能聚合**。

推荐：**挂在 `route_layer`**，并接受"未匹配的请求（404）没有模板"——那类请求用实际路径反而是对的，因为它本来就要暴露"有人在扫路径"。

**② `request_id` 要能进响应头。**
span 里的字段读不出来给响应头用。做法是在 `make_span_with` 里把生成的 id 同时塞进 `req.extensions_mut()`（需要在中间件里用 `&mut Request`），然后在 `on_response` 或错误体构造时从 extensions 取。**这两处必须是同一个值**，否则第 5 节的关联就断了。若嫌这套绕，替代方案是**自己写一个中间件**而不使用 `TraceLayer`：生成 id → 插 extensions → 建 span → `next.run(req)` → 从 extensions 取 id 写响应头 → 记 `http.end`。**对这个规模，手写反而更短、更可控**，`TraceLayer` 的价值主要在成熟的延迟测量上。

**③ `on_response` 是 `Fn`。** 不要在闭包里累加计数或缓存 id——编译期就会拦下来，这是好事，别用 `Mutex` 绕过去。

### 8.2 必测清单

| # | 测什么 | 为什么 |
|---|---|---|
| L1 | **日志里搜不到密码**：带 `password` 字段打登录接口，断言 `capture.text()` 不含该字符串 | 运行时篇 R1.7。一次写对，永久有效 |

| L6 | **导入失败的日志带行号和原始值**：断言 `data.rejected[0].value` 是**规范化前**的原文 | 4.4 |

| L8 | **`job.end` 在 `affected = 0` 时也产出** | 6.2。没有这条，job 静默死亡不可检测 |
| L9 | **启动事件里有 `migration_version`**，且 `data` 里没有 `database_url` | 7.5 和 Q5 |

**L1 和 L2 的实现方式要注意**：不要用 grep 源码找 `password`，要在**运行时**断言输出。源码检查挡不住 `?config`（`Debug` 实现可能带口令）这类间接泄漏。

这条测试是第 2.2 节"字段名不是自由的"的执行者。它拦住的是**拼写漂移**（`equipmentId` vs `equipment_id`）和**顺手加顶层字段**（想记设备型号就直接写了 `model = "FX3"`——应该在 `data` 里）。

### 8.4 不要做的事

- **不要断言日志的完整文本**（含时间戳、顺序），那会让每个无关改动都弄红测试。断言**字段的存在和值**。
- **不要断言日志条数**。数量会随实现细节变化（比如事务重试），而字段契约才是要守的东西。唯一例外是 L8 的"至少一条"。

## 9. 持久化：先算量，再选方案

### 9.1 这台系统会产生多少日志

猜测会让方案失衡，所以先估。按第 6 节的事件清单，一次典型操作的日志量：

| 事件 | 条数 | 单条估算 |
|---|---|---|
| `http.end` | 每个请求 1 条 | ~250 B |
| `biz.*` | 每次写操作 1 条 | ~350 B |
| `upload.ok` | 每张照片 1 条 | ~300 B |
| 其余（`auth.*`、`job.end`、错误） | 每日几十条 | ~300 B |

十人工作室一天的粗略画像——假设**每人每天约 50 次写请求**（登录、浏览列表、改字段、出库、归还、审申请）：

```
500 个 HTTP 请求 × (250 B + 0.5 × 350 B)  ≈ 210 KB
+ 照片上传 30 张 × 300 B                   ≈   9 KB
+ 其余                                     ≈  10 KB
─────────────────────────────────────────────────
约 230 KB / 天  ≈  7 MB / 月  ≈  84 MB / 年
```

**关键比较：一张器材照片（压到 1600 px）是 300–800 KB。一天的日志量相当于一张照片。**

所以第一个结论是：**这台系统在很长时间内不会有"巨大量的积累"这个问题。** 日志的存储量比照片小两到三个数量级（主稿 6.1 估照片是几百 MB），而照片本身也已经是个不痛不痒的量级。

按规模外推，给一个容量参照：

| 日活 | 日志量/天 | 一年（未压缩） | 一年（zstd，约 10:1） |
|---|---|---|---|
| 10 人 | ~230 KB | ~84 MB | ~8 MB |
| 50 人 | ~1.2 MB | ~430 MB | ~45 MB |
| 200 人 | ~5 MB | ~1.8 GB | ~180 MB |

**到 200 人这个数量级，一年的日志压缩后仍然只有 180 MB。** 这就是为什么本节的结论是"用文件"，而不是"上日志系统"。

### 9.2 结论：文件 + 按天分片 + 压缩，不要数据库

| 方案 | 用不用 | 理由 |
|---|---|---|
| **JSON Lines 文件，按天分片，压缩** | **用** | 见 9.3 |
| 数据库表（Postgres 存日志） | **不用** | 日志写入会和业务写入抢同一批连接和同一块磁盘；而日志的查询模式（大范围扫、按子串找）恰好是关系数据库最不擅长的 |
| Elasticsearch / Loki / ClickHouse | **不用**（现在） | 见 9.6 |
| grep + jq | **用** | 见 9.4。对"排障"这个真实用途，它比任何 SQL 都更直接 |

**"日志不进数据库"这条还有一个工程上的理由**：运行时篇 R1.1 定了日志不是事实来源。一旦有人把日志写进业务库，它就会慢慢被人当成事实来源来用（写报表、写统计），然后那些查询就变成了生产依赖，而日志的量级和保留策略本来就不适合承担这个角色。

### 9.3 具体形态

```
写到 stdout（JSON Lines，一行一条记录）
  → 由容器运行时的 json-file driver 按大小轮转
  → 每日由 cron 归档：读昨天的日志 → zstd 压缩 → 按日期命名存放
```

**归档脚本本身就是"持久化策略"的全部**，大约十几行：

```bash
#!/usr/bin/env bash
set -euo pipefail
D=$(date -d yesterday +%F)
OUT=/var/lib/lensmax/logs
mkdir -p "$OUT"
docker compose logs --since "${D}T00:00:00" --until "${D}T23:59:59" app \
  | zstd -19 -q -o "$OUT/${D}.jsonl.zst"
```

四条约定：

| 约定 | 理由 |
|---|---|
| **文件名带日期**（`2026-09-30.jsonl.zst`） | 查询时看文件名就能定位，不需要索引。这是"按天分片"的全部价值 |
| **zstd 而不是 gzip** | 同压缩率下快数倍。日志是"写一次、偶尔读一次"，压缩速度不影响用户，但影响归档任务和事后查询解压的等待时间 |
| **JSON Lines**：一行一条完整记录 | 才允许 `grep` 单行判断、允许 `zstdcat \| jq` 流式处理。**绝不能输出跨行的 JSON 数组或 pretty-print**，那会让流式查询失效 |
| 归档**不做 fsync** | 崩溃时最多丢几秒日志。日志不是账，为它加 fsync 是用业务性能换一个不需要的保证 |

**关于"每天一个文件会不会太多文件"**：一年 365 个文件，十年 3650 个。这不构成任何问题，`ls` 和 glob 都毫无压力。

### 9.4 三个真实查询

日志"可读"的标准不是功能多，是这三个操作能不能一步完成。它们各对应一个会真的被问到的问题：

```bash
# ① 按 request_id 追一次请求的全部日志
#    request_id 在每条记录里，所以跨文件、跨天的都找得到，不需要这些行相邻
zstdcat /var/lib/lensmax/logs/*.jsonl.zst | grep -F '01J8ZQ7K3M9WX2P4'

# ② 按器材追它的操作历史（先看文件索引把范围缩小到今天）
zstdcat /var/lib/lensmax/logs/2026-*.jsonl.zst \
  | jq -c 'select(.ids.equipment_id == 1284)'

# ③ 找出所有真正的错误（注意 biz.reject 是 INFO，不会被捞进来——这是设计意图）
zstdcat /var/lib/lensmax/logs/*.jsonl.zst \
  | jq -c 'select(.level == "ERROR")'
```

**①为什么不需要索引**：第 5 节的 `request_id` 贯穿机制让"一次请求的所有日志"可以被一个子串搜到。这是"时间分片 + 全量扫描"能替代索引系统的原因——**要定位的键在每一条记录里，而不是在文件的位置上**。

**②为什么先看文件名**：`ids.equipment_id` 的时间分布是不确定的（一件器材可能三个月没人动），所以查询要跨天。但绝大多数排查是"最近几天"，按日期 glob 就能把扫描量降到几 MB——解压 + jq 在一秒内。

### 9.5 轮转参数（这是运维要做的唯一一件事）

日志由容器运行时的 `json-file` driver 轮转，一次配置：

```yaml
services:
  app:
    logging:
      driver: json-file
      options:
        max-size: "100m"     # 单文件上限
        max-file: "5"        # 最多保留 5 个 → 最多 500 MB
```

`max-size × max-file` **就是保留窗口**——超出后 Docker 删最旧的。500 MB 对着每天 230 KB 的产出，等于永远不删；对 200 人的规模（每天 5 MB）是约 100 天。**这个参数本身就是保留策略**，不需要另写清理任务。

两个实现细节：

**① 采集器的单行上限。** 很多采集器默认截断超长行（常见 16 KB 或 32 KB）。本设计里最长的一行是 `import.reject`，已经把 `rejected[]` 限制在 20 条（4.4）；若还有必要，**别指望采集器兜底，要在事件层设上限**。

**② `.json()` 层要同时加 `.with_ansi(false)`。** 否则在 TTY 上跑出的文件会夹 ANSI 转义码，让 `jq` 在那些行上报解析错误——而"偶发的 jq 报错"会被误判成日志损坏。

**③ 如果要保留超过本地磁盘的量**：加一个 sidecar（Promtail / Alloy）把文件推到对象存储，或者干脆让上面的归档脚本把 `${D}.jsonl.zst` 顺势传到异地（和主稿 11.2 的备份走同一个目标）。**注意不要把日志和数据库备份混在同一个保留策略里**——两者的价值衰减速度完全不同（数据库备份永久有价值，日志 30 天后基本没人看）。

### 9.6 什么时候才该上日志系统

给一个可判断的触发条件，避免下一个人在没有人要求的情况下引入一个有状态的组件：

| 触发条件 | 才考虑 |
|---|---|
| 需要**跨主机**聚合（部署从单机变成多实例） | Loki 或类似 |
| 需要**按字段聚合出指标**（比如"每天的 409 按项目分组"） | 这时应该先问：**这个统计是不是该进数据库的报表表？** 日志不是做统计的地方 |
| 一年的压缩日志**超过 50 GB** | 按 9.1 的表，这需要日活到几千人。这个产品不会到 |
| 有人**每天**手动 grep 超过 10 次 | 说明有反复出现的问题，**该修那个问题，而不是上日志系统** |

最后一行是这张表里最有用的一条：**"查询不方便"通常不是工具问题，是系统在反复出同一个问题。**

### 9.7 减少量的正确方式：收紧记录，而不是缩短保留

如果确实觉得日志多，正确的做法是**按运行时篇 R1.3 的五个问题逐条检查**——有没有事件既不回答那五个问题、也不是运维必需？那才是该删的。

**不要用缩短保留期来解决量的问题。** 理由：排障的典型时间跨度是"用户两三个月后想起来报了个问题"。把保留从 90 天砍到 7 天，省下的磁盘（按 9.1，一年 8 MB）等于零，代价是三个月前的事故再也查不了。

**一个具体的候选删减项**：不要记每次数据库连接的获取/释放、不要记导入时逐行的处理日志（那是 4.4 里 `rejected[]` 上限 20 条的原因）、不要在 INFO 级别打印 SQL。`sqlx=warn` 那条默认指令（7.2）就是为最后这项设的。

慢查询也不该进日志——**那是 `pg_stat_statements` 的地方**，它比日志更适合做这件事，而且已经在数据库里了。
