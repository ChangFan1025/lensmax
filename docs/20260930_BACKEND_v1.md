## 0. 本稿怎么用

交接稿明确不含技术选型，本稿是它的技术对照面。三条读法：

1. **第 2 节是全部决定。** 后面每一节都是给某一条决定做论证和落地细节。评审时先看第 2 节。
2. **第 3 节的核心是 `occupancy` 表。** 如果只读一节，读那一节——它是本设计里唯一一处"用数据库结构消除整类并发缺陷"的地方，也是选 Postgres 而不是 SQLite 的唯一硬理由。
3. **第 13 节列了未决项，[待拍板清单](20260930_OPEN_DECISIONS_v1.md) 是它的汇总。** 那些地方本稿给了默认方案但需要产品拍板，实现前必须收敛。**接口清单与校验规则在 [实现契约](20260930_IMPL_CONTRACT_v1.md)**，本稿不再重复端点表。

术语：本稿在数据模型和代码层面统一使用 `checkout` / `return`，界面文案沿用交接稿的「出库 / 归还」。交接稿第 11 节指出的「出库 vs 借出」不一致，本稿的立场见第 13.1 节。

**并发控制的边界（重要，见 5.5）：** 本系统的并发控制只解决两类竞争——**状态流转**（`SELECT ... FOR UPDATE`，主稿 5.1）和**档期占用**（排他约束，主稿第 3 节）。**描述性字段的编辑不设锁、不做在线状态、不做协同合并**：它是一次原子提交，后写覆盖，变更写进 `equipment_history` 留痕。理由见 5.5。这个结论的适用范围是**十人以内的单工作室**（实际会编辑同一条记录的是 2～3 人）——超出这个规模需要重新评估，不要在没有人要求的情况下把它做成协同编辑。

## 1. 约束：后端要满足什么

按交接稿的**硬规则**倒推，只有五条约束真正决定架构形状：

| # | 约束 | 出处 | 对架构的要求 |
|---|---|---|---|
| C1 | 器材五态单向流转，违规给人话；状态变更与写历史同事务 | 第 4 节 | 状态机必须有唯一落点；领域逻辑不能散在 handler 里 |
| C2 | 通过审批的器材按日期段预留，别人不能领走 | 第 5.5 节 | 时间区间互斥。这是全系统最容易出错的地方 |
| C3 | 申请人拿到的对象是裁剪过的，整字段不下发 | 第 3 节 | 字段可见性必须有唯一出口，且不能靠前端 |
| C4 | 批量操作整批拒绝、点名违规件，不做部分成功 | 第 4 节 | 批量走单事务，无 savepoint |
| C5 | 主理人唯一、不可被改权限、只有他能建第一个账号 | 第 2 节 | 账号创建权是数据约束，不是配置 |

C2 是唯一一条"应用层只能尽量保证、数据库才能保证"的约束。**它决定了数据库选型。**

## 2. 决定清单

### 2.1 技术栈

| 层 | 选型 | 决定它的是什么 |
|---|---|---|
| 运行时 | Tokio（multi-thread） | — |
| Web 框架 | Axum 0.8 | tower/tower-http 生态；handler 与 extractor 模型干净 |
| 数据库 | **PostgreSQL 16+，启用扩展 `btree_gist`** | **C2**。见第 3 节 |
| 数据访问 | SQLx 0.8（`query!` 宏 + 离线缓存） | 不用 ORM。核心规则是 SQL 性的（排他约束、区间、部分索引） |
| 迁移 | SQLx Migrate，forward-only 的纯 SQL | 可 review、可手工执行 |
| 序列化 | serde，`rename_all = "camelCase"` | 迁就既有前端 |
| 校验 | garde | 与错误体统一 |
| 错误 | thiserror（领域）+ 手写 `IntoResponse`（API） | 见第 8 节 |
| 日期时间 | `time`（SQLx 的 time feature） | 业务日期 `Date`，审计时间 `OffsetDateTime` |
| 密码/会话 | `argon2` + 自托管 session 表 + httpOnly cookie | **C5**。见第 9 节 |
| API 契约 | utoipa → OpenAPI → `openapi-typescript` | 见第 7 节 |
| 图片处理 | `image` + `fast_image_resize` + `kamadak-exif`（读方向） | 见第 6 节 |
| 反向代理 | Caddy | 自动 TLS；静态照片直发 |
| 部署 | Docker Compose：app + postgres + caddy | 见第 12 节 |
| 后台任务 | 同 workspace 第二个 binary（`jobs`），cron 触发 | 见第 11 节 |

### 2.2 结构性决定

| # | 决定 | 理由 |
|---|---|---|
| D1 | **`occupancy` 独立成表，用 Postgres 排他约束保证区间互斥** | C2 从"检查"变成"约束" |
| D2 | 四层分离：`domain`（零 I/O）/ `services`（事务编排）/ `db`（SQL）/ `api`（HTTP） | C1 的状态机只能有一个落点 |
| D3 | 领域函数收 `&mut PgConnection`（由 `Transaction` 解引用得到），不收 `&PgPool` | C1 的后半句由类型强制，而非靠纪律 |
| D4 | 可见性用**两个序列化结构体**，不用白名单过滤函数 | C3 由编译器保证 |
| D5 | 照片内容寻址（SHA-256），不可变，只清孤儿 | 见第 6 节 |
| D6 | 归档（`archived_at`）与「已出售」是两件事，不做软删除 | 见第 3.4 节 |
| D7 | `workspace_id` 从第一天进所有表 | 交接稿第 11 节那个切不动的下拉是预留位 |
| D8 | 服务端下发 `actions` 数组，客户端不推导状态合法性 | 见第 7.4 节 |

### 2.3 明确不采纳

| 方案 | 为什么不 |
|---|---|
| SQLite | C2 需要区间排他约束，SQLite 没有。替代方案（写锁串行化 + 巡检）把数据库保证降级为纪律保证，且失去并发写。单工作室场景下 SQLite 更省事，但只要 C2 存在，Postgres 是更低后悔的选择。**触发回退的条件见第 13.6 节** |
| ORM（SeaORM / Diesel） | 本设计的难点集中在 SQL 层（排他约束、区间运算、部分索引、对账查询），ORM 在这些地方要么无能为力要么要写裸 SQL，净收益为负 |
| JWT 会话 | 需要能立即踢掉被停用的账号（交接稿第 2 节），无状态 token 做不到 |
| 托管认证服务 | C5 的"唯一主理人 + 只有他能建第一个账号"要落成自己数据上的唯一约束，不是第三方配置项 |
| 把图片存进数据库 | 备份体积与"取列表误捞 BLOB"的性能事故，且无法利用静态文件缓存 |
| 生成 PDF 存进系统 | 当前流程是打印出来手写签名，纸质件即原件。**若产品要留签字扫描件，这条需重评**（第 13.3 节） |

## 3. 数据模型

### 3.1 `occupancy`：占用表

**这是本设计的核心。** 交接稿里有三条互相纠缠的规则：

- 第 5.5 节：通过的器材立刻按申请日期段预留，不能被别的出库领走
- 第 5.2 节：已被通过的申请预留了档期的器材不能出库，点名拦下
- 第 5.2 节：出库表单的「预计归还」可留空

按直觉实现会得到两条各自为政的检查路径——申请里检查器材、出库里检查申请——而且都不处理"出库中且没填预计归还日期"的器材在未来能否被预约。

**做法：把"占用"抽成一张一等表，让数据库保证任何两个占用区间不重叠。**

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE occupancy (
  id                 bigserial PRIMARY KEY,
  equipment_id       bigint NOT NULL REFERENCES equipment(id),
  during             daterange NOT NULL,
  kind               text NOT NULL CHECK (kind IN ('RESERVATION','CHECKOUT')),
  source_request_id  bigint REFERENCES request(id),
  source_checkout_id bigint REFERENCES checkout(id),
  created_at         timestamptz NOT NULL DEFAULT now(),

  CONSTRAINT occupancy_bounds CHECK (NOT isempty(during)),
  CONSTRAINT occupancy_no_overlap
    EXCLUDE USING gist (equipment_id WITH =, during WITH &&)
);

CREATE INDEX occupancy_equipment_idx ON occupancy (equipment_id, during);
```

区间一律用**半开区间 `[start, end)`**，`end` 为 `infinity` 表示"无归还期限"。

业务事件到表操作的映射：

| 业务事件 | 对 `occupancy` 的操作 |
|---|---|
| 管理员批准某件器材 | INSERT `[使用开始, 预计归还 + 1天)` |
| 批准时取消勾选某件（= 拒绝） | 不 INSERT。**这就是"部分通过"的实现方式** |
| 办理交付 | 该行 UPDATE：`kind='CHECKOUT'`，区间起点改为实际出库日期，写 `source_checkout_id` |
| 归还某件（逐件） | DELETE 该行 |
| 撤回申请 / 申请作废 | DELETE 相关行 |
| 直接出库（非申请路径） | INSERT `kind='CHECKOUT'` |
| 出库时预计归还未填 | INSERT 时 `end = 'infinity'` |
| 部分归还 | 每次归还释放自己那一行，其余行继续占位 |

为什么 `infinity` 是关键：一条 `[2026-10-01, infinity)` 的占用会让该器材的**任何**未来区间都冲突。这正是交接稿第 5.2 节"没填归还日期"的正确语义——不是"不知道占多久所以先不管"，而是"在归还之前谁也别想预约它"。

### 3.2 冲突的双层处理

应用的预检查负责**给人话**，数据库约束负责**正确性**，两者走同一个错误出口：

```rust
// services/checkout.rs —— 先查，为了拿到人话错误
let conflict = db::occupancy::find_conflict(&mut tx, equipment_id, during, None).await?;
if let Some(c) = conflict {
    return Err(DomainError::Reserved {
        project: c.project_name, start: c.during.start(), end: c.during.end(),
    }.into());
}
// 然后插入。并发下这里若仍冲突，由 23P01 翻译成同一个错误（见第 8 节）
```

预检查的 SQL（半开区间重叠判定，`NULL` 用 `infinity` 语义）：

```sql
SELECT o.id, o.kind, o.during, r.project_name
  FROM occupancy o
  LEFT JOIN request r ON r.id = o.source_request_id
 WHERE o.equipment_id = $1
   AND o.id <> COALESCE($4, -1)
   AND o.during && daterange($2, $3, '[)');
```

### 3.3 完整 DDL 骨架

```sql
-- ---------- 工作区与账号 ----------
CREATE TABLE workspace (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  name        text NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE app_user (
  id             bigserial PRIMARY KEY,
  workspace_id   uuid NOT NULL REFERENCES workspace(id),
  username       text NOT NULL,
  display_name   text NOT NULL,
  password_hash  text NOT NULL,               -- argon2id
  role           text NOT NULL CHECK (role IN ('OWNER','ADMIN','REQUESTER')),
  disabled_at    timestamptz,
  created_at     timestamptz NOT NULL DEFAULT now(),
  updated_at     timestamptz NOT NULL DEFAULT now(),
  UNIQUE (workspace_id, username)
);

-- C5：全库唯一主理人。不是"业务上应该只有一个"，是数据库不允许多个。
CREATE UNIQUE INDEX app_user_one_owner
  ON app_user (workspace_id) WHERE role = 'OWNER';

-- 主理人不可被停用
ALTER TABLE app_user ADD CONSTRAINT app_user_owner_not_disabled
  CHECK (role <> 'OWNER' OR disabled_at IS NULL);

CREATE TABLE app_user_session (
  id          text PRIMARY KEY,               -- 随机 token 的哈希
  user_id     bigint NOT NULL REFERENCES app_user(id) ON DELETE CASCADE,
  created_at  timestamptz NOT NULL DEFAULT now(),
  expires_at  timestamptz NOT NULL,
  revoked_at  timestamptz
);

CREATE TABLE invite (
  id           bigserial PRIMARY KEY,
  workspace_id uuid NOT NULL REFERENCES workspace(id),
  token_hash   text NOT NULL UNIQUE,          -- 明文 token 只在生成时返回一次
  role         text NOT NULL CHECK (role IN ('ADMIN','REQUESTER')),
  created_by   bigint NOT NULL REFERENCES app_user(id),
  expires_at   timestamptz NOT NULL,
  consumed_at  timestamptz,
  consumed_by  bigint REFERENCES app_user(id)
);

-- 主理人的两个开关（交接稿第 3 节）。默认都开。
CREATE TABLE workspace_setting (
  workspace_id           uuid PRIMARY KEY REFERENCES workspace(id),
  requester_can_browse   boolean NOT NULL DEFAULT true,
  requester_can_request  boolean NOT NULL DEFAULT true,
  updated_at             timestamptz NOT NULL DEFAULT now(),
  -- 权限开关的变更是主理人级别的操作，"到哪一天被谁改了"要能答。
  -- 只加 updated_by 而不是建一张变更历史表：开关只有两个、只有一个角色能改，
  -- 记"最后是谁改的"足够裁掉"我没关过"这类争议（见 10.7）。
  updated_by             bigint REFERENCES app_user(id)
);

-- ---------- 分类与器材 ----------
CREATE TABLE category (
  id            bigserial PRIMARY KEY,
  workspace_id  uuid NOT NULL REFERENCES workspace(id),
  name          text NOT NULL,
  code_prefix   text NOT NULL CHECK (code_prefix ~ '^[A-Z0-9]{1,5}$'),
  next_seq      integer NOT NULL DEFAULT 1,   -- 编号分配器，见 3.5
  -- 可用性是派生的（见 3.7）：以下两项只是"显式覆盖"与"新分类默认可选"
  pinned        boolean NOT NULL DEFAULT true,
  disabled_at   timestamptz,
  created_at    timestamptz NOT NULL DEFAULT now(),

  CONSTRAINT category_name_uniq   UNIQUE (workspace_id, name),
  CONSTRAINT category_prefix_uniq UNIQUE (workspace_id, code_prefix),
  -- 复合外键的目标：让 equipment 能用 (workspace_id, category_id) 一起约束（见 3.6）
  CONSTRAINT category_ws_id_uniq  UNIQUE (workspace_id, id)
);

CREATE TABLE photo (
  id             bigserial PRIMARY KEY,
  workspace_id   uuid NOT NULL REFERENCES workspace(id),
  sha256         text NOT NULL,
  rel_path       text NOT NULL,               -- 'ab/cd/abcd….jpg'，绝不存绝对路径
  width          integer NOT NULL,
  height         integer NOT NULL,
  bytes          bigint  NOT NULL,
  original_name  text,
  uploaded_at    timestamptz NOT NULL DEFAULT now(),
  UNIQUE (workspace_id, sha256)
);

CREATE TABLE equipment (
  id              bigserial PRIMARY KEY,
  workspace_id    uuid NOT NULL,
  code            text NOT NULL,              -- CAM-001，生成后永不改变
  name            text NOT NULL,
  category_id     bigint NOT NULL,
  brand           text,
  model           text,
  serial_number   text,
  location        text,
  purchase_date   date,
  price_cents     bigint,                     -- 整数分，不用浮点
  internal_note   text,
  photo_id        bigint REFERENCES photo(id) ON DELETE RESTRICT,
  status          text NOT NULL DEFAULT 'IN_STOCK'
                    CHECK (status IN ('IN_STOCK','CHECKED_OUT','MAINTENANCE','DISABLED','SOLD')),
  archived_at     timestamptz,                -- 与 SOLD 是两件事，见 3.4
  created_at      timestamptz NOT NULL DEFAULT now(),
  updated_at      timestamptz NOT NULL DEFAULT now(),

  CONSTRAINT equipment_code_uniq UNIQUE (workspace_id, code),

  -- 复合外键：见 3.6「workspace_id 一致性」。单列外键会让
  -- equipment.category_id 指向另一个工作区的分类。
  CONSTRAINT equipment_workspace_fk  FOREIGN KEY (workspace_id) REFERENCES workspace(id),
  CONSTRAINT equipment_category_fk   FOREIGN KEY (workspace_id, category_id)
    REFERENCES category(workspace_id, id) ON DELETE RESTRICT
);
```

> **注意 `category_id` 这一处的外键形状变了**：它不再是 `REFERENCES category(id)`，而是**复合外键**指向 `category(workspace_id, id)`。这要求 `category` 上有一个 `UNIQUE (workspace_id, id)`（见 3.6）。理由与代价见 3.6——这是本设计里唯一一处为了工作区隔离而增加的复杂度。

```sql
CREATE INDEX equipment_list_idx ON equipment (workspace_id, created_at DESC, id DESC)

CREATE INDEX equipment_status_idx ON equipment (workspace_id, status) WHERE archived_at IS NULL;
-- 3.7 的"可用分类"查询靠这个索引（EXISTS 子查询）
```

```sql
-- ---------- 项目 ----------
CREATE TABLE project (
  id             bigserial PRIMARY KEY,
  workspace_id   uuid NOT NULL REFERENCES workspace(id),
  name           text NOT NULL,
  client         text,
  project_type   text NOT NULL CHECK (project_type IN
                   ('PROMO','SHORT_FILM','TVC','EVENT','CAMPUS','OTHER')),
  start_date     date,
  end_date       date,
  status         text NOT NULL DEFAULT 'ACTIVE'
                   CHECK (status IN ('ACTIVE','COMPLETED','ARCHIVED')),
  note           text,
  created_at     timestamptz NOT NULL DEFAULT now(),
  updated_at     timestamptz NOT NULL DEFAULT now(),

  CONSTRAINT project_name_uniq UNIQUE (workspace_id, name),
  -- 与 request / checkout 同类的日期区间约束。project 原先漏了这一条，
  -- 是唯一一张有起止日期却没有区间校验的表。
  CONSTRAINT project_date_range_check CHECK (end_date IS NULL OR start_date IS NULL
                                             OR end_date >= start_date)

```

> 交接稿第 11 节指出项目类型是硬编码下拉。本设计把它建成受约束的枚举并在前端映射标签，代价是新增类型要发一次后端。**若产品要可自定义，改为表 + 外键**（第 13.4 节）。

```sql
-- ---------- 申请 ----------
CREATE TABLE request (
  id            bigserial PRIMARY KEY,
  workspace_id  uuid NOT NULL REFERENCES workspace(id),
  requester_id  bigint NOT NULL REFERENCES app_user(id),
  project_name  text NOT NULL,               -- 提交时的自由文本，批准/交付时关联 project
  project_id    bigint REFERENCES project(id),
  use_start     date NOT NULL,
  use_end       date NOT NULL,
  note          text,
  status        text NOT NULL DEFAULT 'PENDING' CHECK (status IN
                  ('PENDING','APPROVED','PARTIAL','REJECTED','DELIVERED','RETURNED','WITHDRAWN')),
  review_note   text,
  reviewed_by   bigint REFERENCES app_user(id),
  reviewed_at   timestamptz,
  created_at    timestamptz NOT NULL DEFAULT now(),

);

CREATE TABLE request_item (
  id            bigserial PRIMARY KEY,
  -- 注意：不是 ON DELETE CASCADE。撤回申请时 request 行保留（标记 WITHDRAWN），
  -- 而级联删会在任何将来真的删 request 行时静默抹掉整份审批事实（见 3.8）。

  reject_reason text,
```

### 3.4 归档 vs 已出售

交接稿第 4 节的状态机里，「已出售」已经是终点；再叠一个软删除会产生两种语义的"消失"。本设计分开：

| 语义 | 机制 | 用途 |
|---|---|---|
| 东西还在，不出借 | `status = DISABLED` | 交接稿第 4 节的"停用不是删除" |
| 东西没了，正常终局 | `status = SOLD` | 状态机终点 |
| 录错了、重复建档 | `archived_at` 非空 | 纠错 |

规则：**出库中禁止归档**（返回 `DomainError::CheckedOutNotArchivable`，人话"已出库的器材不能归档，请先归还"）；列表默认同时排除已归档与已出售，加一个「显示已出售」筛选即可看回。归档可恢复。

### 3.5 编号分配

交接稿第 5.1 节：编号留空自动生成 `分类前缀-三位序号`。

三条规则：

1. **数值来自 `category.next_seq`，不是 `max(code) + 1`。** 后者在并发的两次建档下会撞车，且删除后序号会被回收复用。
2. **生成后永不改变。** 分类改名、改前缀都不能影响已有器材的编号——历史记录、出库清单、纸质档案都引用它。
3. 序号耗尽（三位到 999）时**继续加宽 `CAM-1000`，不截断不回绕**。`CHECK` 约束只限制前缀格式，不限制序号位数。

分配在事务内完成：

```sql
UPDATE category SET next_seq = next_seq + 1
 WHERE id = $1
RETURNING code_prefix, next_seq - 1 AS seq;
```

#### 容量：不需要担心，但要注意"人读过不过得去"

**编号空间实际上是无界的。** 前缀是 `^[A-Z0-9]{1,5}$`，序号是整数且可以无限加宽，所以**每个分类能容纳的件数没有硬上限**。永久占用编号不会碰到任何容量问题——你不是在管理一个有限池子。

**真正的软上限是人的耐受度。** 编号出现在三个场合，都有长度限制：

| 场合 | 耐受长度 |
|---|---|
| 电话里报 | `CAM-002` 顺口；`CAM-0231` 要重复；`CAM-02317` 基本靠拼写 |
| 贴实物标签 | 6–8 字符刚好 |
| 填进 Excel | 无所谓 |

**3 位撑到 999 是舒服的，4 位（`CAM-0001`）也还行，到 5 位该归一化。**

⚠️ **需要在实现前确认一件事**：是否**每个分类**都不会超过 999 件？最可能的例外是消耗品分类（电池、线材、存储卡）。若有一个分类会超过：

- **建议从一开始统一补到 4 位**（`CAM-0001`），而不是让它按需加宽
- 理由：**宽度漂移本身就是维护负担**。若 `CAM-002` 与 `CAM-1000` 并存，按编号排序会退化成字符串序（`CAM-1000` 排在 `CAM-002` 前），而排序是列表页的既有功能
- 而且改宽度会影响**已打印的标签**，越早决定越好

#### "永久占用"会有什么问题：三个，逐个看

| 问题 | 影响 |
|---|---|
| 编号序列有空洞（`CAM-001, CAM-003, CAM-007`） | **为零。** 空洞不携带信息，而且本来就会出现（有人手填编号就会让自动序列跳号） |
| `next_seq` 不回退 | **这是正确的行为**，不是问题。它只增不减，所以天然不会复用——**默认行为就是对的**，不需要为"永久占用"做任何额外的事 |
| 人想"用回"一个编号时会困惑 | **唯一的真实成本**，见下 |

**第三种的正确处理方式是恢复，不是重编号：**

```
有人把 CAM-034 错误归档了，后来想重新建这条记录。
系统给的新编号是 CAM-118。而他手上的旧标签写着 CAM-034。
```

**正确答案是 `POST /api/v1/equipment/{id}/restore`**——恢复归档，编号仍是 `CAM-034`。归档本来就是可恢复的（3.4），所以"我想用回那个编号"这个需求，绝大多数情况下等价于"恢复它"。

#### 放开编号会破坏"归档可恢复"

**这是"不放开"最硬的理由，比纸质凭证更本质：**

> 如果编号能被新器材接手，那么**"恢复归档"就变得危险了**——你恢复 `CAM-034` 时，可能已经有一个新器材也叫 `CAM-034`。
>
> **放开编号 = 削弱归档的可恢复性。**

3.4 明确写了"归档可恢复"。两条决定在语义上冲突：放开编号等于给归档加了一个隐式的"恢复可能失败"条件。

#### 唯一需要补的一个端点

永久占用唯一会打扰人的地方是**手填编号撞到一个看不见的归档行**：

```
GET /api/v1/equipment/code-available?code=CAM-002
→ { "available": false, "reason": "被 CAM-002 占用（已归档）" }
```

**必须把"已归档"这个原因说出来**——否则用户看到"编号被占用"会一头雾水，因为他在列表里根本看不到那件器材（列表默认排除已归档）。

唯一约束仍然兜住正确性（并发下最终靠它），这个端点只是让失败变得可理解。

`UPDATE` 自带行锁，所以并发的两次分配会排队而不是撞车；`equipment(workspace_id, code)` 的唯一约束是最后一道保险（`23505` → `DomainError::DuplicateCode`）。

手工填写的编号也走同一个唯一约束。**不做"编号格式校验"**——前缀规则只约束自动生成的，用户手填 `CAM-001-备用机` 是合法的。

### 3.6 `workspace_id` 一致性：为什么用复合外键

主稿 D7 决定"`workspace_id` 从第一天进所有表"，交接稿第 11 节那个切不动的下拉是给多工作室留的位。**但 D7 只说了"带上这一列"，没有任何一处约束它一致。**

具体后果：`equipment.category_id` 原本是单列外键 `REFERENCES category(id)`，所以**A 工作区的器材可以挂到 B 工作区的分类上**，数据库不会拦。今天只有一个工作区，这件事不会发生；等真的做多工作区时，它已经是一批脏数据。

**做法**：让 `category` 有一个 `UNIQUE (workspace_id, id)`，然后 `equipment` 用**复合外键**

```sql
FOREIGN KEY (workspace_id, category_id) REFERENCES category(workspace_id, id)
```

这样跨工作区的引用在数据库层不可能成立。

**代价要说清楚**：

| 代价 | 说明 |
|---|---|
| 每张被引用的表都多一个 `UNIQUE (workspace_id, id)` 索引 | `id` 已经是主键，这个索引在单工作区下冗余。几百到几千行的量级下开销可忽略 |
| 引用处的外键必须写成两个列 | 比单列啰嗦，且**迁移时必须先建目标表的复合唯一键**，否则外键建不上 |
| 有 `workspace_id` 的表都要有指向 `workspace(id)` 的外键 | 原先部分表用的是 `REFERENCES workspace(id)` 的行内写法，含义相同，改不改都行 |

**范围**：本稿只在 `equipment.category_id` 这一处落成复合外键（它是唯一一处"跨工作区引用会真的产生错误业务"的地方——分类决定编号前缀，挂错分类会让编号规则错乱）。其余跨表引用（`project`、`equipment`、`request`）的 `workspace_id` 一致性**由服务层保证**：所有写入都从 `Actor.workspace_id` 取值，不接受客户端传入。

> 这是一个**有意的取舍**：把"最危险的一处"做成数据库约束，其余靠"workspace_id 只从会话取"这一条实现纪律。全表复合外键会让每个 join 和每个迁移都变复杂，而本系统的正常路径里 `workspace_id` 根本不来自请求体。

### 3.7 分类：可用性是**派生**的，不是手动维护的

`equipment.category_id` 是 `NOT NULL`，所以"删除分类并置空器材"在 DDL 层面不成立。而"禁止删除有器材的分类"会让分类永远删不掉（历史器材永远存在）。

**先说一个错误方案。** 直觉做法是加一个 `disabled_at`，让人在"不再用这个分类"时手动停用。**这是手动内存管理**：

- 你建了分类、用了一阵、器材都归档了 → **你得记得去停用它**，否则它永远出现在新建器材的下拉里
- 忘了 → 下拉框被死分类填满
- 「谁忘了 disable」和「谁忘了 free」是同一个 bug 的两种长相

**加一个定时任务自动停用也不行**：那会在"分类下所有器材都归档"时把它停用，于是**你恢复那件器材，分类却还是停用的**——能回收，不会复活。

**正确形态：可用性在查询时派生，`disabled_at` 只作显式覆盖。**

> 一个分类"可用于新建器材"当且仅当：**它有至少一件未归档的器材**，或 **管理员显式钉住了它**。

| 场景 | 结果 |
|---|---|
| 新建分类、还没建器材 | `pinned` 默认 true → 出现在下拉里 |
| 分类下的器材全归档了 | **不出现**——派生结果变了，不需要任何人做任何事 |
| 恢复那件归档的器材 | **自动重新出现**——条件是"有未归档器材"，而它现在有了 |
| 管理员想在一个还有器材的分类上禁用它 | `disabled_at` 显式覆盖 |

`disabled_at` 于是从"生命周期管理"降级为"显式覆盖"：**它是那种少见的情况——分类下明明有器材，但你就是不想让新器材再归到它。**

```sql
-- ① 新建器材时的下拉：能用的分类（注意 EXISTS）
SELECT * FROM category c
 WHERE c.workspace_id = $1
   AND c.disabled_at IS NULL
   AND (c.pinned OR EXISTS (
         SELECT 1 FROM equipment e
          WHERE e.category_id = c.id AND e.archived_at IS NULL));

-- ② 器材库的筛选器：所有"出现过器材"的分类（含已停用与已归档）
--    否则你查不到历史器材
SELECT DISTINCT c.* FROM category c
  JOIN equipment e ON e.category_id = c.id
 WHERE c.workspace_id = $1;

-- ③ 历史记录里的分类名解析：无条件 join，不看任何状态
```

**①②的差别是要点**：创建时只给"活的"，筛选时给"出现过的"。这两个集合不同，而且**都不需要维护**。需要 `equipment(category_id)` 上的索引，分类十量级、器材几千量级，开销可忽略。

`ON DELETE RESTRICT` 仍然保留：它是"有人绕过界面直接 DELETE"的兜底。

### 3.7.1 同一个模式在系统里还检查出两处

顺手检查了其它"归档代替删除"与"状态字段"的地方：

| 字段 | 判断 |
|---|---|
| `category.disabled_at` | **已修**：改为派生 + 显式覆盖（本节） |
| `equipment.status` | **保持手动**。它是交接稿第 4 节状态机的字面要求——**是业务事实，不是生命周期**。别为了统一而动它 |
| `project.status` | **保持手动**。`ARCHIVED` 是一个人的决定，不是从器材推出来的事实 |
| `checkout.status = OPEN/CLOSED` | **⚠️ 不一致，见下** |

**`checkout.status` 是同一类问题。** 主稿 5.4 论证过"部分归还不需要建状态字段，由读模型推导"，理由是"**避免两个字段争谁为准**"。但 `checkout.status` 恰恰就是那个会争的字段——它和"`checkout_item` 里还有没有 `returned_at IS NULL` 的行"表达的是同一件事。

按主稿自己对"部分归还"用的同一条逻辑，`checkout.status` 应该被删掉，`OPEN`/`CLOSED` 由逐件归还状态推导。

> **这条尚未改**（列在待拍板清单的 T-03）。现在改只是删一列和它的两处赋值；实现之后改要迁移数据。

### 3.8 级联规则：三处 CASCADE 改成 RESTRICT

原稿 `request_item.request_id` 与 `checkout_item.checkout_id` 都是 `ON DELETE CASCADE`。**这条要推翻**：

> 级联删会在有人删掉一张申请单或出库单时，**静默抹掉整份审批事实或出库事实**。

而第 10.1 节刚把 `equipment_history` 定为"唯一的叙事主线"，10.2 节要求 `changed` 数组保留原值——**级联删与这两条直接冲突**。改成 `RESTRICT` 后，删除会失败而不是静默丢数据。

**唯一保留 `CASCADE` 的是 `app_user_session.user_id`**：会话是派生数据，账号走了会话就该消失，它承载不了任何业务事实。

其余 27 处 `REFERENCES` 原稿都没写 `ON DELETE`，Postgres 默认是 `NO ACTION`（等价于 `RESTRICT` 的拒删，但检查时机略晚）。**全部显式写成 `RESTRICT`**：默认值虽然行为相近，但"没写"和"写了"在 review 时无法区分，而下一个人看到 `ON DELETE CASCADE` 以外什么都不写，会以为作者没想过这件事。

> `NO ACTION` 与 `RESTRICT` 的差别只在**检查时机**（`RESTRICT` 立即拒绝，`NO ACTION` 允许延迟到语句末/事务末），对本系统的用法二者等价。**选 `RESTRICT` 的理由是可读性**：它明确写了意图。

```
xtask/                      # dev-db、gen-api 等一次性命令
```

**`domain` 不依赖 sqlx 和 tokio，这不是洁癖**：它让状态机和可见性规则能在毫秒级跑几百个单测，也让将来真要拆服务时不必重写业务规则。

`domain` 只用 `time::Date` 这种表述业务概念的类型，不出现 `sqlx` 类型、不出现 `PgConnection`。

## 5. 写路径

### 5.1 唯一形状

所有改变器材状态的操作只有一种写法：

```rust
pub async fn checkout(
    pool: &PgPool,
    actor: ActorId,
    cmd: CheckoutCmd,
) -> Result<CheckoutView, AppError> {
    let mut tx = pool.begin().await?;

    // 1. 锁器材行，读当前状态（顺序按 equipment.id，防批量死锁）
    let equipments = db::equipment::lock_many(&mut tx, &cmd.equipment_ids).await?;

    // 2. 过状态机 —— 唯一的合法性判断
    for eq in &equipments {
        domain::state_machine::assert_transition(eq.status, EquipStatus::CheckedOut)?;
        //       ^ 违规返回 DomainError::IllegalTransition { from, to }
    }

    // 3. 占用检查（给人话）+ 插入（正确性由排他约束兜底）
    let during = domain::occupancy::checkout_range(cmd.checkout_date, cmd.expected_date);
    for eq in &equipments {
        if let Some(c) = db::occupancy::find_conflict(&mut tx, eq.id, during, None).await? {
            return Err(DomainError::Reserved { /* 点名是哪件、被哪个项目占 */ }.into());
        }
        db::occupancy::insert(&mut tx, eq.id, during, OccupancyKind::Checkout, ...).await?;
    }

    // 4. 写 checkout / checkout_item
    // 5. 改状态
    db::equipment::set_status(&mut tx, &ids, EquipStatus::CheckedOut).await?;
    // 6. 同事务写 history（交接稿第 4 节最后一条）
    db::history::write_many(&mut tx, actor, HistoryAction::Checkout, &equipments).await?;

    tx.commit().await?;
    // ...
}
```

**规则：领域/服务函数收 `&mut PgConnection`，不收 `&PgPool`。** `Transaction` 解引用就得到它。这样"状态变更 + 写历史必须同事务"由类型强制，而不是靠约定——交接稿第 4 节最后一条不需要靠纪律维持。

### 5.2 锁

`occupancy` 的排他约束已经保证并发安全，所以**主路径不需要 `SELECT ... FOR UPDATE`**。只有两处要显式锁：

1. **批量操作按 `equipment.id` 升序取锁**，否则两个批量事务可能互锁。
2. `category.next_seq` 的 `UPDATE`（自带行锁，见 3.5）。

少用锁比多用好：锁的排序规则一旦漏了，得到的死锁比不用锁更难查。

### 5.3 批量的全有或全无

交接稿第 4 节：批量删除时若混了出库中的器材，整批拒绝并点名是哪几件，不做部分成功。

实现：**一个事务，不设 savepoint。** 先在步骤 2 把所有违规件收集齐再返回，让用户一次看到全部问题：

```rust
let violations: Vec<_> = equipments.iter()
    .filter_map(|e| domain::state_machine::check(e.status, target).err())
    .collect();
if !violations.is_empty() {
    return Err(DomainError::BatchRejected { items: violations }.into());
}
```

错误体的 `message` 是"以下器材不能删除（出库中）：CAM-003、CAM-011"。

### 5.4 归还

逐件归还（交接稿第 5.3 节：一件一条记录）。单件归还 = 一个事务：

1. 锁该 `checkout_item` 与 `equipment` 行
2. `checkout_item.returned_at = now()`，`return_note` 落库
3. `DELETE occupancy WHERE equipment_id = $1 AND source_checkout_id = $2`
4. `equipment.status = IN_STOCK`
5. 写 history
6. 若该 `checkout` 全部 item 已归还 → `checkout.status = CLOSED`
7. 若 `checkout.source_request_id` 非空 → 更新对应 `request_item.returned_at`；若该申请全部 item 已归还 → `request.status = RETURNED`（交接稿第 5.3 节"全部还完，申请单自动结案"）

**"部分归还"不需要建状态。** 交接稿第 10 节说没做部分归还；在本模型里它是读模型的事——申请单状态仍是 `DELIVERED`，只要 `request_item` 里还有 `returned_at IS NULL` 的行，界面就该显示"部分归还中"。加一个状态字段反而会引入"到底哪个字段为准"的问题。

### 5.5 字段编辑的并发：不设锁

器材的**描述性字段**（名称、品牌、型号、序列号、存放位置、内部备注、价格、购买日期）会被管理员通过编辑弹窗修改。这一节定的是这类编辑的并发语义。

**结论：不设编辑锁，不做在线状态，不做协同合并。** 编辑是一次原子提交（读-改-写），后写覆盖，变更写进历史留痕。

#### 为什么不做

两个管理员同时编辑同一条记录的场景规模决定了做法。本系统的实际使用者是**十人以内的单工作室**，其中会编辑同一条器材记录的是 **2～3 人**，且编辑发生在现场（手机、弹窗、填两格、保存），不是长时间驻留的编辑会话。

在这个规模下，任何并发编辑机制的收益都很小，而它们各自都有真实代价：

| 方案 | 代价 | 结论 |
|---|---|---|
| 编辑锁（别人在改就不能打开） | 浏览器崩溃、关标签页、断网都会把人挡在门外，要引入 TTL、续期、接管、保存时二次校验 | 不做 |
| 在线状态（显示谁在改） | 一张 `presence` 表 + 客户端心跳 + 轮询下发 | 不做。2～3 人的场景下，看到同事在改的概率极低，而"我改了别人也改了"可以被历史记录兜住 |
| 字段级冲突检测（改到同一字段才拒绝 409） | 要接收客户端基线状态、做三方比较、界面要给冲突选择界面 | 不做。**若将来出现真实的静默覆盖事故，这是第一个该加的东西**（见下方"如果将来要加"） |
| CRDT / 实时协同 | 一个有状态的同步服务、一套同步协议、离线补偿、schema 逐文档迁移、压测与收敛性测试 | 明确不做。字符级合并只对"多人在同一段长文本上迭代"有价值，本系统只有内部备注一个长文本字段，且几乎不会并发 |
| 乐观并发（`version` + `If-Match`，整个表单拒绝） | 甲改名称、乙改价格也会互相挡 | 不做。它挡住了不该挡的编辑 |

**注意这里要区分两类"并发"，它们的处理方式完全不同：**

| | 是什么 | 谁需要 | 例子 |
|---|---|---|---|
| **编辑冲突** | 两个人改同一条记录的描述性字段 | **本系统不处理**（原子提交，后写覆盖） | 甲把型号改成 `FX3`，乙改成 `ILME-FX3` |
| **状态流转竞争** | 两个人并发触发同一个状态变更 | **必须处理**（5.1 第 1 步的 `lock_many`） | 两个人同时点「确认出库」 |
| **档期占用竞争** | 两个人要同一件器材的同一段时间 | **必须处理**（第 3 节的排他约束） | 申请批了 CAM-003 的 10-01～10-05，别人要出库它 |

第二行如果不锁行，两个事务都会读到 `IN_STOCK`、都通过状态机、各写一条出库记录。**规则：锁的用途是"一个业务事件只能发生一次"，不是"一个字段只能一个人改"。** 前者是正确性，后者在本系统的规模下不存在。

#### 留痕：复用 `equipment_history`，不新增表

交接稿第 4 节要求"每一步都留痕，谁也赖不掉"。现场最容易出现的争议是有人不承认自己改过价格或序列号，所以字段变更必须可查。

做法是给已有的 `equipment_history` 加一个 `UPDATE` 动作，把变更的字段放进已有的 `detail jsonb`：

```json
{ "action": "UPDATE",
  "detail": { "changed": [
    { "field": "price_cents",   "from": 980000, "to": 1280000 },
    { "field": "serial_number", "from": null,   "to": "SN-4471" }
  ] } }
```

一行记录，不新增表、不新增查询路径，历史列表照常渲染（交接稿第 6 节"近 5 条"）。

**是否只记敏感字段**（价格、序列号、状态）：只记敏感字段能减少历史噪音，但会让"我改的名称哪去了"没有答案。**决定是全记**，噪音在界面层解决（历史列表默认折叠连续的 `UPDATE` 记录）。理由是同一个机制覆盖两种情况，不值得为"值不值得记"再写一套判断。

#### 长文本（内部备注）

**和短字段一样，不加特殊处理。** 不需要自动保存、不需要防抖、不需要冲突提示——因为它就是编辑表单里的一个字段，跟着表单一起提交。

唯一值得记住的一点：**如果将来内部备注变得很长且被频繁编辑**，第一个该加的是"自动保存 + 三方合并"（下面那条），而不是 CRDT。

#### 如果将来要加

出现真实的静默覆盖事故时（有人报"我改的东西不见了"），按这个顺序加，不要跳步：

1. **加字段级冲突检测**：客户端提交时带上打开表单时的基线（`version` 或基线的字段快照），服务端对比"我改的字段"与"基线之后被改的字段"。**只有交集才返回 409**，并把两个值都给用户看。这样甲改名称、乙改价格两者都保住，只有真正改到同一个字段才需要人判断。这一条的成本是：`equipment` 加一个 `version` 列、详情接口下发它、编辑接口校验它、界面加一个冲突选择态。
2. 若第 1 步的 409 出现得太频繁，再加**在线状态**（`presence` 表 + 心跳 + 轮询），让人在编辑前就避开。
3. **只有在多人需要同时修改同一段长文本时**，才考虑协同合并。到那一步再评估 CRDT 与独立同步服务；本稿的结论是这一步在当前产品里不需要。

在加第 1 步之前，静默覆盖的实际后果是"某个字段回到了另一个人的值"——它**不会损坏数据、不会破坏状态机、不会造成档期冲突**，而且历史记录里有完整的 `changed` 数组可以人工恢复。这是决定"先不做"的量化依据。

## 6. 文件系统

### 6.1 范围

**存：器材照片。** 交接稿第 5.1 节明确有照片入口，详情弹窗有大图，列表有缩图。

**不存：** CSV 导入的原文件（解析完即弃）、出库清单 PDF（按需生成直接吐给浏览器）、签字件（当前设计是纸质签名，纸质件即原件——若产品要留扫描件，见第 13.3 节）。

规模：几百到几千张，每张压到长边 1600 后 300–800 KB，合计几百 MB。

### 6.2 布局：内容寻址 + 两层分片

```
$LENSMAX_DATA/
  photos/
    ab/cd/abcd1234…ef.jpg          # 原图（客户端已压到长边 1600）
    ab/cd/abcd1234…ef.thumb.jpg    # 缩图（长边 320）
  tmp/                             # 写入中转，必须与 photos 同一文件系统
```

路径 = 内容的 SHA-256。这一条决定顺带解决四件事：

| 问题 | 为什么自动解决 |
|---|---|
| 手机重传同一张 | 路径相同，写之前发现存在就跳过。幂等，不需要去重逻辑 |
| 路径穿越 | 路径里没有用户输入，原始文件名从不参与路径计算 |
| 缓存失效 | URL 即内容，`Cache-Control: public, max-age=31536000, immutable` 永久有效 |
| 换图后的旧图 | 旧 blob 不可变，历史记录仍能引用，不会变死链 |

原文件名（`IMG_4821.JPG`）只存库当展示用。

### 6.3 上传流程

```
POST /api/photos   (multipart/form-data)
 1. 收流时限制大小（8 MB 上限）并校验 JPEG 魔数            ← 不信任 Content-Type
 2. 边收边算 sha256
 3. 目标已存在 → 直接返回引用，不做任何写                   ← 幂等
 4. 写 tmp/tmp-{uuid}.jpg → fsync 文件 → fsync 父目录
    → rename 到 photos/ab/cd/{hash}.jpg                    ← 原子
 5. spawn_blocking：解码（限制像素上限 8000×8000）、按 EXIF 摆正、
    缩到 320 编码 → 同一个 tmp+rename 流程，得到 .thumb.jpg
 6. 两个文件都就位后，写 photo 行 + pending_upload 行
```

三个必须做对的细节：

**原图字节直接落盘，不做完整解码。** 客户端已经压到 1600 px，服务端再解一遍没有收益。**解码只发生在生成缩图那一步，且必须限制解码后的像素上限**——否则一张 10 KB 的"解压炸弹"能让进程 OOM。这是这条流水线上唯一的真实攻击面。

**EXIF 方向必须在缩图那一步处理掉。** 手机竖拍的照片文件本身是横的，靠 EXIF 标记旋转。原图保留 EXIF 无所谓，但缩图若不摆正，器材库列表里全是躺着的器材照片。这是手机上传必然会踩的坑。

**上传与器材保存是两个请求。** 这符合交接稿第 5.1 节的动线（先拍照，再填名称分类，最后保存），也让"传了照片但表单没提交"变成一个可由定时任务清理的正常状态，而不是需要回滚的异常。`pending_upload` 表就是为这个窗口存在的。

### 6.4 数据库里存什么

存**相对路径**，不存绝对路径、不存 URL：

```
photo: { rel_path: "ab/cd/abcd….jpg", sha256: "abcd…", width: 1600, height: 1200,
         bytes: 438221, original_name: "IMG_4821.JPG", uploaded_at: … }
```

URL 由 API 层按环境拼（`{PHOTO_BASE_URL}/{rel_path}`）。这样同一个库能对着本地盘或对象存储，换存储不动数据。

返回给前端的是**结构化引用**，不是裸字符串：

```json
{ "id": "77", "url": "https://…/ab/cd/….jpg", "thumbUrl": "https://…/ab/cd/….thumb.jpg",
  "width": 1600, "height": 1200, "sha256": "abcd…", "originalName": "IMG_4821.JPG" }
```

详情弹窗要原图、列表要缩图、宽高用来占位防列表跳动。这些信息一旦在接口上丢失就得靠猜。

### 6.5 清理：只清孤儿，绝不在请求路径上删

换图时不删旧文件（可能被历史引用）。用**标记清除**，低频跑（每周）：

1. 扫描 `photos/` 下所有 hash
2. 减去数据库中被引用的 hash 集合（`photo` 表）
3. 再减去 `pending_upload` 里 24 小时内的记录
4. 剩下的删掉，日志记录删除数量

**绝不在请求路径上删文件。** 一次误删是永久数据损失，一次没删只是占几百 KB。

### 6.6 谁把文件发给浏览器

**Caddy 直接发。** 照片 URL 是内容地址、永久可缓存；且按交接稿第 3 节的权限矩阵，器材照片对三种角色都可见——所以静态发**不需要鉴权**。

```
handle_path /photos/* {
  root * {$LENSMAX_DATA}/photos
  file_server
  header Cache-Control "public, max-age=31536000, immutable"
}
```

把二进制从 Axum 挪出去省掉一次应用层拷贝和一次 tokio 任务占用。**唯一要避免的错**是在静态路径前面挂会话检查——那会毁掉所有缓存收益。

若将来照片需要分角色可见，改为签名 URL 或走 Axum 转发。当前不需要。

### 6.7 格式约束

**服务端只接受 JPEG。** 前端走 canvas → `toBlob('image/jpeg')`，导出必然是 JPEG；PNG 只在允许截图直传时收。

**待验证**：iPhone Safari 下 `<input type="file" accept="image/*" capture>` 有时提供 **HEIC**。若前端压缩那一步确实是 canvas 重编码，则不是问题；若存在直接上传原文件的路径，服务端会收到解不了的 HEIC。立场是**前端统一转 JPEG**，而不是服务端引入 HEIC 解码器（额外依赖 + 专利问题）。

## 7. 网络与序列化

### 7.1 三条总原则

1. **线上跑的是稳定代码，不是中文。** 枚举传 `IN_STOCK`，中文标签由前端映射。交接稿第 11 节的术语尚未定（"出库"vs"借出"），标签不该烧进接口。
2. **服务端决定"能做什么"，客户端不推导。** 状态合法性（第 4 节的状态机）与角色权限（第 3 节的矩阵）都由服务端算好，放在 `actions` 里下发。
3. **看不见的字段用"不存在"表达，不用 `null`。** 若申请人的 payload 里出现 `"purchasePriceCents": null`，那就是泄漏了该字段的存在。

### 7.2 类型约定

| 类别 | 约定 | 理由 |
|---|---|---|
| 字段名 | 全 DTO `#[serde(rename_all = "camelCase")]` | 迁就既有前端 |
| 业务日期 | `"2026-10-01"`，不带时间不带时区 | 出库日期/预计归还就是日历日。带时区必然产生"10-01 到底算哪天"的争论 |
| 审计时间 | RFC 3339 带偏移 | 库列是 `timestamptz`，传的是瞬时 |
| ID | **字符串**（`"1284"`），语义上不可运算 | 前端不写 `id + 1`；将来换 UUID/复合键不破坏契约 |
| 金额 | **整数分** `priceCents: 128000` | 台账的钱不碰浮点。前端除以 100 显示 |
| 枚举 | `SCREAMING_SNAKE` | 稳定，与展示解耦 |

推论：交接稿第 8 节"状态永远颜色 + 文字"的**颜色和文字都不该由后端下发**。后端只说 `IN_STOCK`。若将来要在服务端渲染逾期提醒邮件，再单独加一份标签表，不要为此把中文塞进主接口。

### 7.3 错误信封

每个非 2xx 都是同一个形状：

```json
{ "error": {
    "code": "ILLEGAL_TRANSITION",
    "message": "不能从“维修”改为“出库”",
    "field": null,
    "requestId": "01J8Z…"
} }
```

- `message` 直接进交接稿第 7 节那条表单内红条（字段级错误不消失）。
- `field` 供表单定位到输入框。
- `requestId` 进日志，用户截图时能对上。

状态码按语义分，不全用 400：

| 情况 | 码 |
|---|---|
| 校验失败（缺项目名称、日期区间反了） | 400 |
| **数据库 `CHECK` 被用户输入触发（`23514`）** | **400**（不是 500，见 8.1） |
| 未登录 / 会话失效 | 401 |
| 角色不允许（申请人访问全库历史） | 403 |
| **被工作区开关拦住（关掉浏览）** | **403** `BROWSING_DISABLED` |
| 不存在或已归档 | 404 |
| **档期冲突 `23P01`** | **409** |
| **外键被引用（`23503`，删不掉）** | **409** |
| **状态流转非法** | **422** |
| **被工作区开关拦住（关掉申请）** | **422** `REQUESTING_DISABLED` |
| **重试耗尽 / 查询超时（`57014`、`25P03`、`PoolTimedOut`）** | **503** + `Retry-After: 1` |
| 数据库不可用 | **503**（不是 500，见运行时篇 R7.1） |
| 限流 | 429（**本设计目前没有限流**，这一格先留着；`T-02` 式的"不留没实现的码"倾向应删掉它） |

分开 409 和 422 有用：前端对 409 提示"换日期或换器材"，对 422 提示"先归还"。

**503 与 500 的分界是有意的**：503 表示"稍后重试可能成功"，前端据此显示"系统繁忙，请稍后重试"；500 表示"出错了"，前端显示"出错了，请联系管理员"并带上 `requestId`。把前者报成 500 会让用户做错下一步动作。

### 7.4 `actions`：把状态机判断推到服务端

不要把 `status` 丢给前端让它自己算按钮：

```json
{
  "id": "1284", "code": "CAM-003", "name": "Sony FX3", "status": "CHECKED_OUT",
  "isOverdue": true,
  "actions": [
    { "key": "return",      "enabled": true,  "reason": null },
    { "key": "edit",        "enabled": false, "reason": "出库中的器材不能编辑" },
    { "key": "maintenance", "enabled": false, "reason": "先归还" }
  ]
}
```

一个数组同时承载**状态机允许什么**（交接稿第 4 节）和**这个角色允许什么**（第 3 节）。前端只负责画——第 7 节那句"按钮禁用带原因（title 说明为什么不能点）"直接就是 `reason` 字段，不需要前端各处硬编码中文理由。

`isOverdue` 也由服务端算：超期是"今天 > 预计归还 且状态仍为出库"，是随时钟变化的判断，客户端与服务端时钟不一致时以服务端为准。

### 7.5 列表：游标分页

```
GET /api/equipment?q=fx3&category=CAM&status=IN_STOCK&sort=recent&cursor=…&limit=50
→ { "items": [...], "nextCursor": "eyJ…" }
```

不用 offset。理由不是性能而是**正确性**：器材库持续有人出库归还，offset 分页会在翻页时漏掉或重复行。游标基于 `(created_at, id)` 或 `(code)`，`limit` 上限 100。

搜索覆盖名称/编号/品牌/型号/序列号（交接稿第 6 节）。四个筛选器（分类、状态、品牌、排序）走 `QueryBuilder` 动态拼接。**注意**：`QueryBuilder` 的每个片段都必须是编译期常量字符串，用户输入只走 `.bind()`——这是拼接类代码最常见的注入点。

### 7.6 写入形状

**PATCH 要能区分"不改"和"清空"**，因为交接稿第 5.1 节说除名称分类外其余都可留空：

```rust
#[serde(default, skip_serializing_if = "Option::is_none")]
pub purchase_date: Option<Option<Date>>,
```

```json
{}                                // 不动
{ "purchaseDate": null }          // 清空
{ "purchaseDate": "2024-03-01" }  // 设置
```

不用三态的话，用户永远没法把一个填错的购买日期改回空。

**变更返回更新后的资源，不返回 `{"ok": true}`。** 第 5.1 节"保存后直接进详情页"、第 5.2 节"批量出库后生成清单"——返回新对象就不用再来一次 GET，弱网下少一个来回。

### 7.7 可见性：两个结构体，不是一个过滤函数

```rust
#[derive(Serialize)] #[serde(rename_all = "camelCase")]
pub struct EquipmentRequester {
    id, code, name, category, brand, model, status, location, photo, actions
}

#[derive(Serialize)] #[serde(rename_all = "camelCase")]
pub struct EquipmentAdmin {
    /* 上面全部 + purchasePriceCents, purchaseDate, serialNumber,
       internalNote, createdAt, updatedAt */
}
```

两条纪律：

1. **被禁字段一律不出现**（不加 `Option`、不输出 `null`）。类型不同，编译器保证"忘了删"不会发生。
2. **不用 `skip_serializing_if` 做权限。** 那个属性的语义是"可选"，用来表达"禁止"以后没人分得清"这是空的还是我看不到"。权限用不同类型，可选性用属性——两件事不混。

配套契约测试：用申请人身份打每一个读接口，断言返回 JSON 的 key 集合 ⊆ 白名单。类型系统管"忘了搬"，这条测试管"契约漂移"。加字段时它会红。

### 7.8 两条越权路径

交接稿第 3 节的规则在服务端有两处必须专门守：

| 路径 | 风险 | 处理 |
|---|---|---|
| **出库交接清单**（第 5.2 节） | 清单含序列号，而签字人可能是看不到序列号的申请人 | 清单内容从专用接口取：`GET /api/checkouts/{id}/manifest`，返回打印专用 DTO，角色守卫收在这一个 handler 里。**不允许前端拿器材列表 DTO 拼清单** |
| **数据导出备份**（第 6 节） | 是原始导出还是按角色裁剪？ | 需产品决定（第 13.2 节）。默认：**仅 OWNER/ADMIN，原始导出**，且在导出文件里写入导出人、时间、范围 |

### 7.9 传输层

- JSON 响应开 gzip/brotli（在 Caddy 上开）。器材列表是高度重复的 JSON，压缩收益大。
- **图片不压缩**，且明确给出 `Content-Length`，让客户端能显示进度（弱网下直接影响上传成功率）。
- 列表接口的响应体上限显式设定。第 5.1 节的 CSV 导入上限 1000 件、预览只回前 12 行——不要让"导入预览"把 1000 行全推给前端。

## 8. 错误处理

领域层返回类型化错误，API 层集中翻译一次：

```rust
#[derive(Debug, thiserror::Error)]
pub enum DomainError {
    // —— 状态与流程 ——
    #[error("不能从“{from}”改为“{to}”")]
    IllegalTransition { from: EquipStatus, to: EquipStatus },
    #[error("以下器材不能处理（{reason}）：{items}")]
    BatchRejected { reason: &'static str, items: String },
    #[error("已出库的器材不能归档，请先归还")]
    CheckedOutNotArchivable,
    #[error("这件器材还有未关闭的维修记录，请先完成维修")]
    OpenMaintenanceExists,

    // —— 档期 ——
    #[error("已被「{project}」在 {start} 至 {end} 占用")]
    Reserved { project: String, start: Date, end: Date },
    /// 排他约束 `23P01` 被触发但查不出冲突方（并发极端情况）。
    /// 正常路径应该由 `Reserved` 承载，因为预检查会先拿到明细。
    #[error("这件器材在该时段已被占用，请换日期或换器材")]
    Conflict,

    // —— 数据完整性 ——
    #[error("编号已存在：{code}")]
    DuplicateCode { code: String },
    #[error("编号已被占用，请换一个")]
    DuplicateCodeUnknown,
    #[error("这个用户名已被使用")]
    DuplicateUserName,
    #[error("{entity}正在被引用，不能删除")]
    ReferenceInUse { entity: &'static str },
    /// `CHECK` 约束被用户输入触发（`23514`）。
    /// **必须走 400 而不是 500** —— 填错一个字段不是服务器错误。
    #[error("{message}")]
    InvalidField { field: &'static str, message: &'static str },

    // —— 账号与权限 ——
    #[error("主理人的权限不能被修改")]
    OwnerImmutable,
    #[error("主理人不能被停用")]
    OwnerNotDisableable,
    #[error("暂未开放申请权限")]
    RequestingDisabled,
    #[error("暂未开放器材浏览")]
    BrowsingDisabled,

    // —— 可用性 ——
    #[error("系统繁忙，请稍后重试")]
    TemporaryUnavailable,
}
```

> **`DuplicateCode { code }` 在翻译点是拿不到编号的**（`From<sqlx::Error>` 没有业务上下文）。所以另有一个 `DuplicateCodeUnknown` 承载"约束拦住了但我不知道是哪个编号"，**由服务层在捕获后补查编号、换成 `DuplicateCode { code }`**。若补查失败（比如并发下已被删），才把 `DuplicateCodeUnknown` 交给用户——它的文案是完整的，不会出现"编号已存在："这种半句话。

### 8.1 约束违例的翻译：按 SQLSTATE 分类

**这是全会话里最容易漏的一段。** 原稿只处理了 `23P01` 和 `23505`，而**能被用户输入直接触发的约束有五大类**：

```rust
/// 五类完整性违例。`23P01` 与 `23505` 之外的三个原稿没有处理，
/// 它们会让"用户填错一个字段"变成 500。
fn translate_constraint(db: &dyn sqlx::DatabaseError) -> Option<DomainError> {
    match db.code().as_deref()? {
        // 排他约束：档期冲突
        "23P01" => Some(DomainError::Conflict),

        // 唯一约束：逐条 discriminate
        "23505" => match db.constraint() {
            Some("equipment_code_uniq") => Some(DomainError::DuplicateCodeUnknown),
            Some("category_name_uniq") | Some("category_prefix_uniq")
                => Some(DomainError::DuplicateCodeUnknown),
            Some("app_user_one_owner") => Some(DomainError::OwnerImmutable),
            Some("app_user_username_uniq") => Some(DomainError::DuplicateUserName),
            Some("maintenance_one_open") => Some(DomainError::OpenMaintenanceExists),
            Some("project_name_uniq") => Some(DomainError::DuplicateCodeUnknown),
            _ => None,   // 落到 500，但要记 error 日志：见下
        },

        // CHECK 约束：用户输入触发的字段级错误 → 400，不是 500
        "23514" => match db.constraint() {
            Some("category_code_prefix_check")
                => Some(DomainError::InvalidField { field: "code_prefix",
                     message: "前缀只能是大写字母和数字，最多 5 位" }),
            Some("request_use_end_check")
                => Some(DomainError::InvalidField { field: "use_end",
                     message: "预计归还不能早于使用开始" }),
            Some("checkout_expected_date_check")
                => Some(DomainError::InvalidField { field: "expected_date",
                     message: "预计归还不能早于出库日期" }),
            Some("project_date_range_check")
                => Some(DomainError::InvalidField { field: "end_date",
                     message: "结束日期不能早于开始日期" }),
            Some("app_user_owner_not_disabled") => Some(DomainError::OwnerNotDisableable),
            Some("maintenance_outcome_check")
                => Some(DomainError::InvalidField { field: "outcome",
                     message: "维修结果只能是恢复在库或转停用" }),
            _ => None,
        },

        // 外键：被引用的行不存在或仍被引用
        "23503" => Some(DomainError::ReferenceInUse { entity: "该记录" }),

        _ => None,
    }
}
```

**为什么不把它放进 `impl From<sqlx::Error>`**：`From` 无法携带业务上下文（哪个字段、哪条记录），而上面每一条都需要。**做法是 `From` 只保留最粗的一层**（够用的场合直接翻），需要上下文的在服务层调用 `translate_constraint` 并补齐信息。这比在 `From` 里塞一个"上下文登记表"简单得多。

**`CHECK` 违例走 400 而不是 500，这条有实际后果**：分类前缀填小写 `cam` 是**用户会真的犯的错**，给它 500 意味着用户看到"服务器错误"而不是"前缀只能是大写字母和数字"。而 500 还会污染错误率指标（运行时篇 R1.4）。

**没匹配上的约束一律落到 500，但必须记日志。** 未匹配意味着"有一条约束我没翻译"——那是一个需要补代码的信号，不是可以静默的常规情况。日志里要带 `db.constraint()` 的值，否则你只知道"有个 500"，不知道是哪条约束。

### 8.2 重试与状态码

**`23P01` / `23505` / `23514` / `23503` 一律不可重试**：重试必然再失败，而且会把一个 409 变成一个 503——**前端据此把"换日期或换器材"变成"稍后重试"，用户的下一步动作被改错了。**

可重试的只有"整笔事务确实没生效"的错误，详细分类、退避参数与 `commit()` 阶段不重试的理由见 [实现契约](20260930_IMPL_CONTRACT_v1.md) §4。

主稿 7.3 的状态码矩阵最后一行原文是 `限流 / 事务重试耗尽 → 429 / 503`，**要拆开**：`429` 保持"限流"原义（本设计目前没有限流，这一格先留着），**重试耗尽用 `503` + `Retry-After: 1`**。

### 8.3 显式命名，不依赖 Postgres 默认约束名

上面那两段 `match db.constraint()` **完全依赖迁移里显式命名约束**。Postgres 的默认命名（`equipment_workspace_id_code_key`）会在某次改列名时静默失配，而失配的表现是"这个错误不翻译了"——很难注意到。

原稿第 8 节末尾自己就要求了显式命名（`CONSTRAINT equipment_code_uniq UNIQUE (workspace_id, code)`），但同节的代码示例用的却是默认名 `equipment_workspace_id_code_key`。**这是自相矛盾，已修正**：迁移里每条约束都必须有显式名字，且名字要写进本节的 `match`。

### 8.4 两个协议层的静默陷阱

**① `time::Date` 的 serde 默认格式不是 `"2026-10-01"`。** `time` crate 的 `Date` 默认序列化成 `[year, ordinal]` 数组，也就是 `[2026, 274]`。而 7.2 规定业务日期是 `"YYYY-MM-DD"`。

不显式指定格式就会**静默违反 7.2**，而且 `gen-api` 从 serde 内省出来的 TypeScript 类型会跟着变成 `number[]`，前端 DTO 声明是 `string`——编译期不报、类型检查不报，要到前端渲染日期时才发现。

每个日期字段都要挂 `#[serde(with = "time::serde::format_description!(date = "[year]-[month]-[day]"))]`，并且**用契约测试断言序列化结果是一个匹配 `^\d{4}-\d{2}-\d{2}$` 的字符串**（而不是断言类型）。

**② `updated_at` 必须在每次 UPDATE 里显式 `SET updated_at = now()`。** Postgres **没有 `ON UPDATE CURRENT_TIMESTAMP`** 这种机制（那是 MySQL 的）。`DEFAULT now()` 只在 INSERT 时生效。

后果：任何忘记这一句的 UPDATE 会让 `updated_at` 永远停在创建时间，**不报错**。而 5.5 的字段编辑走的正是 UPDATE，且 `EquipmentAdmin` 会把这个字段下发给前端——于是列表中"最后修改时间"会长期显示建档那一刻。

**对策是纪律而非机制**：所有改这些表的 SQL 都必须带这一句。可以用一条测试守（改一个字段，断言 `updated_at` 变大）——**建议只对 `equipment` 写这条测试**，覆盖最常用的那条路径，其余靠 review。

## 9. 认证与授权

自托管，理由见第 2.3 节。

- **密码**：`argon2` crate，Argon2id，参数写在一个常量里。
- **会话**：`app_user_session` 表，cookie 为 `httpOnly; Secure; SameSite=Lax`。校验走一个 `FromRequestParts` extractor，每请求查一次会话（单工作室规模下这次查询可以忽略；真要优化再加内存缓存）。停用账号时删除其全部会话——这是选有状态会话的**唯一理由**。
- **邀请**：`invite` 表，明文 token 只在生成时返回一次，库里存 hash，有 `expires_at` 和一次性 `consumed_at`。这一张表顺手解决交接稿第 10 节的"邀请邮件没有邮件服务"——生成链接手动复制即可；将来接邮件服务只加一个发送器，表结构不动。
- **首个账号**：`app_user_one_owner` 唯一索引 + "当 workspace 无 OWNER 时允许匿名创建"这一条 bootstrap 接口（只在没有任何 OWNER 时可用，用过即永久失效）。
- **角色守卫**：`Actor::can_change_role(&self, target)` 里**显式列出 OWNER 不可被改**，返回 `DomainError::OwnerImmutable`。不依赖"界面上不显示开关"——那是 UI 事实，不是安全边界。
- **主理人交接**：目前无设计（第 13.7 节）。数据库层面 `app_user_one_owner` 是一个唯一索引，转移需要"先降级旧的、再升级新的"两步事务；这一条要产品先确认要不要做。

## 10. 操作历史与活动流

交接稿第 6 节要求：器材详情弹窗显示"历史操作（近 5 条）"，出入库记录页显示"全库操作流水"，项目卡片显示"历史出库记录数"。这一节定这些界面的数据来源与形状。

**"近 5 条"这个数字在 5.5 落地后就不成立了。** 描述性字段编辑开始留痕之后，一条记录的历史会显著变长，5 条会在两周内被填满，然后这个区域永久只显示最近两天的噪音。

### 10.1 唯一的叙事主线

操作事实在主稿里散在四处：`equipment_history`、`checkout`、`maintenance`、以及 5.5 引入的 `UPDATE` 动作。**界面只读一处：**

> **`equipment_history` 是唯一的叙事主线，其余表只用来补充点开后的细节。**

理由：一次出库会同时产生 `checkout` 行和 `equipment_history` 行。若界面从两处聚合，同一次出库会显示两次，而且"谁排前面"取决于时间戳的毫秒差——结果不稳定且无法复现。

映射：

| 界面上的动作 | `action` | 点开后显示 |
|---|---|---|
| 建档 | `CREATE` | 初始字段 |
| 出库 | `CHECKOUT` | 跳 `checkout`：项目、使用人、交接清单 |
| 归还 | `RETURN` | 归还日期、备注 |
| 送修 / 维修完成 | `MAINTENANCE_SEND` / `MAINTENANCE_CLOSE` | 跳 `maintenance`：故障说明、维修单位、费用 |
| 停用 / 恢复 / 出售 / 归档 | 同名 | — |
| **修改** | `UPDATE` | `detail.changed` 数组（5.5） |

### 10.2 修改记录的两个要求

**① `changed` 数组必须存原值。** 5.5 那个 `from` / `to` 结构存在的理由就是这个界面——用户会问"这价格原来多少"，答案只在 `from` 里。**不要为了省空间只存新值。**

**② 字段名 → 中文标签的映射放前端。** `price_cents` 不能出现在界面上，但后端只传字段名（主稿 7.2：线上跑的是稳定代码，不是中文）。这样改文案不用发后端。交接稿第 9 节的术语表是这张映射表的雏形。

渲染形状：

```
李四  修改了 器材          10-01 14:22
      价格      9,800.00 → 12,800.00
      存放位置  A柜 → B柜
```

### 10.3 噪音：界面层合并，不动数据

一个人在表单里改了名称又改了型号，会产生多条 `UPDATE`；连改三次名称 = 三条。

**对策：界面层合并同一人、同一实体、5 分钟内的连续 `UPDATE`**，显示成一条"修改了 名称、型号、价格"。

这是**显示层的合并，底层仍然每次提交一条**。两个目标必须分开：**审计要精确到每次提交，界面要可读。** 把合并做进数据层会让审计失去粒度，而审计正是 5.5 引入 `UPDATE` 留痕的全部目的。

### 10.4 权限

| 角色 | 器材历史 |
|---|---|
| OWNER / ADMIN | 全部，含字段修改 |
| **REQUESTER** | **完全不给入口** |

申请人不能看全库历史（交接稿第 3 节），而且字段修改里含价格和序列号——正是申请人被裁剪掉的字段。**所以权限过滤不只在"能看哪些器材"这一层，还要在"能看哪些条目"这一层。**

**决定：申请人完全不给历史入口**，而不是做字段级的条目过滤。申请人的界面里只需要"他的申请单里每件器材当前的状态"，给申请人做历史过滤的收益是零。

### 10.5 一个接口，四个界面

```

GET /api/v1/activity?scope=workspace&cursor=…&includeUpdates=false
```

### 10.6 账号不删除

`equipment_history.actor_id` 指向 `app_user`。规则：**账号只停用（`disabled_at`），不删除**（第 9 节的机制已经如此）。停用账号在历史里照常显示名字并标注"(已停用)"。

**不要为了清理账号去删行**——那会让历史失去作者，而"谁改的"正是这个界面存在的理由。

## 11. 后台任务

`jobs` binary，cron 触发，每个任务独立可重入：

| 任务 | 频率 | 做什么 |
|---|---|---|
| 逾期扫描 | 每日 | 查 `status='CHECKED_OUT' AND expected_date < today`，产出提醒。**通知渠道未定**（第 13.8 节），当前只写日志并在总览页查询里体现 |
| 照片孤儿清理 | 每周 | 第 6.5 节的标记清除 |
| 占用对账 | 每日 | 检查 `occupancy` 与源头的一致性：每条 `RESERVATION` 应有一条 `approved = true` 的 `request_item`；每条已归还的 `checkout_item` 不应有对应的 `CHECKOUT` 占用。发现偏差记 error 日志 |
| 会话清理 | 每日 | 删除 `expires_at < now()` 的会话行 |
| 邀请清理 | 每日 | 标记过期邀请 |

**占用对账不替代排他约束，而是查逻辑错误。** 排他约束保证"不会有两行重叠"，对账查的是"该有的行是不是没了、不该有的行是不是还在"——这是写路径 bug 的探针，不是并发防护。

## 12. 部署与运维

### 12.1 形态

```
docker compose:
  app        # Axum，一个镜像两个入口（api / jobs）
  postgres   # 16+，需要 btree_gist
  caddy      # TLS + /photos 静态直发 + JSON 压缩
volumes:
  pg_data
  lensmax_data   # photos/ 与 tmp/，必须同一文件系统（rename 依赖这个）
```

### 12.2 备份

**数据库**：`pg_dump -Fc` 每日 + 异地副本。**必须定期演练恢复**——只备份不演练等于没备份。

**照片**：一份冷数据，增量同步到同一异地目标。**不要塞进每日数据库备份包**（体积差三个数量级）。

**两者要一致**：数据库里的 `photo.rel_path` 指向文件。恢复时若只恢复库不恢复文件，会得到一堆死链；若只恢复文件不恢复库，会得到一堆孤儿（可被清理任务重扫，无害）。所以恢复顺序是**先文件、后库**。

### 12.3 托管 Postgres

Neon / Supabase / RDS 都可以，把备份、PITR、升级接过去。**选之前必须确认 `btree_gist` 在白名单里**——有些"Postgres 兼容"服务不给，缺了它整个第 3 节的设计要回退到应用层检查。这是选型的第一道门槛，不是优化项。

### 12.4 构建

Rust release 构建慢，Docker 层缓存必须做对（`cargo-chef` 或等价方案），否则每次部署都在等编译。这一点在交接稿"小团队改一行上线"的手感上是真实成本。

**`.sqlx/` 离线缓存进仓库**，CI 加一条检查：改了 SQL 但忘了 `cargo sqlx prepare` 就红。

## 13. 未决项

> **本节是索引。完整清单（含推荐答案、可否决的形式、以及"现在不定会不会返工"的分组）在 [20260930_OPEN_DECISIONS_v1.md](20260930_OPEN_DECISIONS_v1.md)，编号 `D-01`…`D-18` 指那份文档。** 下列内容保留在此是为了让本稿自洽。

实现前需产品/负责人确认。第 13.1–13.3 是阻塞项（不定就无法开工），其余可先按默认方案实现。

### 13.1 术语：出库 vs 借出（阻塞）

交接稿第 11 节指出界面用"出库/出入库记录"、数据模型和文档用"借出"，需要统一。

**本稿立场：采用「出库」。** 理由不是偏好，是成本不对称——界面文案、导航、按钮、CSV 模板列名、打印抬头已经全部是"出库"，改成"借出"要动的是对外可见的纸质凭证；而数据模型改一个词只是重命名。且交接稿第 0 节自己定的规则是"冲突时以真实界面为准"。

本稿代码层用 `checkout` / `return` 与界面词"出库/归还"并存，这是**有意的**：代码用英文避免中文标识符，界面用中文业务词。需要统一的是**同一个概念不要有两个中文说法**，不是代码和界面必须逐字相同。

### 13.2 导出备份是否按角色裁剪（阻塞）

交接稿第 6 节把"导出备份"列为管理员能力，但没说导出内容。

**默认方案**：仅 OWNER / ADMIN 可导出，导出**原始数据**（含价格/序列号），并在文件头写入导出人、时间、范围。理由：备份的用途是灾难恢复，裁剪过的备份没有恢复价值。

**需要确认**：是否存在"管理员导出给别人看"的场景？若有，那需要第二个"脱敏导出"接口。

### 13.3 是否归档已签字的出库清单（阻塞）

当前流程是打印 → 手写签名 → 纸质件即原件。系统不存签字件。

**若产品要求系统留档**（举证、审计），则：需要新增一类文档存储（扫描件/照片上传），且清单 PDF 要服务端生成（`typst`），并解决中文字体内嵌——**字体子集必须打进镜像**，否则线上第一份出库单全是方框。

### 13.4 项目类型是否可自定义

交接稿第 11 节指出类型是硬编码下拉。本稿建成受约束枚举（`PROMO/SHORT_FILM/TVC/EVENT/CAMPUS/OTHER`）。

若产品要自定义（而且"其他"这个选项的存在本身说明分类可能不够用），改为 `project_type` 表 + 外键。**现在决定成本最低**，因为还没有数据。

### 13.5 搜索实现

交接稿第 6 节的搜索覆盖名称/编号/品牌/型号/序列号。中文没有词干，`to_tsvector` 对中文近乎无效。

**默认方案**：`ILIKE '%q%'` + `pg_trgm` 的 GIN 索引。器材量级（几千）下足够。

**需在真实数据上验证**：若器材数上万或有性能问题，再评估分词方案。**不要一开始就上 Elasticsearch 之类**——那是给一个还没有性能问题的系统加一个需要运维的组件。

### 13.6 何时该回退到 SQLite

本稿选 Postgres 的唯一硬理由是 C2（区间排他约束）。

**触发回退的条件**：确认长期单工作室、无并发写需求、且不接受任何数据库运维成本。此时 SQLite 是更省事的选择，代价是：

- `occupancy` 互斥改由"写路径串行化（`BEGIN IMMEDIATE`）+ 巡检任务"保证，从数据库保证降级为纪律保证；
- 失去并发写；
- 迁移到 Postgres 时要重做 DDL（区间类型、枚举、约束）。

**记录这个条件的目的**：避免下一个人在没有新信息的情况下把选型再讨论一遍。

### 13.7 主理人交接

见第 9 节末。当前无设计。需确认：主理人离职/换人时怎么转移？不做会成为一个单点故障。

### 13.8 逾期提醒的通知渠道

交接稿第 10 节指出目前只有总览页的红色提示条。逾期是器材管理最大的实际损失点。

**这是唯一一个会把外部服务引进架构的点**（企业微信/飞书/SMS/邮件）。后端只留一个 `notify()` 端口，渠道是产品决定。**未定之前，逾期扫描任务只写日志**。

### 13.9 CSV 导入的重复判定

交接稿第 5.1 节的模板列固定为 `器材编号,器材名称,分类,品牌,型号,序列号,存放位置,购买日期,购买价格,备注`，其中"器材编号"由 CSV 提供，但系统也允许留空自动生成。

**未定**：同一份文件导入两次会怎样？模板里没有天然唯一键。两个选项：按编号去重（有编号的行覆盖/跳过，无编号的行每次都新建），或每次全部新建。

**建议**：按 `(workspace_id, code)` 去重，导入预览里把"已存在，将跳过"的行标出来。这与"不做部分成功"不冲突——去重是预期行为，不是失败。

### 13.10 HEIC

见第 6.7 节。需验证前端是否存在直接上传原文件的路径。
