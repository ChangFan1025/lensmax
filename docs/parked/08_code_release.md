## 1. 结论先行

| 问题 | 结论 |
|---|---|
| 能不能释放编号？ | **能，但只能释放"从未离开过系统"的编号。** 见第 3 节的判据 |
| 释放后能和"归档可恢复"共存吗？ | **能，但需要把两件事分开**：编号的**归属**和编号的**可用性**。见第 4 节 |
| 高效算法是什么？ | 不是"找空洞"——是**把已释放的编号放进一张池表，取最小的那一个**。O(log n)，一个索引。见第 5 节 |
| 该不该现在做？ | **不该。** 先按永久占用实现，等真出现"编号不够用"或"空洞碍事"的证据再做。理由见第 6 节 |
| 从永久占用切到可释放，难吗？ | **不难**，只需回填"历史使用情况"。反向（可释放 → 永久占用）**做不到** |

## 2. 先明确一件事：编号的"占用"是两个不同的东西

现在主稿 3.5 把两件事压成了一个唯一约束：

| | 含义 | 谁关心 |
|---|---|---|
| **归属** | 这个编号指的是哪一件器材 | 历史记录、纸质单据、实物标签 |
| **可用性** | 这个编号能不能给新器材 | 建档时的分配逻辑 |

**"永久占用"是一条规则同时管住了两件事**：`(workspace_id, code)` 唯一且覆盖归档行，所以归档 = 归属仍在 + 可用性也没有。

**"释放编号"要拆开它们**：让归属仍在（历史可追溯），但把可用性交还。

**这个拆分是整份设计的核心**，后面所有复杂度都来自它。

---

## 3. 可释放判据：编号是否"离开过系统"

**这是整份预研里最难、也最重要的一条。**

一个编号一旦印在**实物标签**上或**已签字的出库清单**上，它就进入了物理世界。此时释放它，物理世界与数据库的对应就断了——一张纸上的 `CAM-002` 会指向两件东西。

所以判据必须是 **"这个编号从未离开过系统"**，而**归档不等于未离开过**。

```rust
/// 编号可释放的判据。
/// 每一条都必须能从库里判定，不能依赖"某人记得"。
pub fn is_releasable(conn: &mut PgConnection, code_row: &CodeRow) -> Result<Releasability, AppError>
```

| # | 判据 | 成本 |
|---|---|---|
| 1 | 该器材**已归档**（`archived_at IS NOT NULL`） | O(1)，行内 |
| 2 | 该器材**当前不在出库中**（`status <> 'CHECKED_OUT'`） | O(1)，行内。归档已经隐含了这条 |
| 3 | **从未出现在任何 `checkout_item`** | O(log n)，`checkout_item(equipment_id)` 索引一次探针 |
| 4 | **从未出现在任何已交付的 `request_item`** | O(log n)，同上 |
| 5 | 从未有过 `maintenance` 记录 | 建议**不作为**否决条件——维修不会让编号离开系统（不印在对外单据上） |
| 6 | **没有被导出过** | ⚠️ 见下 |

**第 3 条是真正的分界线。** 器材只要出过库，编号就上了签字的清单，**永久不可释放**。

第 6 条是这条判据的一个真实漏洞，值得单独说：

> 器材**从未出库**，但有人做过一次 CSV 导出、或者打印过器材清单，那份文件流到了外面。
>
> **系统无法知道那一列编号有没有被记下来。** 严格来说，任何一次导出都会让此后所有编号"可能离开过系统"。

**三种处理**：

| 处理 | 评价 |
|---|---|
| 忽略导出这个因素 | **推荐**。导出记录不是物理凭证，而且把它纳入判据会让"导出过"变成一条永久冻结全局编号的事件——**代价远大于收益** |
| 记录每次导出的编号范围，纳入判据 | 过于保守：一次导出冻结此后所有编号，等于编号永远不可释放 |
| 导出时不给编号列 | 会破坏导出的用途（财务核对要编号） |

**结论：判据只看第 1、3、4 条**（归档 + 从未出库/交付）。**并且要在界面上把这句话说给用户**——"这个编号从未由本系统交给过任何人，所以可以释放"。这是把不可判定的事情变成**可判定的、且诚实的**。

## 4. 与"归档可恢复"的张力：正面解决

主稿 3.5 已经指出这条张力：

> 如果编号能被新器材接手，那么**恢复归档就变得危险**——你恢复 `CAM-034` 时，可能已经有一个新器材也叫 `CAM-034`。

**这正是第 2 节那个"归属 vs 可用性"拆分的用途。** 三态设计：

```rust
enum CodeState {
    InUse,      // 归属某件在册器材，不可分配
    Released,   // 归属一件已归档器材，可被新器材分配
    Retired,    // 归属一件已归档器材，永久不可再分配（出过库的）
}
```

**规则**：

| 状态 | 归属 | 可分配 | 能归档恢复吗 |
|---|---|---|---|
| `InUse` | 在册器材 | ✗ | — |
| `Released` | 已归档器材 | ✓ | **能**，且恢复时**自动把它从 `Released` 撤回到 `InUse`** |
| `Retired` | 已归档器材 | ✗ | 能，且它本来就不可分配，没有冲突 |

**关键在于 `Released → InUse` 的回撤是原子的**，而且必须**抢在别人分配之前**：

```sql
-- 恢复归档时，先原子地撤回该编号的可用性；失败说明已被别人用掉
UPDATE code_pool SET released_at = NULL
 WHERE workspace_id = $1 AND code = $2 AND released_at IS NOT NULL
RETURNING code;
-- 0 行 → 该编号已被新器材占用 → 恢复时给这件器材一个"编号冲突"的明确提示，
--        由人决定：换新编号，或先处理占用它的那件器材
```

**这就是"归属 vs 可用性"拆开之后买到的能力**：恢复不再"危险"，而是**要么成功、要么给出一个人能理解的冲突**。冲突罕见（要求两件事同时发生），但必须是明确的而不是静默的。

> **⚠️ 这条规则有一个上限要承认**：如果 `CAM-002` 被释放、被新器材用了、然后你恢复那件旧器材，**旧器材必须换编号**。而主稿 3.5 第 2 条说"编号生成后永不改变"。
>
> **这不矛盾**：那条规则约束的是**正常操作**（分类改名不能让编号变），而这里是**人为的编号回收**带来的冲突解决。但要在界面文案里说清——"该编号已被新器材使用，恢复后这件器材需要一个新编号"。**这是释放编号必须付的代价，也是它值得慎用的原因。**

## 5. 高效算法：不是"找空洞"，是"维护池"

**先排除一个错误方向。** 直觉做法是"每次分配时找最小的未使用编号"：

```sql
-- ❌ 不要这样
SELECT min(seq) + 1 FROM ... WHERE NOT EXISTS (...)
```

它有两个问题：**① 每次分配都要扫**；**② 它假设编号连续**，而实际上手填编号会让序列出现任意空洞，所以它找出来的"最小空洞"可能是别人手填的未来编号。

**正确做法：把已释放的编号放进一张池表，分配时取最小的那一个。**

```sql
CREATE TABLE code_pool (
  workspace_id  uuid   NOT NULL,
  code          text   NOT NULL,
  -- 该编号曾经归属的器材（已归档）。归属关系不因释放而消失。
  equipment_id  bigint NOT NULL REFERENCES equipment(id) ON DELETE RESTRICT,
  released_at   timestamptz NOT NULL DEFAULT now(),
  released_by   bigint NOT NULL REFERENCES app_user(id),
  release_reason text NOT NULL,

  PRIMARY KEY (workspace_id, code),
  -- 编号的状态：见第 4 节。Retired 的行留在表里但不可分配。
  CONSTRAINT code_pool_state_check CHECK (state IN ('RELEASED','RETIRED'))
);

-- 取最小可用编号的关键索引
CREATE INDEX code_pool_available_idx
  ON code_pool (workspace_id, code)
  WHERE state = 'RELEASED';
```

**分配逻辑（事务内）**：

```sql
-- ① 先看池里有没有可用的。SKIP LOCKED 让并发分配不会互相等
SELECT code FROM code_pool
 WHERE workspace_id = $1 AND state = 'RELEASED'
 ORDER BY code
 LIMIT 1
   FOR UPDATE SKIP LOCKED;

-- ② 有 → 从池里移除，用它
DELETE FROM code_pool WHERE workspace_id = $1 AND code = $2;

-- ③ 没有 → 走原来的计数器
UPDATE category SET next_seq = next_seq + 1
 WHERE id = $3
RETURNING code_prefix, next_seq - 1 AS seq;
```

**复杂度**：`ORDER BY code` 走 `code_pool_available_idx` 的有序索引，取最小是 **O(log n)** 而不是 O(n)。`SKIP LOCKED` 让两个并发分配各自拿到**不同的**最小可用编号，而不是一个等另一个。

**⚠️ `ORDER BY code` 是字符串序，这有一个真陷阱**：`CAM-1000` 会排在 `CAM-999` 前面。如果序号宽度会漂移（主稿 3.5 说会），那么"最小可用编号"会被算错。

**两个解法**：

| 解法 | 说明 |
|---|---|
| **池表里存一个数值列 `seq`**，`ORDER BY seq` | 干净。需要解析 `code` 得到 `seq`（建档时已知，直接存） |
| **统一补零宽度**（主稿 3.5 已建议） | `CAM-0999` / `CAM-1000` 的字符串序与数值序一致 |

**推荐两者都做**：补零宽度让编号本身排序正确（列表页也需要），池表存 `seq` 让分配逻辑不依赖字符串。

**注意：本表的量级是"被释放的编号数"，不是"器材数"。** 它是**小的**——只有"从未出库过"的编号才会进来（第 3 节）。几千件器材的系统里，这张表长期可能是**个位数到几十行**。

> **所以"高效"这个词要重新理解**：这里的算法复杂度不是瓶颈（几十行怎么排都快）。**真正的成本在判据上**——第 3 节那两条"是否从未出库"的探针，每次释放都要跑。

## 6. 抽象层

按 [实现篇](../20260930_RUST_IMPL_v1.md) 第 2 节的规矩：调用方只看意图，看不到机制。

```rust
// domain/codes.rs —— 私有类型，不出模块

/// 编号的状态。**调用方看不到它**，只通过下面的方法间接感知。
enum CodeState { InUse, Released, Retired }

struct CodePoolRow { /* workspace_id, code, seq, equipment_id, released_at, state */ }
```

```rust
// domain/ledger.rs —— 调用方看到的

impl Ledger {
    /// 建档。**编号从哪来是内部决定的** —— 池里的空闲号优先，其次计数器。
    /// 调用方不传 code，也不知道它怎么被选中。
    pub async fn create_equipment(
        conn: &mut PgConnection, actor: &Actor, cmd: CreateEquipmentCmd,
    ) -> Result<Equipment, AppError>;

    /// 显式指定编号建档（手填）。编号不可用时给出**可理解的原因**。
    pub async fn create_equipment_with_code(
        conn: &mut PgConnection, actor: &Actor, cmd: CreateEquipmentCmd, code: Code,
    ) -> Result<Equipment, AppError>;

    /// 释放一个编号，使其可被后续器材使用。
    /// **它的失败条件是业务判据**（第 3 节），不是"操作不允许"。
    pub async fn release_code(
        conn: &mut PgConnection, actor: &Actor, equipment_id: i64, reason: &str,
    ) -> Result<ReleaseOutcome, AppError>;

    /// 恢复归档。**这里藏着 `Released → InUse` 的原子回撤**（第 4 节）。
    pub async fn restore_archived(
        conn: &mut PgConnection, actor: &Actor, equipment_id: i64,
    ) -> Result<Equipment, AppError>;
}

/// 释放的结果是**三态**，不是成功/失败二元。
pub enum ReleaseOutcome {
    Released,
    /// 编号已经离开过系统（出过库），永久不可释放。
    Retired { because: RetireReason },
}

pub enum RetireReason {
    HasCheckoutHistory { checkout_count: i64 },
    HasDeliveredRequest { request_id: i64 },
}
```

**三条设计规则**：

1. **`create_equipment` 不接收编号。** 一旦接收，"编号从哪来"就变成了调用方的责任——那正是要藏起来的东西。
2. **`release_code` 的返回类型是三态而不是 `Result<()>`。** 因为"不能释放"是一个**业务结论**（并且要告诉用户为什么），不是错误。
3. **`restore_archived` 是唯一需要知道池的地方**，因为回撤发生在这里。调用方不需要知道。

**与既有决定的关系**：

| 既有决定 | 本设计的关系 |
|---|---|
| 编号一旦生成永不改变（主稿 3.5） | **相容**，除了一处：冲突解决时旧器材要换号。见第 4 节的警告 |
| `RESTRICT` 级联、不提供 DELETE | **相容**。池表也是 `RESTRICT`，且没有删除，只有状态 |
| 所有写入经 Rust 服务层 | **强化**。`code_pool` 是**最不能**被绕过的一张表——它直接决定编号会不会撞 |

## 7. 迁移路径与不可逆性

### 从永久占用 → 可释放（容易）

```sql
-- 1. 建 code_pool（第 5 节的 DDL）
-- 2. 回填：找出所有"已归档 + 从未出库 + 从未交付"的编号
INSERT INTO code_pool (workspace_id, code, equipment_id, state, release_reason)
SELECT e.workspace_id, e.code, e.id,
       CASE WHEN <有出库历史> THEN 'RETIRED' ELSE 'RELEASED' END,
       '迁移回填'
  FROM equipment e
 WHERE e.archived_at IS NOT NULL;
```

**成本**：一次全表扫 + 两次 anti-join。几千行，秒级。**可以在任何时刻做，包括上线后很久。**

### 从可释放 → 永久占用（做不到）

一旦有编号被真正复用（新旧两件器材都拿过 `CAM-002`），**回退时会面临"哪一条该保留 `CAM-002`"这个无法判定问题**——那个依据在第一次复用的那一刻就丢了。

**所以这条决定是单向的。** 这也是我建议**先不放开**的最强理由：不放开可以随时放开，放开不能撤回。

## 8. 该不该现在做

**我建议不做，按永久占用实现。** 理由：

| # | 理由 |
|---|---|
| 1 | **没有证据表明需要它。** 编号空间是无界的（主稿 3.5），所以释放**不解决容量问题** |
| 2 | **它解决的问题（编号空洞）价值很低**：空洞不携带信息，没人会去研究少了 `CAM-002` |
| 3 | **它的成本不低**：一个新表、一个新状态机、`restore_archived` 里的一条原子回撤、一处"编号会变"的例外（破坏主稿 3.5 第 2 条）、以及最容易错的一处——判据 |
| 4 | **它引入的真实风险**：一旦释放的编号被用掉，"恢复归档"就可能失败或被迫换号。而"归档可恢复"是主稿 3.4 的既有承诺 |
| 5 | **它不可撤回**（第 7 节） |

**触发重新评估的条件**（写给下一个接手的人，避免重新讨论）：

- 某个分类的编号**真的接近宽度需要加宽**，且空洞让编号可读性明显变差
- 出现"录错建档 → 归档 → 想重来"的**高频**操作（当前预期是罕见）
- 有人明确要求"编号要连续"（例如外部审计或客户对账要求）

**在那之前，正确做法是主稿 3.5 的现状：永久占用 + `code-available` 端点把"已归档占用"这个原因说出来。**

## 10. 待验证（未实测）

本机无 `cargo`、无 `psql`、无 Docker。以下为推理而非实测：

| # | 待验证 | 失败表象 |
|---|---|---|
| 1 | `FOR UPDATE SKIP LOCKED` 在 `LIMIT 1` + `ORDER BY` 下的行为是否符合预期（跳过被锁的行而不是阻塞） | 并发分配退化成串行，或有一个请求拿到已被占用的编号 |
| 2 | `DELETE FROM code_pool` 后随即 `INSERT equipment` 在同一事务里是否必然安全（依赖唯一约束的位置） | 需要改成先插入再加约束 |
| 3 | 第 4 节那条 `UPDATE code_pool SET released_at = NULL` 与分配逻辑的竞态窗口 | 恢复与分配同时成功 → 两条 `CAM-002` |
| 4 | 池表的 `state` 列与 `released_at` 是否真的需要同时存在（可能可以合并成一个 `retired_at`） | 冗余列，但无害 |

**第 3 条是最需要实测的一条**——它是本设计里唯一一处"两个操作同时成功就会撞号"的窗口，而唯一约束是最后一道。实施时必须写一条并发测试把它钉住。
