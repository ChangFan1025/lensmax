## A 组：阻塞 DDL

### D-01 分类"不再使用"怎么表达？

| | |
|---|---|
| **推荐** | **可用性改成派生**：一个分类"可用于新建器材"当且仅当**它有至少一件未归档的器材**，或**管理员显式钉住了它**（`category.pinned`）。`disabled_at` 从"生命周期管理"降级为"显式覆盖"——只用于"分类下明明有器材、但我不想让新器材再归到它"这种少见情况 |
| **为什么不是"手动停用"** | 那等于**手动内存管理**：器材都归档了，你得记得去停用分类，否则它永远留在新建器材的下拉里；忘了就慢慢填满。**"谁忘了 disable"和"谁忘了 free"是同一个 bug** |
| **为什么不是"定时任务自动停用"** | 那会在分类下所有器材归档时把它停用，于是**恢复那件器材后分类还是停用的**——能回收，不会复活。派生没有这个问题：条件是"有未归档器材"，恢复器材后它自动重新出现 |
| **否决的代价** | 如果你要"手动停用"语义，那么需要一个"定期清理没人用的分类"的习惯动作，且需要接受"恢复器材后分类仍不可选"的困惑 |
| **阻塞** | **是**——决定 `category` 表要不要 `pinned` 列 |

### D-02 一个编号能不能被两件器材先后使用？ —— ⏸ **已挂起，预研中**

> **状态（2026-09-30）**：产品决定**先留着，后面研究**。
>
> **预研在**：`docs/parked/08_code_release.md`——释放编号的高效算法与抽象层设计。
>
> **记下的要求**：「如果要释放编号的话，需要有一个高效算法和抽象层去管它。」

**实现时的默认值**：先按**不放开**（永久占用）实现，因为：

- 它是当前默认，且**不放开可以随时切到放开**（放开需要补"历史使用情况"的数据，但从"从未释放"开始是干净的）
- **反过来不行**：一旦放开，库里就有两条同号，判断依据丢了

**容量不是理由。** 序号可以无限加宽（`CAM-999` 之后是 `CAM-1000`），所以**每个分类的件数没有硬上限**——永久占用不会碰到任何容量问题。

**真正的软上限是人的耐受度**：编号要在电话里报、要贴在实物上。3 位撑到 999 舒服，4 位还行，5 位该归一化。

**这条问的是什么。** `equipment` 现在的 `(workspace_id, code)` 唯一约束**覆盖已归档的行**。于是：

> 建档时手滑填成 `CAM-002`，归档了它；现在新建一件器材想用 `CAM-002` —— 能不能用？

| | 不放开（推荐） | 放开 |
|---|---|---|
| 数据库 | 保持 `UNIQUE (workspace_id, code)` | 改部分唯一索引 `WHERE archived_at IS NULL` |
| 归档行是否占用编号 | 占用，永久 | 让出 |
| 编号序列 | 会出现空洞（`CAM-002` 永久消失） | 无空洞 |
| **同一编号历史上指过两件东西** | **不会** | **会** |
| 查历史 `CAM-002` 是谁 | 唯一答案 | 要看时间 |
| 纸质出库单上印的 `CAM-002` | 唯一指向 | **可能有歧义** |

| | |
|---|---|
| **推荐** | **不放开**。归档行继续占用编号；需要纠正编号时**允许改 `code` 到另一个未被占用的值**，不释放旧值 |
| **理由（业务，不是洁癖）** | 交接稿 5.2 的出库交接清单**是打印出来给现场签字的三联纸，逐件印着编号**。一张 2026 年的单子写着 `CAM-002`，两年后有人拿它来对账，必须能确定是哪台机器 |
| **为什么这条不能"以后再改"** | **它是 18 条里唯一一条错了收不回来的技术决定**。一旦放开，库里就有两条 `CAM-002`，而**没有任何依据能判断哪条该保留**——那个依据在放开的那一刻就丢了。其余决定（撤回规则、拒绝理由、分类可用性）改了只是改一行 Rust + 重发，库里不用清理 |
| **比纸质凭证更硬的理由** | **放开编号会破坏"归档可恢复"**（主稿 3.4）：如果编号能被新器材接手，你恢复 `CAM-034` 时可能已经有一个新器材也叫 `CAM-034`。**放开编号 = 给归档加一个隐式的"恢复可能失败"条件** |
| **"我想用回那个编号"怎么满足** | **恢复归档**（`POST /equipment/{id}/restore`），而不是重编号。所以这个需求 99% 的情况下不是"放开编号"的理由 |
| **需要补的一个端点** | `GET /equipment/code-available?code=…`，**必须说出"已归档"这个原因**——否则用户看到"编号被占用"会一头雾水，因为他在列表里看不到那件器材（列表默认排除已归档） |
| **若你们的情况相反** | 如果编号**只存在于系统内部**、从不出现在纸面、也没人拿它对照实物贴标签，那放开更省事（编号空洞反而麻烦）。**这条取决于编号有没有脱离系统存在，需要你回答** |
| **阻塞** | **是**——决定唯一索引的形状 |

### D-04 已签字的出库清单要不要在系统里存档？

| | |
|---|---|
| **推荐** | **不存档**。当前流程是打印 → 手写签名 → 纸质件即原件 |
| **理由** | 存档需要新增一类文档存储（扫描件上传）+ 服务端生成 PDF + **中文字体子集打进镜像**（否则线上第一份出库单全是方框）。这三件事的成本远大于"把纸放抽屉里" |

## B 组：阻塞接口

### D-06 关掉"允许浏览/允许申请"时，已批准的档期怎么办？

| | |
|---|---|
| **推荐** | **保留，一行 `occupancy` 都不动**。两个开关是**准入开关**——只阻止开始新动作，绝不回溯 |
| **理由（三条，按强度）** | ① 主稿 3.1 那张「业务事件 → occupancy 操作」映射表是**封闭的**（只有交付/归还/撤回三个事件写占用），开关根本不在其中<br>② 释放**不可逆**——别人能立刻领走，开关再打开也回不来<br>③ **开关注释放会打穿每日占用对账**：对账规则是「每条 `RESERVATION` 必须有对应的 `approved = true` 的 `request_item`」，释放后这条规则天天误报 ERROR，**对账从 bug 探针退化成噪音** |
| **否决的代价** | 需要新增一条"开关变更 → 批量作废 + 批量 DELETE 占用"的写路径，并接受：已交付的器材仍在外面但占用被删、`checkout.source_request_id` 指向一个已作废的申请、对账永久误报 |
| **阻塞** | **是** |

### D-07 关掉开关后，申请人还能看到「我的申请」并撤回吗？

| | |
|---|---|
| **推荐** | **能。始终能。** 两个开关只约束"浏览全库器材"和"提交新申请" |
| **理由** | 否则申请人陷入黑盒——看不到自己的单、也撤不回，而主稿 3.1 的"撤回释放占用"路径会因此断掉 |
| **阻塞** | **是**（决定 `GET /requests/mine` 和 `withdraw` 要不要过开关检查） |

### D-08「允许申请 = 开，允许浏览 = 关」这个组合允许吗？

| | |
|---|---|
| **推荐** | **不允许，保存时拦住**（422："不允许浏览时也必须允许申请，否则申请人无法挑选器材"） |
| **理由** | 申请是针对具体器材的，看不到器材库就没法提交 |
| **若你要允许** | 需要额外定义"看不到器材库时申请表单里的器材怎么选"——那是一个新功能（比如按编号盲填），不是配置组合 |
| **阻塞** | **是**（低成本，只是校验规则） |

### D-09 谁能改这两个开关？

| | |
|---|---|
| **推荐** | **只有主理人**。管理员能读（界面上知道当前状态）但不能写。且明确：**开关只约束申请人，主理人/管理员的一切操作不受影响** |
| **理由** | 这是"影响全库所有申请人"的开关，下放给管理员等于第二个人能瘫痪申请流程 |
| **阻塞** | 否（但影响端点权限档） |

### D-10 申请人被拒时能看到「这件为什么没批」吗？

| | |
|---|---|
| **推荐** | **能看到哪些件被拒 + 管理员为该件填写的自由文本理由；理由允许留空；不给结构化的"替代器材"字段** |
| **理由** | 管理员的真实用法是"AM-002 没批是因为被《宣传片A》占住了，建议换 AM-005"——这类信息需要载体，而自由文本够用。加"替代器材"字段要额外一列 + 一个"替代品当前是否可用"的读模型，成本远大于收益 |
| **需要提醒的** | 这会让审批界面多一个输入框。**如果不提供快捷语，这个字段两周内会退化成空格**——所以界面要预置几条常用理由 |
| **若否决（不给理由）** | DDL 不需要改，但**仍然要新增申请单视图 + 契约测试**（现在申请人视图完全没定义） |
| **阻塞** | **是**（决定 `request_item.reject_reason` 这一列） |

### D-11「全部拒绝」怎么产生？「部分通过」和「未通过」操作一样吗？

| | |
|---|---|
| **推荐** | **界面上两个操作**（逐件勾选 = 部分通过；一个"拒绝整单"快捷按钮），**但服务端只有一个写路径**；`status` 一律由逐件结果**推导**，不直接写；提交审批时写 `reviewed_at`/`reviewed_by`，**用它区分"未审"与"审完全拒"** |
| **为什么需要独立判别位** | 在"取消勾选 = 拒绝"的模型下：若把未勾选项写成 `approved = false`，则**"全拒"与"未审"在数据行上无法区分**；若只写被勾选项、其余留 `NULL`，则**"全拒"根本落不到 `REJECTED`**。两条路都需要 `reviewed_at` |
| **顺带要确认一条新规则** | **申请单至少要有一件器材**（主稿现在没有这条约束，推导规则缺了它会有歧义） |
| **阻塞** | **是**（决定 `status` 是写出来的还是推导的，以及要不要 `reject` 端点） |

### D-12 申请人能不能撤回申请？

| | |
|---|---|
| **推荐** | **`PENDING` 时可撤回（v1 必做）；`APPROVED`/`PARTIAL` 时也可撤回**（若"项目取消"是高频场景就一并做） |
| **行为** | 撤回后 `request` 行**保留**并标记 `WITHDRAWN`，只 `DELETE` 对应的 `occupancy` 行（档期释放） |
| **`DELIVERED` 不能撤回** | 器材在外面，只能逐件归还 |
| **要请产品确认的** | "已批准后项目黄了"这个场景**有多频繁**？如果常有，v1 就要两个状态都能撤 |
| **若只做 v1（只允许 PENDING）** | `WITHDRAWN` 不再是死枚举值，但"批了之后项目取消"无解 |
| **阻塞** | **是**（决定要不要处理 `occupancy` 的 DELETE 路径 + `request` 行锁） |

### D-13 被拒之后怎么再申请？

| | |
|---|---|
| **推荐** | **不动原申请单。"再次申请" = 复制原单（预填未获批的件）另开一张新单**，走同一条 `POST /requests`。原单只读，理由与结果永不改写 |
| **理由** | 天然绕开"改已存在的单"这个复杂问题——原单是一份冻结的历史记录 |
| **若你要"改原单重审"** | 这是一个**比现在这份设计大得多的任务**：多轮审批 + `request_item` 级日期 + `status` 回退 + `occupancy` 对齐。**建议单独开一份设计，不要并进来** |
| **阻塞** | 否（推荐方案不需要新端点） |

### D-14 审批动作要不要留痕到库里？

| | |
|---|---|
| **推荐** | **要。新建 `request_event` 表**（候选 2） |
| **为什么不能只靠日志** | 运行时篇 R1.1 规定"只在日志里的事会在日志被轮转掉的那天消失"，而日志大约保留 100 天。审批事实显然要永久可查 |
| **三个候选** | ① `equipment_history.action` 加 `REQUEST_REVIEW` —— 会污染"这件器材发生过什么"的主线（一次审批要为每件被拒器材写一条）<br>② **新建 `request_event` 表** —— 最干净，一张新表 + 一个查询路径<br>③ 只靠 `request.reviewed_by`/`reviewed_at` + 逐件结果 —— 零成本，但**只有"最后一次"**，多轮审批会丢历史 |
| **一个佐证** | 运行时篇 R7.5 的上线验收清单有 16 条，**没有任何一条与申请审批有关**——覆盖了 readiness、优雅停机、并发互斥、可见性、`23P01`、磁盘满、CSV 编码、字段编辑、备份、日志，但没有"走一遍申请 → 审批 → 交付"。这和"审批不留痕"是同一件事在两个文档里的两次留白 |
| **阻塞** | **是**（决定要不要新表） |
